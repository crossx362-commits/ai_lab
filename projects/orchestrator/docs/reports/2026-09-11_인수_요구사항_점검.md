# 인수 요구사항 구현 대조 — 전체 완료 아님

점검 대상은 현재 대화의 오케스트레이터 `projects/orchestrator`다. 저장소 전체 Git 상태를 먼저 확인하고, 이 프로젝트의 진입점·설정·Provider·큐·복구·메모리·UI·로그·문서 및 연결된 검증 대상을 대조했다. 다른 ai_lab 프로젝트 전체를 검증한 보고서는 아니다.

**판정: 기반 구현은 상당 부분 있지만, 요청한 GPT + Ollama 장기 자율 운영 시스템은 미완성이다.** 보드의 88.9%는 등록 작업 중 DONE+PASS 8/9 비율이며, 이 요구사항 전체의 구현률이 아니다.

## 1. Git과 인수 상태

- 조사 시작 HEAD: `5665cc0d`, 브랜치 `master`. 강제 초기화·checkout·변경 삭제를 하지 않았다.
- 시작 시 수정 6파일: `.codex/hooks.json`, 가드레일 원장, BOARD.md, README.md, board_commands.py, board.py. 미추적 항목은 보드 집계·잔여 한도 모듈, 테스트, 서비스 설치 도구, 보드 검증 보고서였다.
- 최근 커밋은 울온 target 연결(`87f25537`), Blender 검증 축(`85e3d708`), 보고서·활동 표시(`125a9c72`), 토큰 집계·컨텍스트 상한(`ddfdb306`) 등이다.
- Git 작성자 정보만으로 어느 AI가 작성했는지는 확정할 수 없다. SESSION_HANDOFF.md의 설명과 실제 코드를 비교했다. 앞선 Codex 작업과 다른 세션 변경이 섞여 있다.

- TODO/FIXME 검색에서 기능 미구현 목록은 나오지 않았다. 추상 메서드의 NotImplementedError와 리뷰 프롬프트의 TODO 문구만 확인됐다. TODO가 없다는 사실은 완성을 뜻하지 않는다.

## 2. 원래 시스템과 현재 구조

현재 시스템은 Unity/Blender 개발 목표를 작업으로 나누고, 격리된 Git worktree에서 AI가 구현한 결과를 컴파일·테스트·리뷰한 뒤 작업 브랜치에 커밋하는 오케스트레이터다. 메인 브랜치 자동 병합은 하지 않는다.

진입점은 `orch` → `orch_core.cli`, 보드는 `tools/board.py`, 보드 명령 소비자는 `orch_core.board_commands`다. 개발 작업 SQLite와 보드 명령 SQLite가 따로 있고, Provider 캐시·메모리 표본은 JSON으로 저장한다. Claude/Grok/Codex는 CliAgent 어댑터로 분리돼 있지만 Ollama는 별도 요약 함수 경로다.

## 4. 이번에 수정하고 검증한 문제

실제 로컬 Python CLI가 파일을 만든 뒤 `exit 7` 하도록 하고, 운영 DB와 분리한 임시 SQLite/Git에서 재현했다. 컴파일 게이트는 이 테스트에서 결정적인 시험 응답으로 대체했다. 실제 Unity 전체 통과를 의미하지 않는다.

1. 구현 CLI 실패 후 파일이 남으면 게이트를 거쳐 DONE이 될 수 있었다. 이제 실패로 기록하고 파일을 보존한다.
2. 계획 CLI 실패 후 plan.json이 남으면 READY/작업 목록으로 등록됐다. 이제 BLOCKED로 남긴다.
3. 리뷰 CLI 실패 후 approve JSON이 남으면 승인됐다. 이제 UNKNOWN이며 다른 검토 후보를 확인한다.
4. 리뷰 파일 누락으로 작업 상태가 REVIEW여도 실행 함수가 0을 반환했다. 상위 계획이 이를 완료로 취급했다. 이제 DONE만 0을 반환한다.
5. 실행 도중 Provider 소진으로 BLOCKED_CLOUD_REQUIRED가 되어도 반환값은 일반 실패 1이었다. 이제 3을 반환해 기존 Provider 대기 분기로 전달한다. 같은 작업 재개 구조는 별도 미해결이다.
6. JSON 문법은 맞지만 객체가 아닌 계획/리뷰 응답(`[]`, `null`, 숫자)에서 AttributeError가 났다. 이제 실패/UNKNOWN으로 처리한다.

수정 전 6개 테스트: 실패 5 + 예외 1. 수정 후 6개 모두 통과. 기존 보드 테스트를 합친 50개도 통과했다.

## 5. 남은 핵심 결함 — 재현 근거

### P1: 계획의 다음 작업에 선행 코드가 없다

`cli.cmd_run_plan`은 완료 key로 실행 순서만 제어한다. `execute_goal`과 `gitwt.create_worktree`는 각 작업을 대상 저장소 HEAD에서 시작한다. 앞 작업 브랜치의 결과를 다음 작업 기반으로 넘기지 않는다.

격리 재현: T1이 first.py를 만든 뒤 T2가 first.py 존재를 검사했다. T2는 `inherited=False`였고 계획은 DONE이었다. 검증 게이트는 시험용 응답이므로 코드 전달 문제를 독립적으로 측정한 결과다. 완료 브랜치의 변경을 다음 작업 기반에 전달하는 구조가 필요하다. 메인 브랜치 강제 병합으로 해결해서는 안 된다.

근거: `orch_core/cli.py:849`, `orch_core/gitwt.py:78`, `logs/takeover-continuity-evidence.json`.

### P2: 재개가 같은 작업을 이어가지 않는다

`cmd_resume_blocked`는 기존 worktree·base_commit·실패 문맥을 전달하지 않고 새 execute_goal을 부른다. `requeue`도 이전 실행을 보관하고 자리표시를 다시 세운다.

격리 재현: 기존 task #1의 partial.py는 보존됐지만 재개가 task #2를 만들었고, 새 작업은 partial.py를 볼 수 없었다(`same_worktree=false`, `inherited=False`). 파일 삭제는 없지만 이전 작업이 다음 실행에 연결되지 않는다.

근거: `orch_core/cli.py:1040`, `orch_core/handoff.py:58`, `logs/takeover-continuity-evidence.json`.

### P2: Provider 한도 상태를 다른 조회가 덮을 수 있다

`probe_all`이 처음 읽은 JSON 전체를 마지막에 다시 저장한다. 그 사이 다른 실행에서 mark로 기록한 최신 RATE_LIMITED/cooldown이 사라질 수 있다. 원자적 교체와 동시 갱신 병합/잠금이 없다.

격리 재현: 인증 검사 도중 새 RATE_LIMITED(900초)를 기록했지만 마지막 파일은 AVAILABLE, cooldown_until=0이었다. 같은 계정을 쓰는 codex/astra의 한도 상태도 개별 이름으로 저장돼 함께 관리되지 않는다.

근거: `orch_core/providers.py:94`, `orch_core/providers.py:250`, `logs/takeover-provider-race.json`.

### 추가 확인·개선 대상

- Provider 승계 시 attempts 값을 내리지만 for 루프의 다음 회차는 소비된다. 최종 회차에 Provider가 실패하면 대체 후보가 있어도 호출되지 않는다.
- plan은 구현/리뷰와 달리 동일한 Provider 후보 선택·승계 경로를 거치지 않는다.
- Grok 조사 설정과 router의 research 플래그는 있었지만 execute_goal에서 조사 실행으로 소비되지 않는다. 기본 research_agent는 이번에 null로 바꿨다.
- 작업별 done_criteria는 리뷰에 전달되지만 일반 구현 프롬프트의 독립 입력으로는 전달되지 않는다.
- 오래된 프로세스 그룹을 정리하는 복구 함수는 저장된 PGID를 사용한다. 실제 회수 전 프로세스 재사용 검증을 강화해야 한다. 이번 점검에서는 dry-run만 실행했다.
- SESSION_HANDOFF.md의 STOP 켜짐·계획 7 상황은 현재 상태와 맞지 않는다. 다음 인수 때 정적 문구 대신 실측 상태를 우선해야 한다.
