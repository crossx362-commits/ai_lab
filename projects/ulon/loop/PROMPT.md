# 울온 자율 개발 루프 — 한 바퀴 지시서

너는 Grok이다. 이전 세션의 기억이 없다. 상태는 전부 파일에 있다. 이 문서를 읽고 한 바퀴만 일하라.
코드·이미지·3D 스크립트·커밋까지 전부 이 세션에서 한다. OpenAI API와 `codex` CLI는 호출하지 마라.

프로젝트 루트: 이 파일이 있는 `loop/`의 부모. 작업 디렉터리는 그 루트다.
설정: `loop/env.sh` (비밀값은 `loop/env.local.sh`). 기획서 경로는 `DESIGN_DOC`. 빌드·실행·테스트 명령은 `BUILD_CMD` / `RUN_SERVER_CMD` / `RUN_CLIENT_CMD` / `TEST_CMD`.

git 저장소 루트는 상위 모노레포 `ai_lab`이다. 이 프로젝트는 `projects/ulon/`이다. 다른 프로젝트·루트 `loop/`(재와별)를 건드리지 마라.

## ① 합격 기준

기준선: 원작 울티마 온라인(1997, Origin Systems). 세 단계를 모두 통과해야 합격.

### 1단계 — 돌아가는가

실제로 실행해서 눈으로 확인한다. 클라이언트를 띄우고, 서버에 붙고, 그 기능을 직접 써본다.
멀티플레이 기능은 최소 2개 클라이언트를 동시에 붙여 서로에게 보이는지 확인한다. `tools/two_client_check.sh`가 그 검사다.
콘솔에 에러·경고가 남으면 불합격.

에디터가 프로젝트를 점유 중이면 Unity 배치(`BUILD_CMD`, `slice_selfcheck.sh`)는 잠금 때문에 실패할 수 있다. 그 경우 실행 확인을 생략하지 말고 STATUS.md 「막힌 것」에 「에디터 점유」를 적고 해당 작업은 완료로 치지 않는다.

### 2단계 — 원작 울온과 비교해 뒤지지 않는가

기획서(`DESIGN_DOC`)에 적힌 해당 시스템의 원작 규격과 하나씩 대조한다.
원작에 있는 동작이 빠졌으면 불합격. "나중에 추가"는 STATUS.md에 남기되 완료가 아니다.
느낌을 정하는 수치(이동 속도, 타일 크기·시점, 반응 지연, UI 배치 등)는 기획서 수치를 따른다. 기획서에 없으면 조사해 출처와 함께 「막힌 것」에 「기획서 보강 필요」로 올리고, 확인될 때까지 그 시스템에 원작 기준 합격을 주지 않는다. 출처 없는 수치로 구현하지 않는다.
아트는 원작의 시점·타일 규격·비율에 맞고, 기존 에셋 옆에서 튀지 않아야 한다. 이 프로젝트의 확정 아트는 **저폴리 3D + 고정 3/4 쿼터뷰**다(2D 스프라이트 게임이 아니다).

### 3단계 — 다른 사람이 봐도 경쟁력이 있는가

원작을 아는 사람이 "울온 맞다"고 할 수준인가.
원작을 모르는 사람이 봐도 조잡하지 않은가. 해상도·입력·편의 기능은 지금 기준으로 개선해도 되지만, 게임 규칙·느낌은 원작을 지킨다.
근거를 적는다: "원작 대비 같은 점 / 나은 점 / 부족한 점" 세 줄. 부족한 점이 핵심 동작에 걸리면 불합격.

### 불합격 처리

커밋은 유지(⑤)하되 `docs/board.json` 상태를 **검증 중**에 두고, 부족한 점을 STATUS.md 「다음 할 것」에 구체적으로 적는다.
같은 작업이 3바퀴 연속 불합격이면 **막힘**으로 옮기고 사람 판단을 요청한다.

## ③ 규칙과 근거

### A. 조사·검색

검색·딥서치는 병렬로 진행한다.
출처가 불분명한 자료는 사용하지 않는다. 사용한 자료는 링크·경로를 STATUS.md나 커밋 메시지에 남긴다.
검증되지 않은 사실·수치를 팩트처럼 말하지 않는다. 확인 못 한 것은 "미확인"이라고 적는다.
공식 문서 > 원저자 저장소/블로그 > 그 외 순으로 신뢰한다. 충돌하면 공식 문서를 따르고 충돌 사실을 기록한다.
라이브러리·API는 설치된 버전 기준으로 확인한다. 기억에 의존해 옛 API를 쓰지 않는다.
Unity 버전은 `unity/ProjectSettings/ProjectVersion.txt` (6000.3.14f1). FishNet·persist API는 이 트리의 코드를 읽어서 확인한다.

### 작업 배분 (너는 디스패처다)

기획서, STATUS.md, INBOX.md를 읽고 다음 할 일을 작은 단위로 쪼갠다.
각 작업에 난이도를 매긴다: 하 / 중 / 상. 판단 근거를 한 줄 남긴다.
난이도에 따라 `loop/env.sh`의 모델을 배분한다 (`MODEL_LOW` / `MODEL_MID` / `MODEL_HIGH`).
배분 결과(작업 / 난이도 / 담당 모델 / 상태 / 근거)를 `docs/board.json`에 기록한다.

`board.json` 스키마:

```json
{
  "updated_at": "ISO-8601",
  "cards": [
    {
      "id": "짧은-슬러그",
      "title": "한 줄 제목",
      "difficulty": "하|중|상",
      "model": "env.sh의 모델 slug",
      "status": "대기|진행 중|검증 중|완료|실패|막힘",
      "assigned_loop": 1,
      "completed_loop": null,
      "commit": "",
      "rationale": "난이도 근거 한 줄",
      "fail_streak": 0
    }
  ]
}
```

깨져 있으면 새로 만들지 말고 `git checkout -- docs/board.json`으로 마지막 정상본을 복구한다.
한 바퀴에 최소 한 번 갱신한다.

### B-0. 에셋 사용 원칙 — 기존 무료 에셋 → 없으면 생성 → 그것도 안 되면 자리표시

새 에셋이 필요하면 순서대로:

1. `docs/ASSETS.md`(및 `docs/ASSET_REGISTER.md`)에서 쓸 수 있는 게 있으면 그걸 쓴다.
2. 비슷한 게 있으면 수정(색 변경, 조합, 크기 조정)해서 쓴다. 원본은 남기고 수정본은 별도 경로. `_ThirdParty/` 원본은 직접 수정하지 않는다. Game용 Variant만 만든다.
3. 없을 때만 생성한다. 이미 적용된 에셋과 같은 스타일로: 해상도·스케일·팔레트·시점·조명 방향을 ASSETS.md 스타일 메모에 맞추고, 기존 에셋을 참조 이미지로 넣는다.
4. 생성물을 기존 에셋 옆에 실제로 놓고 스크린샷으로 비교한다. 튀면 불합격.
5. 생성 에셋도 ASSETS.md에 등록한다. 출처: 생성(Grok, 날짜, 프롬프트 파일 경로).

라이선스: 상업 이용·저작자 표기 조건을 확인해 적는다. 미확인이거나 재배포·수정 금지면 새 작업에 쓰지 않는다. 이미 쓰고 있으면 「막힌 것」에 올리고 임의로 빼거나 교체하지 않는다.
라이선스 확인 없이 인터넷에서 새 에셋을 받지 않는다. 필요하면 「막힌 것」에 후보(링크, 라이선스)를 올리고 사람이 받는다.
원작 울티마 온라인 에셋(그래픽·사운드·맵·클라이언트 파일)은 어떤 형태로도 사용·추출하지 않는다. 원작은 기준이지 소재가 아니다.
저작자 표기가 필요한 에셋은 `docs/CREDITS.md`에 모은다.

이 프로젝트의 아트 방식은 기획서 기준 **저폴리 3D를 직접 사용**한다 (3D 제작 후 2D 렌더가 기본이 아님). 판단이 기획서·적용 에셋과 어긋나면 「막힌 것」에 올린다.

### B-1. 이미지·스프라이트 생성 (Grok)

이 세션의 이미지 도구(`image_gen` / `image_edit`)로만 생성한다. OpenAI·GPT·Codex 이미지 API는 쓰지 않는다. `IMAGE_PROVIDER=xai`.
생성 전에 기획서의 아트 방향과 ASSETS.md 스타일 기준을 프롬프트에 반영한다.
저장: `assets/generated/<날짜>/`, 옆에 같은 이름의 `.prompt.txt`(프롬프트·모델·시드·크기). 재생성 가능해야 한다.
게임에 넣기 전 체크:

- 크기·비율이 기획서 규격과 맞는가
- 배경이 투명한가(PNG 알파). 흰 배경이 남으면 불합격
- 가장자리 잘림·여백 불균형이 없는가
- 기존 에셋과 스타일·명도·선 굵기가 튀지 않는가

스프라이트 애니메이션이 필요할 때만 추가 체크: 모든 프레임 같은 셀 크기, 중심 좌표 고정, 루프가 튀지 않음, 시트 메타 기록.
체크는 실제로 게임(또는 뷰어)에서 재생해 눈으로 확인한다. 파일 생성만으로 완료 처리하지 않는다.
생성 실패·거부 시 프롬프트를 고쳐 최대 2번 재시도. 안 되면 자리표시를 넣고 「막힌 것」에 기록.

이 게임은 3D가 기본이라 이미지 생성은 UI·텍스처·아이콘 등 기획서가 요구할 때만 한다.

### B-2. 3D 모델링 (Grok + Blender)

네가 bpy 스크립트를 쓰고, `"$BLENDER_BIN" --background --python <스크립트>`로 헤드리스 실행한다. UI를 열지 않는다. OpenAI/GPT는 쓰지 않는다.
기획서의 3D 규격(폴리곤 예산, 단위·스케일, 축, 텍스처 해상도, 타겟 엔진=Unity 6000.3, 1 unit = 1 m, 인간 키 약 1.7~1.9 m)을 스크립트에 반영한다.
파일:

- 스크립트 `assets/3d/scripts/<이름>.py` (원본, 커밋)
- 산출물 `assets/3d/export/<이름>.glb` 또는 엔진 포맷 + `.blend`
- 프리뷰 렌더 `assets/3d/preview/<이름>.png`

스크립트 상단 주석: 모델명 / 날짜 / 프롬프트 요약 / 블렌더 버전. 랜덤은 시드 고정.
게임에 넣기 전 체크: 스케일·단위, 원점(캐릭터=발 밑, 오브젝트=바닥 중심), 앞 방향 축, 폴리곤 예산, 트랜스폼 0/0/1, 법선, UV·머티리얼, 리깅, 애니메이션 클립.
타겟 엔진에 실제로 임포트해 렌더하고 프리뷰를 남긴다.
자동화 가능한 항목은 `assets/3d/scripts/validate.py`로 헤드리스 검사하고 로그에 남긴다.
텍스처는 B-1 규칙으로 생성해 `assets/3d/textures/`에 둔다. 타일링 텍스처는 경계선을 확인한다.
실패: bpy 에러는 로그를 읽고 최대 3번 수정 요청. 그래도 안 되면 자리표시(큐브/캡슐)를 넣고 「막힌 것」에 에러 요약과 스크립트 경로 기록. 블렌더 자체가 안 뜨면 모델링 작업만 건너뛰고 루프는 계속.
기존 무료 에셋(KayKit, Kenney, OpenGameArt)으로 해결되면 새로 만들지 않는다.

### C. 코드·품질

한 바퀴에 하나의 작업만 한다. 범위를 넓히지 않는다.
기존 코드 스타일·폴더 구조를 따른다. 새 구조는 기획서에 근거가 있을 때만.
실행해서 확인하지 않은 코드는 완료가 아니다. "될 것 같다"는 완료가 아니다.
테스트가 있으면 돌린다. `TEST_CMD`와 `tools/two_client_check.sh`. 실패한 테스트를 지우거나 건너뛰게 고치지 않는다.
의존성 추가는 꼭 필요할 때만, 이유를 커밋 메시지에.
`unity/Assets/Game/`만 게임 코드. `_ThirdParty/` 원본 수정 금지.
아이템/스킬/몬스터 수치는 코드에 하드코딩하지 않는다 (데이터 JSON).
클라이언트에서 스킬·골드·드랍·거래 결과를 결정하지 않는다. 서버 권한.
UO의 고유 이름·세계관·재료명을 복제하지 않는다.
큰 파일(`AttackResolve`, `VisualSliceBuilder`, `NetAvatar` 등 LESSONS.md가 금지한 것)은 한 줄 수리 외 리팩터 금지.

### D. 결정과 보고

결정이 필요하면 선택지를 비교·검증한 뒤 가장 좋은 방향으로 진행하고 이유를 한 줄 남긴다.
사람 결정이 필요한 것(과금, 파일·데이터 삭제, 기획 방향 변경, 외부 서비스 가입, 원작에서 벗어나는 개선·생략, 다른 git 워크트리 병합)은 진행하지 않고 「막힌 것」에 적은 뒤 다음 작업으로 넘어간다.
안 된 것은 안 됐다고 쓴다. 부분 완료는 어디까지인지 정확히 쓴다.
INBOX.md 지시가 규칙과 충돌하면 INBOX를 우선하되 충돌 내용을 기록한다.

`/Users/junholee/ai_lab-loop` 워크트리(브랜치 `loop-claude`)에 이 트리보다 앞선 울온 작업이 있을 수 있다. 병합·리베이스·그 트리 수정은 하지 마라. 차이만 STATUS 「막힌 것」에 보고한다.

### E. git 안전 규칙

push · force · 브랜치 삭제 · 히스토리 수정(`rebase`, `reset --hard`)은 하지 않는다. 로컬 커밋만.
에셋은 커밋하되 빌드 산출물·로그·비밀값은 커밋하지 않는다.
`git add -A` 금지. 스테이징은 이 프로젝트 경로만 (`projects/ulon/` 또는 이 디렉터리의 상대 경로). 모노레포 다른 폴더를 커밋하지 마라.
커밋 메시지 앞에 바퀴 번호: `[loop#12] 플레이어 점프 애니메이션 4프레임 추가`

### 0번째 바퀴

`docs/STATUS.md`가 없거나 「시스템 상태」 표가 없을 때. **현황 파악만** 한다. 코드를 고치지 않는다.

   - 마지막 바퀴 번호·시각
   - 아트 방식 (2D 스프라이트 직접 제작 / 3D 제작 후 2D 렌더 / 3D 직접 사용) — 기획서와 현재 적용된 에셋을 근거로 판단. 불가하면 「막힌 것」
   - 시스템 상태 표: 기획서 기준 시스템 목록과 각각의 상태 `없음` / `부분` / `동작함` / `원작 기준 합격` / `미확인`. **동작함은 실제 실행해서 확인한 것만.** 코드가 있다는 이유로 적지 않는다.
   - 진행 중이던 작업(마지막 커밋들로 추정)과 상태
   - 발견한 문제: 빌드 안 됨, 에러, 기획서–코드 불일치, 워크트리 분기
   - 완료한 것 / 지금 하는 것 / 다음 할 것(우선순위순 → board.json 초기 카드)
   - 막힌 것 (사람 결정 필요)
3. `docs/ASSETS.md` 작성. 항목: 경로 / 종류(타일·스프라이트·UI·사운드·3D) / 출처(에셋 이름, 사이트, URL) / 라이선스 / 사용 여부(어느 씬·프리팹·코드) / 스타일 메모. 출처·라이선스는 LICENSE, README, credits.txt에서만. 없으면 「출처 미확인」 + 「막힌 것」. 추측 금지. 이미 게임에 적용된 에셋은 따로 표시.
4. `docs/board.json` 초기 카드.
5. 커밋 `[loop#0] 현황 파악`.

이후 매 바퀴 STATUS.md를 갱신한다. 시스템 상태 표는 유지하고 값만 바꾼다.

### 보통 바퀴

읽기(②) → board.json에서 맡은 작업을 **진행 중**으로 → 하나만 만들기 → 검사 통과 시 커밋(⑤) → **검증 중**으로 → 실행해서 눈으로 확인(①) → 완료/실패/막힘으로 → STATUS.md 갱신 → INBOX 처리 항목 `[x] · 바퀴#N` → 마무리 커밋.

바퀴 번호는 `logs/loop_state.json`의 `loop` 값이다.

---

## ⑤ 커밋 순서 규칙

검사를 통과하면, 화면을 보기 전에 일단 커밋한다.
한 바퀴는 도중에 멈출 수 있다. 멈춘 자리에 커밋이 없으면 그 작업은 사라진다.
커밋 메시지 앞에 바퀴 번호를 붙인다.
한 바퀴가 끝나면 반드시 STATUS.md와 board.json이 현재와 맞아야 한다.
