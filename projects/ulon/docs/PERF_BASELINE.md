## 프레임 시간 기준선 (2026-09-07 실측, 이 맥)

`bash tools/frame_probe.sh` — Development 스탠드얼론을 빌드해 한 번 실행하고(`-frameprobe`),
세 지점에서 VSync를 풀고 180프레임을 모은다. **매 랩 돌리지 않는다**(빌드 비용). 결과 `builds/qa/frame_times.md`.

| 지점 | 중앙값(ms) | p95(ms) | 중앙값 기준 fps |
|---|---:|---:|---:|
| 던전 1 방 | 4.5 | 24.0 | 221 |
| 마을 광장 | 4.3 | 21.5 | 231 |
| 월드 조망 | 3.0 | 8.2 | 335 |

**읽는 법과 한계**
- 중앙값 3~4.5ms(220~335fps)다 — 이 맥에서 **지금 성능은 문제가 아니다**. 개수 상한은 그래서 예산이 아니라 회귀 경보다.
- p95가 21~24ms로 튄다. Development 빌드의 셰이더 준비·GC로 보이나 **원인을 확인하지 않았다** — 단정하지 않는다.
- 월드 조망이 방보다 빠른 것은 거리 컬링 때문으로 보이지만 역시 미확인이다.
- 카메라를 좌표로 세우는 방식이라 프레임 구도가 QA 샷과 정확히 같지는 않다.
- 기계 한 대의 값이다. 사양이 다른 기계에서는 다시 재야 한다.

## 프레임 시간 — 지금 잴 수 있는가 (조사 2026-09-07)

**요약: 진짜 프레임 시간은 지금 자동으로 못 잰다.** 위 표의 「렌더 제출(ms)」은 `Camera.Render()`
호출의 CPU 시간이라 GPU 대기·물리·스크립트·VSync가 빠져 있다 — **대리 지표다.**

| 경로 | 지금 가능한가 | 근거 |
|---|---|---|
| `-batchmode -nographics` 셀프체크 | **불가** | 렌더 루프 자체가 없다. 카메라 렌더을 넣었더니 세그폴트(VFX 랩 실측). |
| `-batchmode`(그래픽) 편집기 | **부분** | `Camera.Render()`를 직접 부르는 CPU 시간만. 프레임 루프가 아니라 「제출 1회」다. 지금 재는 값이 이것. |
| PlayMode 테스트(배치) | **불가(패키지 없음)** | `com.unity.test-framework`가 `Packages/manifest.json`에 없다. 넣으면 의존성 추가라 승인 대상. |
| 스탠드얼론 빌드 실행 | **가능하지만 미구축** | Development 빌드에서 `FrameTimingManager`·`Time.deltaTime`을 파일로 남기면 실측이 된다. 빌드 잡·실행 자동화가 아직 없다. |
| 유니티 프로파일러 연결 | **수동만** | 사람이 에디터를 열고 붙여야 한다. 무인 루프에서 못 쓴다. |

**다음 랩 후보(택1, 검수 판정 필요)**
1. 스탠드얼론 Development 빌드 + 프레임 시간 로거(가장 정직한 값, 빌드 시간 비용 큼).
2. `com.unity.test-framework` 도입 후 PlayMode에서 N프레임 측정(의존성 추가 = 승인 필요).
3. 지금처럼 렌더 제출 시간을 **대리 지표로만** 쓰고, 상한은 개수 축에 건다(가장 싸고, 가장 약하다).

## 릴리스 재측정 (2026-09-08, 검수 지시)

「p95 21~24ms 튐」이 **게임의 성질인지 계측기의 성질인지** 가르기 위해 같은 장면을 릴리스 빌드로
다시 쟀다(`bash tools/frame_probe.sh --release`, 결과 `builds/qa/frame_times_release.md`).

| 지점 | Development 중앙/p95 | **릴리스 중앙/p95** |
|---|---|---|
| 던전 1 방 | 4.5 / 24.0 ms | **1.6 / 2.0 ms** |
| 마을 광장 | 4.3 / 21.5 ms | **2.8 / 3.2~3.3 ms** |
| 월드 조망 | 3.0 / 8.2 ms | **0.8 / 0.9 ms** |

두 번 돌려 편차 0.1ms 안. **결론: p95 튐은 Development 빌드의 성질이었다** — 프로파일러 훅·디버그
검사를 달고 도는 빌드로 잰 값이다. 릴리스에서는 p95가 중앙값의 1.2배 안이고 어느 지점도 3.3ms를
넘지 않는다(60fps 예산 16.7ms의 20%).

**교훈: 계측기가 결과를 만든다 — 무엇으로 쟀는지가 곧 무엇을 쟀는지다.** 「튐」을 게임의 문제로
적어 두고 원인을 찾지 않은 채 몇 랩을 지났다(원장에 「미결은 저절로 닫히지 않는다」로 남긴 그 계열).


## 머티리얼 축의 자를 바꿨다 (2026-09-08, 검수 판정)

마을 광장의 「머티리얼 종류」가 84로 상한 83을 넘겨 경보가 울렸다. **상한을 올리는 대신 내역을
찍어 봤다**(경보에 목록을 붙여 둔 이유가 이것이다):

```
colormap ×34, grass ×7, Glow ×4, dirt ×3, texture ×2, 그 외 34종
```

34개 `colormap`은 **Kenney 프롭 34개가 각자 품고 있는 같은 재질**이었다(FBX 내장 재질이라 경로가
전부 다르다). 프롭을 하나 놓을 때마다 자동으로 오르는 숫자는 「무거워졌다」의 신호가 아니다.

- **새 자**: `PerfReport.MaterialKey` = 셰이더 + 메인 텍스처 에셋 + 색. 「그리는 그림의 가짓수」.
  한계 선언: 광택·타일링만 다른 두 재질은 한 종류로 센다.
- **양방향 NC**(`AssertPerfMaterialRulerNegativeControl`): ㉠ 같은 그림의 사본을 물리면 36→36(안 늚)
  ㉡ 씬에 없던 다른 재질을 물리면 36→37이고 그 값으로 판정하면 경보가 울린다. 실측으로 둘 다 봤다.
- **렌더러 수는 별도 축으로 유지**하되 마을 기준선을 730 → **852**(오늘 실측)로 갱신했다.

| 지점 | 렌더러(실측→상한) | 삼각형 | 머티리얼 종류(새 자, 실측→상한) |
|---|---:|---:|---:|
| 던전 1 방 | 99 → 160 | 26,005 → 43,000 | 10 → 15 |
| 마을 광장 40m | 852 → 1,278 | 162,698 → 191,000 | 36 → 54 |
| 월드 조망 200m | 2,259 → 3,600 | 341,425 → 507,000 | 39 → 59 |

머티리얼 실측이 39·42가 아니라 36·39인 것은 같은 랩에서 **돌길 도포 재현성 결함**을 고쳤기 때문이다
(아래). 상한은 전부 실측 × 1.5.

## 재현성 결함 — 같은 소스, 두 트리가 다른 결과 (2026-09-08)

증상: 루프 worktree에서는 `무텍스처 재질 렌더러 618개`(`Dungeon1/ground_pathTile/Visual/:dirt`)로
빨간불인데 공유 트리는 같은 커밋에서 통과했다. 순서대로 짚었다 —
①텍스처 git 추적 여부: **추적된다**(미추적·무시 파일 0건) ②`.mtl` 경로: `.mtl`이 없다(내장 재질)
③`.meta` 임포터 설정: 두 트리 **md5 동일**(`materialLocation: 1` = 내장). 즉 소스는 같다.

원인은 **도포 시점**이었다. 풀·흙 도포(`PaintSceneByName`)가 `ApplyVillageMaterials`, 곧 **마을을 짓는
도중**에만 돌았다. 던전 입구·방의 돌길 타일은 그 뒤에 세워지므로 **그 판에서는 안 칠해진 채** 남고,
씬은 매 실행 저장되므로 **다음 실행에서야** 이름 기준 도포에 걸려 초록이 된다. 그래서 「그 물건이
언제 생겼나」에 따라 트리마다 결과가 갈렸다. 환경 차이가 아니라 재현성 결함이다.

수리: 바위가 이미 그랬듯 도포를 `EnsureWorldPropMaterials`(소품이 **전부 놓인 뒤**에 도는 자리)로
옮겼다. 확인: 씬을 커밋 상태로 되돌린 뒤(첫 판과 같은 조건) 셀프체크 EXIT=0.

**852는 목표가 아니라 현재값이다**(검수 지시 2026-09-08). 렌더러 기준선을 730에서 852로 갱신한 것은
「이만큼 써도 된다」는 허가가 아니라 **오늘 실제로 그만큼 서 있다**는 기록이다. 다음 사람이 이 수를
예산으로 읽고 채우지 마라 — 늘어난 이유를 못 대면 그건 회귀다.

## 지형 셰이더 교체 재측정 (2026-09-09, 랩 ⑧ — 검수 조건 ①)

지형을 유니티 기본 셰이더에서 `Ulon/TerrainTriplanar`(픽셀당 도포 9겹 × 3축 = 텍스처 페치 27회)로
갈았다. **셰이더를 갈면 지금 기준선은 다른 세계의 값이므로** 같은 씬을 두 번 쟀다 —
차이가 셰이더 값인지 씬이 달라진 값인지 가르기 위해 **대조군을 실제로 만들었다**
(`terrain.materialTemplate = null`로 기본 셰이더 복귀 후 같은 절차로 빌드·측정, 그 뒤 되돌림).

| 지점 | 대조군: 기본 지형 셰이더 중앙/p95 | **삼면 투영 중앙/p95** | 셰이더 값 |
|---|---|---|---:|
| 던전 1 방 | 1.7 / 9.0 ms | **2.1 / 9.0 ms** | +0.4 ms |
| 마을 광장 | 2.1 / 2.3 ms | **2.3 / 2.8 ms** | +0.2 ms |
| 월드 조망 | 1.3 / 1.4 ms | **1.4 / 1.6 ms** | +0.1 ms |

측정: `bash tools/frame_probe.sh --release`, 두 판 다 같은 커밋·같은 기계·릴리스 빌드.

**읽는 법**: 지형이 화면을 가장 많이 덮는 **월드 조망에서 값이 가장 싸다**(+0.1ms). 지형 픽셀은
멀수록 밉으로 내려가고, 화면을 채우는 것은 도리어 소품·캐릭터이기 때문으로 보인다(미확인).
던전 방의 +0.4ms는 지형이 거의 안 보이는 자리라 셰이더 탓으로 보기 어렵다 — 빌드 간 편차일 수
있다(대조군 p95 9.0ms가 양쪽 같은 것도 그쪽을 가리킨다). 어느 쪽이든 60fps 예산 16.7ms의 14% 안.

**대조군을 안 만들었으면 틀리게 적을 뻔했다.** 지난 기준선(2026-09-08)과 그냥 비교하면 월드 조망이
0.8 → 1.4ms로 **1.7배**다. 그 사이 씬 내용이 달라졌을 뿐인데(아래) 그 값을 셰이더 값으로 적었을
것이다. **무엇과 비교했는지가 곧 무엇을 쟀는지다** — 이 문서 위쪽 「계측기가 결과를 만든다」의 짝.

### 렌더러·삼각형이 크게 줄었다 — 닫힘 (2026-09-09, 검수 지시 ①)

증상: 마을 광장 렌더러 852 → **374**, 삼각형 162,698 → **82,189**. 전후 광장 샷은 같았다.
**줄어든 것도 설명 못 하면 회귀**이므로 의심(랩 ④ 실내 이전)을 **확인**했다 — 성능 때와 같은
방법으로 **옛 씬을 되살려서** 쟀다:

```bash
git checkout a52625f9^ -- unity/Assets/Game/Scenes/Bootstrap.unity   # 랩 ④ 직전 씬

```

랩 ④ 직전 씬 실측: 마을 광장 렌더러 **852** · 삼각형 **162,698** · Skinned **105**.
지금 씬: **374 · 82,189 · 42**. 지난 기준선과 **자릿수까지 같다** — 차이는 전부
`a52625f9`(「실내/실외를 이름 아닌 자리로 가른다」)에서 실내가 40m 반경 밖으로 나간 몫이다.
없어진 물건이 아니라 **자리를 옮긴 물건**이다(Skinned 105→42도 같이 옮겨간 실내 사람들).

**회귀 아님.** 위쪽 표의 374·82,189가 오늘의 현재값이다.
