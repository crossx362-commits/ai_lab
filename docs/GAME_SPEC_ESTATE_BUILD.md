## 1. 문제 — 「위치가 안 맞는다」의 정체

스크린샷을 보면 건물이 마름모 위에 **앉아 있지 않고 떠 있거나 옆 칸을 침범한다.**
코드를 열어 원인을 셋으로 좁혔다.

### 1-1. 격자에 **자리 크기(footprint)** 개념이 아예 없다 ← 근본 원인

`EstateGrid`는 한 칸에 `Cell` 하나를 넣는다. 즉 **모든 건물이 논리적으로 1칸**이다.
그런데 화면 크기는 `EstateYard.BuildingBox`가 크기표(`art/prop_scale.json`)의
**월드 유닛**에서 뽑는다 — 격자와 아무 관계 없는 숫자다.

```
bh = units × (tw / 4.2)      // 4.2 = TileUnits, 한 칸이 담는 지면 폭(유닛)
bw = bh × (텍스처 종횡비)
```

실측 결과(스프라이트 원본 + 크기표):

| 건물 | 원본 px | 종횡비 | units | 폭/칸 | 높이/칸 |
|---|---|---|---|---|---|
| 본성 | 1487×1516 | 0.98 | 5.2 | **1.21** | 1.24 |
| 광산 | 1783×1626 | 1.10 | 4.0 | **1.04** | 0.95 |
| 창고 | 1522×1803 | 0.84 | 3.8 | 0.76 | 0.90 |
| 수비대 | 1799×1271 | 1.42 | 3.7 | **1.25** | 0.88 |
| 대장간 | 1672×1694 | 0.99 | 3.8 | 0.89 | 0.90 |
| 영묘 | 1618×1809 | 0.89 | 3.2 | **0.68** | 0.76 |
| 탑 | 1248×1885 | 0.66 | 4.8 | 0.76 | 1.14 |
| 경매장 | 1596×1569 | 1.02 | 3.9 | 0.94 | 0.93 |

**폭이 0.68칸에서 1.25칸까지 흩어진다.** 1칸을 넘는 것(본성·광산·수비대)은 이웃 칸을
침범하고, 0.7칸짜리(영묘)는 제 자리에 비해 작아 떠 보인다. **크기의 진실이 격자가 아니라
아트 종횡비에 있는 것**이 문제다 — 이 저장소가 반복해 겪은 「진실이 두 곳으로 갈라짐」이다
(2026-08-18 전투 유닛에서 같은 계열을 고쳤고, 그때 영지도 크기표를 읽게 바꿨지만
**격자와 맞추는 일은 안 했다** — WORKLOG의 「바닥 다이아몬드와의 정렬은 미확인」이 이것이다).

### 1-2. 건물이 마름모 **중심**이 아니라 그 위에 앉는다

```csharp
float sit = cell == Wall ? 0.55f : 0.42f;
return new Rect(p.x + (tw - bw) * 0.5f, p.y + th * sit - bh, bw, bh);
```

`p`는 칸의 좌상단이고 마름모의 중심은 `p.y + th × 0.5`다. `sit = 0.42`면 밑동이
중심보다 **0.08×th 위**에 놓인다 — 모든 건물이 조금씩 공중에 뜬다. 성벽만 0.55로
따로 맞춰 놓은 것이 이 값이 손으로 맞춘 숫자라는 증거다.

### 1-3. 건설 팔레트가 하단 고정바에 가린다

스크린샷에서 팔레트 타일(`화살…·마법…·성벽 0·함정 0`)의 아랫부분이 내비 도크에
덮여 글씨가 반만 보인다. §16 위반이다.

### ⚠️ 아직 확인 못 한 것 (구현 1단계에서 계측한다)

스크린샷의 **긴 헛간**은 어느 전용 아트의 종횡비와도 안 맞는다(전용 8종은 전부
0.66~1.42인데 그 헛간은 눈대중 2 이상). `EstateBuildings.PropOf`가 전용 그림을 못 찾아
`OldOf`(`village_barn_0`)로 **조용히 폴백**하고 있을 가능성이 있다.
`HasDedicated`는 `Resources.Load<Texture2D>`로 판정하는데, 이 저장소는 **png가
Texture2D가 아닌 타입으로 임포트돼 로드가 상시 실패한 전례**가 있다(CLAUDE.md
「임시 대체물이 본물을 가린다」). **추측하지 말고 폴백이 일어나면 경고를 찍게 만든 뒤
화면으로 확인한다.** 폴백이 맞다면 1-1의 크기 분석은 일부 건물에 대해 무의미하다.

## 2. 설계

### 2-1. 자리 크기를 격자가 소유한다 (1-1의 답)

건물마다 **칸 단위 자리 크기**를 정의하고, 화면 크기는 거기서만 낸다.

```csharp
// EstateGrid
public static Vector2Int FootprintOf(Cell c) => c switch
{
    Cell.Keep      => new Vector2Int(2, 2),   // 본성이 가장 크다
    Cell.Warehouse => new Vector2Int(2, 1),
    Cell.Mine      => new Vector2Int(2, 1),
    Cell.Barracks  => new Vector2Int(2, 1),
    Cell.Smith     => new Vector2Int(1, 1),
    Cell.Auction   => new Vector2Int(1, 1),
    Cell.Mausoleum => new Vector2Int(1, 1),
    _              => new Vector2Int(1, 1),   // 방어 건물은 전부 1칸
};
```

- 여러 칸을 차지하는 건물은 **좌상단 칸에 `Cell` 값을, 나머지 칸에 점유 표시**를 둔다.
  `Cell` enum에 값을 끼우면 옛 세이브가 깨지므로(주석에 이미 경고가 있다)
  **점유는 별도 배열**로 들고 저장 문자열 뒤에 덧붙인다.
- 화면 상자는 자리 크기에서 낸다:
  `bw = footprint.x × tw`, `bh = bw / 종횡비` — 크기표(`prop_scale.json`)는
  **더 이상 영지 건물 크기에 관여하지 않는다**(필드 프랍용으로만 남는다).
  그래야 크기의 진실이 한 곳(격자)이 된다.
- 밑동은 자리 마름모의 **중심**에 놓는다(`sit` 상수 제거).
  자리가 2×1이면 두 칸을 합친 마름모의 중심이다.

**아트가 이 규칙을 따라야 한다** — §2-4에서 다룬다.

### 2-2. 끌어서 옮기기 (오너 결정: 7동 전부, 경로 재계산)

- 건물을 누르면 **선택**, 끌면 **이동 미리보기**(반투명 + 놓을 칸 강조).
  `EstateYard`에 이미 있는 `_down`/`_dragging` 판정을 재사용한다 —
  마을 끌어 보기(Pan)와 충돌하지 않게 **건물 위에서 시작한 드래그만** 이동으로 본다.
- 놓을 수 없는 자리는 이유를 화면에 적는다(`EstateGrid.WhyCannotPlace`를 허브 건물까지
  확장): 자리 크기가 겹친다 / 격자 밖이다 / 건설 중이다.
- **침략 경로는 매번 재계산한다.** `PathLength`·`InvaderSide`는 이미 `_cells`를 매번
  훑으므로 코드 변경은 작다. 다만:
  - **창고가 움직이면 경로의 목적지가 바뀐다.** `StoreX/StoreY` 상수를 지우고
    `Cell.Warehouse`의 현재 위치를 찾아 쓴다. 이 상수는 `PathLength`·`DistToStore`
    두 곳에 박혀 있다.
  - **4면이 전부 막히는 배치를 거부**하는 `WouldSeal` 규칙은 그대로 살린다(§13-3).
    허브 건물은 `Walkable`이므로 성벽과 달리 길을 막지 않는다 — 규칙 변경 없음.

### 2-3. 건설·업그레이드 창 (오너: "건물 선택해서 바로 창 떠서 보게")

지금 `EstateBuild`는 **본성 레벨 하나만** 다룬다(`K_LV`·`K_TO`·`K_DONE` 단일 키).
이를 건물별로 일반화한다.

```csharp
// EstateBuild — 건물별 상태. 키에 Cell 이름을 붙인다.
int   Level(Cell c)
bool  Busy(Cell c)
long  RemainingSeconds(Cell c)
long  UpgradeCost(Cell c, int fromLevel)
double UpgradeSeconds(Cell c, int fromLevel)
bool  TryStartUpgrade(Cell c)
```

- **시간·비용 곡선은 기존 식을 그대로 쓴다**(`BaseSeconds 5분 × 1.6^(lv-1)`, 상한 24h;
  `8골드/시간 × 1.5^lv`). 건물마다 계수를 다르게 두고 싶으면 그건 §18 앵커에서
  유도해야 하는 밸런스 사안이라 **이번 범위 밖**이다 — 일단 전 건물 동일 곡선으로 열고,
  수치는 백호(밸런스)가 따로 본다.
- **본성 레벨이 상한**이다(클래시의 타운홀 규칙). 다른 건물은 `Level ≤ KeepLevel`.
  이유: 상한이 없으면 업그레이드 순서가 없어지고 §13-2의 본성 중심 진행이 무너진다.
- **완료는 수령 버튼 없이 시각이 되면 적용된다** — 기존 `EstateBuild`의 원칙(숙제 금지)을
  그대로 잇는다.
- **창**: 건물을 누르면 뜨는 패널. 현재 레벨 · 다음 레벨 효과 · 비용 · 시간 ·
  「업그레이드」와 「즉시 완료(러시)」. `EstateRush`가 이미 있으므로 재사용한다.
  창은 **화면 아래쪽 도크**로 띄운다(§16 — 마을을 가리지 않는다). 이번 세션에 고친
  `UiPages.LabelFit`·`CardPad`를 쓰면 글씨 잘림은 자동으로 안 난다.

### 2-4. 아트 (오너: 8동 재생성 + 티어 + 공사판)

**생성 규칙은 CLAUDE.md §5를 따른다** — 힉스필드 Nano Banana 2(`nano_banana_flash`) · 2k ·
`art/aigen.py`만. 확인함: `aigen.py`는 이미 힉스필드 CLI로만 나간다(Pro·Gemini로 안 보낸다).

> **오너 지시(2026-08-18): "영지 필요 리소스는 힉스필드로 만들어. 적어도 클래시 오브 클랜보다
> 퀄리티 좋아야 함."**
>
> 이 지시는 두 가지를 **덮어쓴다**(§0 권위 1번 = 오너 직접 지시):
> - WORKLOG의 「있는 대상은 다시 뽑지 않는다(중복 재생성 금지)」 — 영지 8동은 **다시 뽑는다.**
> - 「할로우 화풍 강제 취소」와의 관계: 영지는 새로 뽑으므로 화풍을 여기서 정해야 한다.
>   `aigen.py`가 모든 프롬프트 앞에 `HOLLOW_STYLE`을 강제로 붙이므로, 클래시 수준의
>   **입체감·재질·색**을 내려면 이 강제와 정면으로 부딪친다 — §4-A에 판단을 적었다.

#### 품질 기준 — 「클래시보다 낫다」를 재는 법

"좋아야 함"은 그대로면 판정이 안 된다. 넘겨짚지 않게 **셀 수 있는 것**으로 바꾼다.
클래시 오브 클랜 건물의 관찰 가능한 성질을 기준으로 삼는다:

| 재는 것 | 기준 | 왜 |
|---|---|---|
| 실루엣 식별 | 8동을 **단색 실루엣으로만** 보여줘도 무엇인지 갈린다 | 클래시의 핵심. 축소돼도 읽힌다 |
| 밑동 접지 | 밑동이 `plot` 마름모에 **그림자와 함께** 닿는다 | 떠 보이면 즉시 조악해 보인다 |
| 입체 방향 | 광원이 8동 전부 **같은 방향** | 하나만 어긋나도 붙여넣은 티가 난다 |
| 티어 대비 | `_0` → `_2`가 **실루엣만으로** 성장이 읽힌다 | 업그레이드 보상감의 전부 |
| 해상도 | 화면 표시 크기의 **2배 이상** 원본 | 확대(Zoom 1.55)에서 안 뭉갠다 |
| 흰 종이 잔재 | `leftover_white_pct` < 2% | CLAUDE.md 실측 사고 |

**판정은 스크린샷으로 한다** — 8동을 실제 영지 화면에 올린 한 장과, 같은 프레임의
단색 실루엣 버전을 나란히 뽑아 본다(별이의 `game_image_quality` 확장 슬롯 재사용).
실루엣 버전에서 구분이 안 되면 그 장은 실패다. **오너 확인 없이 「좋다」고 판정하지 않는다.**

- **자리 크기에 맞춰 그린다.** 1×1은 마름모 하나, 2×1·2×2는 그만큼 넓은 밑동.
  캔버스 아래쪽에 **밑동이 닿는 선**을 두고 그 선이 마름모 중심에 오게 한다 —
  §2-1의 앵커가 성립하려면 아트가 이 약속을 지켜야 한다.
- **바닥과 어울리게**: 바닥 타일은 `ground/estate/estate_grass·path·plot`이다.
  건물 밑동이 `plot`(흙 자리) 위에 앉는 그림이어야 경계가 안 튄다.
- **티어**: `estate_<이름>_0/_1/_2`. `_0` 접미사는 이미 티어를 염두에 둔 이름이다.
  레벨 구간(예: 1–4 / 5–9 / 10–13)마다 그림이 바뀐다.
- **공사판**: `estate_scaffold_0` 한 장을 공용으로 쓰고 건물 위에 겹친다.
  건물마다 공사판을 따로 그리면 8×3장이 더 든다 — 값에 비해 효과가 작다.
- **반입 확인은 §5 절차 그대로**: `game_asset_names.py`로 누락·낡음·미사용·meta 대조 →
  `read_console` 경고 0 → Play 스크린샷 육안.

## 3. 구현 순서 (마디마다 커밋 + 스크린샷)

| # | 무엇 | 통과 기준 |
|---|---|---|
| 1 | **폴백 계측**(§1의 미확인 항목) | 전용 그림을 못 찾으면 경고를 찍는다. 8동 전부 전용 사용 확인 — 폴백이면 임포트부터 고친다 |
| 2 | 자리 크기 + 밑동 앵커 | 건물이 제 마름모 중심에 앉고 이웃을 안 넘는다. 스크린샷 육안 + 자리 겹침 0 자가점검 |
| 3 | 팔레트가 내비에 안 가린다 | 1280×720에서 팔레트 아랫변 < 내비 윗변 |
| 4 | 건물별 레벨·업그레이드 창 | 건물을 누르면 창이 뜨고, 시각이 지나면 수령 없이 레벨이 오른다 |
| 5 | 끌어서 옮기기 + 경로 재계산 | 창고를 옮기면 `InvaderSide`가 실제로 바뀐다(네거티브 컨트롤: 안 바뀌면 `StoreX` 상수가 남아 있다) |
| 6 | 아트 8동 + 티어 + 공사판 | 자리 크기대로 그려지고 밑동이 `plot`에 앉는다 |

**1·2·3이 먼저다** — 오너가 「위치가 안 맞는다」고 한 것이 그것이고, 그게 맞지 않으면
새 아트를 아무리 잘 그려도 같은 자리에 어긋나게 놓인다.

---

## 4-A. [오너 판단 필요] 화풍 — 할로우 강제와 클래시 품질은 같이 못 간다

`aigen.py`는 **모든 프롬프트 앞에 `HOLLOW_STYLE`을 붙인다**: 몸은 검정, 얼굴은 빈 눈 가면,
액센트 한 점, **이끼 초록·땅바닥이 있으면 그 장은 버린다**. 지금 영지 8동이 검은 실루엣
덩어리로 보이는 이유가 이것이다.

클래시 오브 클랜 건물의 품질은 정반대 성질에서 나온다 — **재질이 구분되는 색**(나무·돌·금속),
**부드러운 명암과 두꺼운 아웃라인**, **밝은 지면과 그림자의 대비**. 흑백 실루엣 강제를 유지한
채로는 「클래시보다 낫다」가 성립하지 않는다. 둘 중 하나를 골라야 한다:

| 안 | 내용 | 잃는 것 |
|---|---|---|
| **A. 영지만 예외** (추천) | 영지 건물에 한해 `HOLLOW_STYLE` 대신 「어두운 배경 위 저채도 컬러 + 재질 구분 + 접지 그림자」 규칙을 쓴다. 전투·몹·캐릭터는 그대로 | 영지와 전투 화면의 화풍이 조금 갈린다 |
| B. 할로우 유지 | 흑백 실루엣 안에서 명암만 올린다 | 클래시 대비 우위를 주장할 수 없다 — 오너 지시를 못 지킨다 |
| C. 전체 전환 | 게임 전체를 클래시 계열로 | 이미 만든 캐릭터·몹 수십 장 재작업. 이번 범위를 한참 넘는다 |

**A를 추천한다.** 영지는 전투와 화면이 완전히 분리돼 있어 화풍이 조금 달라도 충돌하지 않고,
클래시·쿠키런 킹덤도 마을과 전투의 톤이 다르다. 다만 **배경(`bg_estate`)과 바닥 타일이
이미 어두우므로** 저채도를 유지해 붕 뜨지 않게 한다.

**이건 오너가 정할 일이다** — 화풍은 되돌리기 비싸고, CLAUDE.md §5가 명시한 규칙을
내가 임의로 깰 사안이 아니다.

## 4. 안 하는 것 (YAGNI)

- **일꾼(건설 대기열) 없음.** 동시 건설 제한은 재화 소비처를 하나 더 만들지만
  이번 범위에서 검증할 게 이미 6마디다. 필요하면 나중에 연다.
- **빈 칸에 새 건물 신축 없음.** 8동은 이미 다 서 있다. 「건설」은 **업그레이드와 이동**으로
  구현하고, 신축은 방어 건물(성벽·탑·함정)의 기존 팔레트가 이미 담당한다.
- **건물별 시간·비용 계수 분화 없음.** §18 앵커 유도가 필요한 밸런스 사안이다.
