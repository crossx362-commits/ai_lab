# 재와 별 자율 개발 루프 연속성 설계

작성일: 2026-08-27  
상태: 오너 대화 설계 승인, 구현 전 문서 검토

## 1. 목적

오너가 어느 AI 대화에서든 "자율 개발 루프를 시작하라"고 지시하면 같은 단일 시작 절차를
즉시 실행한다. 시작된 루프는 오너가 명시적으로 중단하기 전까지 영구 종료하지 않는다.

루프가 진행하지 못하는 경우에는 원인을 다음 두 종류로만 나눠 처리한다.

- 사용량 한도: 선택된 AI의 사용량이 회복될 때까지 종료하지 않고 대기·재확인한다.
- 오류: 오류 원인을 먼저 진단·수정·검증한 뒤 원래 개발 작업으로 복귀한다.

정상 작업 실패, AI 오류, 사용량 한도 때문에 루프가 스스로 `STOP`을 만들거나 성공 종료하는
동작은 제거한다. `STOP`은 오너의 명시적 중단 신호로만 쓴다.

## 2. 확인된 근본 원인

2026-08-27 실측에서 다음이 확인됐다.

1. `loop/env.sh`의 실행기 체인이 `claude` 하나로 고정되어 다른 실행 경로가 사실상 막혔다.
2. Claude가 반환한 "organization has disabled subscription access"는 사용량 한도와 서버 장애
   어느 쪽에도 분류되지 않아 일반 실패로 누적됐다.
3. `STATUS.md` 미갱신 3회가 작업 오류가 아니라 AI 실행 불능 때문에 발생했는데도 루프가
   exit 0으로 종료됐다.
4. launchd는 저장소 파일이 아니라 `Application Support`에 복사된 별도 실행본을 사용했다.
   저장소 `loop.sh`·`env.sh`와 실제 실행본의 체크섬이 달라 수정과 실행이 분리됐다.
5. 재시작 절차가 `STOP` 제거와 배포·등록·실행 확인으로 나뉘어 있어, 실행 주체가 절차 일부를
   빠뜨리면 시작 명령이 성공한 것처럼 보여도 루프는 즉시 종료될 수 있다.
6. 현 감시자는 사용량 대기·복구 작업을 별도 상태로 알지 못하고 최근 lap 로그의 시각만으로
   정체를 판단한다.

## 3. 운영 상태 모델

런타임 상태는 git에서 제외되는 단일 상태 파일에 기록한다. 최소 상태는 다음 네 가지다.

- `running`: 정상 개발 바퀴 실행 중
- `quota_wait`: 선택된 AI의 사용량 회복 대기 중
- `recovering`: 마지막 오류의 원인 진단·수정·검증 중
- `owner_stopped`: 오너가 명시적으로 중단함

상태 파일에는 현재 AI, 마지막 정상 활동 시각, 마지막 오류 분류, 다음 재확인 시각만 둔다.
개발 진척·기획 판단은 계속 `docs/STATUS.md`와 기존 문서가 담당한다. 런타임 상태를 개발 문서에
복제하지 않는다.

각 대기 구간에서도 heartbeat를 갱신한다. 감시자는 lap 로그 시각 대신 상태와 heartbeat를 함께
판정하여 `quota_wait`를 정체로 오인하지 않는다.

## 4. 단일 시작·중단 경로

모든 대화형 AI와 보드가 같은 제어 명령을 사용한다.

### 시작

`start`는 멱등적으로 다음을 한 번에 수행한다.

1. 저장소의 `STOP`과 `HOLD`를 해제한다.
2. 오너가 AI를 지정했으면 그 값을 현재 실행기로 기록하고, 지정하지 않았으면 직전 설정을 쓴다.
3. launchd 등록본이 저장소의 `loop/loop.sh`를 직접 실행하도록 등록한다.
4. 이미 실행 중이면 중복 프로세스를 만들지 않고 현재 PID를 확인한다.
5. 멈춰 있으면 서비스를 시작하고 실제 프로세스 또는 첫 heartbeat가 나타나는지 확인한다.
6. 확인 실패는 성공으로 보고하지 않고 즉시 `recovering`으로 전환한다.

`Application Support`에 실행 스크립트 사본을 배포하는 구조는 메인 루프에서 제거한다. launchd가
저장소 원본을 직접 실행하게 하여 저장소와 실제 실행본의 불일치 자체를 없앤다.

### 중단

오너의 명시적 `stop`만 `STOP`을 만든다. 루프·감시자·오류 처리기는 `STOP`을 생성하지 않는다.
현재 바퀴를 마친 뒤 `owner_stopped`로 정상 종료하며, 감시자는 이 상태를 존중한다.

## 5. 사용량 한도 처리

사용량 한도는 공식 사용량 조회 결과와 실제 CLI의 명시적 한도 응답으로 판정한다. 인증 실패,
실행 파일 부재, 서버 오류, 코드 오류를 사용량 한도로 뭉뚱그리지 않는다.

한도 판정 시:

1. 상태를 `quota_wait`로 기록한다.
2. 루프 프로세스를 끝내거나 `STOP`을 만들지 않는다.
3. 제공되는 초기화 시각이 있으면 그 시각까지 대기한다.
4. 초기화 시각을 알 수 없으면 짧은 고정 간격으로 사용량만 재확인한다.
5. 대기 중 heartbeat를 갱신한다.
6. 사용 가능 판정 즉시 같은 AI로 원래 개발 작업을 계속한다.

일반 개발 AI를 임의로 교체하는 자동 회전은 기본 동작으로 두지 않는다. 오너가 선택한 AI의
사용량이 소진되면 그 AI의 회복을 기다린다는 지시를 따른다.

## 6. 오류 복구

한도가 아닌 비정상 종료는 실패 횟수를 세어 루프를 죽이는 대신 `recovering`으로 전환한다.

1. 마지막 명령, 종료 코드, 로그 끝부분, 실행 설정을 복구 입력으로 고정한다.
2. 오류가 설정·배포·루프 코드 문제인지, AI 실행기 자체 문제인지 구분한다.
3. 현재 AI가 실행 가능하면 같은 AI가 원인을 수정한다.
4. 현재 AI 자체가 실행 불가능한 경우에만 설치된 다른 AI 하나를 복구 실행기로 사용한다.
5. 복구 실행기는 오류와 직접 관련된 파일만 수정하고 해당 재현 테스트를 통과시킨다.
6. 루프 본체가 바뀌었으면 launchd가 새 원본을 다시 읽도록 재기동한다.
7. 정상 heartbeat를 확인한 뒤 상태를 `running`으로 바꾸고 원래 개발 작업을 재개한다.

복구에 실패해도 `STOP` 또는 성공 종료로 빠지지 않는다. 오류와 다음 재시도 시각을 남기고 계속
복구를 재시도한다. 사람에게 알리는 조건은 권한·로그인처럼 코드로 해결할 수 없는 상태가 실제로
확인된 경우뿐이며, 기존 예원 검수 경로를 따른다.

## 7. 감시자 역할

감시자는 재시작을 반복하는 별도 안전장치가 아니라 상태 머신의 외부 실행자다.

- `running`인데 heartbeat가 끊겼으면 비정상 종료로 보고 `recovering`을 시작한다.
- `quota_wait`이고 heartbeat가 살아 있으면 건드리지 않는다.
- `recovering`이면 중복 복구 세션을 만들지 않는다.
- `owner_stopped` 또는 `STOP`이면 아무것도 시작하지 않는다.
- 서비스 등록이 사라졌으면 저장소 원본을 가리키도록 다시 등록한 뒤 상태에 맞게 계속한다.

## 8. 변경 범위

예상 변경 대상은 다음으로 제한한다.

- `loop/loop.sh`: 영구 종료 분기 제거, 한도 대기와 오류 복구 상태 전환
- `loop/env.sh`: 충돌하는 실행기 기본값 정리, 재확인 간격 설정
- `loop/loop_watch.sh`: 상태·heartbeat 기반 감시와 복구 실행
- `loop/deploy_launchd.sh`: 단일 멱등 시작 경로, 저장소 원본 직접 실행
- `loop/com.ailab.autonomous_loop.plist`: 저장소 원본 실행 및 비정상 종료 재기동
- `loop/board.py`: 보드 재개도 동일 시작 경로 사용
- `loop/README.md`: 실제 시작·중단 명령과 상태 의미
- `loop/test_*.sh` 또는 `loop/test_*.py`: 아래 회귀 시나리오

현재 작업 트리에 이미 존재하는 다른 세션의 변경은 보존한다. 수정 전 메인 루프와 속도 레인을
정상 중단하고, 대상 파일의 기존 diff를 기준으로 좁은 패치만 적용한다.

## 9. 검증 기준

구현은 다음 네거티브 컨트롤을 모두 통과해야 한다.

1. `STOP`과 `HOLD`가 있는 상태에서 `start` 한 번으로 둘이 해제되고 루프가 실제 실행된다.
2. 동일한 `start`를 두 번 호출해도 메인 루프 프로세스는 하나뿐이다.
3. AI가 사용량 한도 응답을 반환하면 다른 AI로 개발 작업을 넘기거나 종료하지 않고
   `quota_wait`에 머물다가 회복 후 같은 AI로 진행한다.
4. Claude 구독 접근 차단 응답은 한도로 오인하지 않고 `recovering`으로 분류된다.
5. 일반 오류가 연속 세 번 발생해도 `STOP`이 생기거나 exit 0으로 영구 종료되지 않는다.
6. 복구가 성공하면 새 heartbeat와 다음 정상 lap이 생성된다.
7. `quota_wait`가 90분을 넘겨도 감시자가 정상 대기를 강제 재시작하지 않는다.
8. launchd가 참조하는 `loop.sh` 경로가 저장소 원본과 같아 별도 사본 불일치가 없다.
9. 기존 loop 단위 테스트와 `python3 projects/ai-team/harness/check_all.py`가 모두 통과한다.
10. 실제 launchd 등록 후 PID·상태·heartbeat를 확인하고, 테스트용 한 바퀴가 정상 종료되는 것을
    확인한 다음 무한 루프를 재개한다.

## 10. 비목표

- 정상 개발 작업마다 AI를 자동 교체하는 스케줄러를 새로 만들지 않는다.
- 새로운 승인 게이트를 만들지 않는다.
- 게임 개발 우선순위나 아트 생성 규칙을 바꾸지 않는다.
- 오너가 의도적으로 만든 `STOP`을 감시자가 무시하지 않는다.
- 자격증명·조직 정책처럼 코드로 바꿀 권한이 없는 외부 상태를 임의로 수정하지 않는다.
