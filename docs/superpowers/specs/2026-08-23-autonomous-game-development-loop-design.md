# 재와별 자율 병렬 게임 개발 루프 설계

- 상태: 구현 승인 전 최종 설계안
- 작성일: 2026-08-23
- 대상 저장소: `ai_lab`
- 자동 통합 대상: `autonomous/integration`
- 보호 대상: `master` 및 사용자가 작업 중인 모든 기존 워크트리

## 1. 목적과 합격 기준

이 시스템은 Claude, Codex, Grok이 매 바퀴 새 헤드리스 세션으로 게임을 개발하되, 한 명만 일하거나 최대 세 명이 독립 작업을 병렬 수행할 수 있게 한다. 대화 기억은 사용하지 않고 저장소의 문서, 작업 명세, Git 커밋, 실행 로그만 기억으로 사용한다.

합격은 단순히 코드가 생성됐거나 테스트가 한 번 통과했다는 뜻이 아니다. 다음 조건을 모두 만족해야 한다.

1. 빌드·정적 검사·관련 회귀 테스트가 통과한다.
2. 실제 게임을 실행해 기능과 화면을 확인한 증거가 남는다.
3. 다른 제공자의 최상급 모델이 정확한 커밋을 독립 검토한다.
4. 게임성, 조작성, 시각 완성도, 경쟁 제품 대비 품질이 작업 목표에 맞는다.
5. 이미지와 스프라이트는 실제 게임 안에서 크기, 중심, 프레임 간격, 잔여 흰색, 애니메이션 흔들림을 확인한다.
6. 승인한 커밋과 통합한 커밋이 동일하거나, 통합 과정에서 SHA가 달라졌다면 새 결과를 다시 검사·검토한다.
7. `master`와 다른 AI의 작업물을 자동으로 덮어쓰거나 오염시키지 않는다.

## 2. 지침 권위와 읽기 순서

### 2.1 권위 순서

충돌 시 다음 순서로 판단한다.

1. 현재 사용자의 직접 지시
2. 루트 `DIRECTIVES.md`와 `AGENTS.md`
3. 대상 경로의 가장 가까운 `CLAUDE.md`
4. `docs/feedback/INBOX.md`
5. `docs/STATUS.md` 및 게임 작업 문서
6. 해당 작업 명세와 코드의 현재 동작

오래된 문서의 “단일 세션만 사용”, “Grok Imagine 금지”, “Windows 운영”, “에이전트 8명”, “게임 개발에 로컬·미니 모델 사용” 규칙은 최신 직접 지시와 현재 상위 지침에 맞게 좁게 갱신한다. 사고 이력과 금지 이유는 삭제하지 않고 현재 규칙과 구분해 보존한다.

### 2.2 매 바퀴 읽기 순서

코디네이터와 작업자는 다음 순서로 필요한 범위만 읽는다.

1. 안전 부트스트랩: `DIRECTIVES.md`, `AGENTS.md`, 대상 경로의 `CLAUDE.md`
2. 사용자 우선 지시: 루트 작업공간의 `docs/feedback/INBOX.md` 원자 스냅샷
3. 진행 상태: `autonomous/integration` 정확한 SHA의 `docs/STATUS.md`
4. 게임별 작업 기록과 명령서: `GAME_WORKLOG.md`, `ORDERS.md`가 있으면 읽기
5. 안정 기획: `docs/DESIGN.md`와 대상 기능 명세
6. 해당 작업에 필요한 코드·테스트·에셋만 읽기

문서 전체를 매번 프롬프트에 복사하지 않는다. 경로와 읽기 순서를 주고, 작업 명세에는 관련 파일과 증거만 넣는다.

INBOX와 사용자가 채우는 DESIGN은 루트 작업공간 파일을 해시 전·후가 같은 안정 스냅샷으로 읽는다. 읽는 중 바뀌면 다시 스냅샷한다. STATUS와 통합된 작업 기록은 루트 파일이 아니라 바퀴 시작 때 고정한 `autonomous/integration` SHA에서 `git show` 또는 detached snapshot으로 읽는다. 이 두 원천과 해시를 계획자·작업자·검토자에게 명시적으로 전달한다.

따라서 루트 `docs/STATUS.md`는 초기 틀이며 자동 루프가 직접 수정하지 않는다. 최신 상태는 통합 브랜치의 같은 경로와 보드용 읽기 전용 미러에서 보여준다. README는 이 차이와 최신 STATUS를 보는 방법을 명시한다. 이 방식으로 사용자의 미커밋 INBOX를 놓치지 않으면서 자동화가 사용자 작업공간을 더럽히지 않는다.

## 3. 전체 구조

### 3.1 구성 요소

- `loop/loop.sh`: 무한 반복, STOP 처리, 바퀴 수·대기 시간 관리, 한 바퀴 코디네이터 호출
- `loop/env.sh`: 모델, 최대 턴, 동시 작업 수, 대기, 최대 바퀴, 재시도와 회로 차단기 설정
- `loop/PROMPT.md`: 모든 새 세션이 읽는 공통 5절 지침
- `projects/ai-team/scripts/autonomous_game_loop.py`: 결정론적 코디네이터와 상태 기계
- `projects/ai-team/tests/test_autonomous_game_loop.py`: 스케줄링, Git 보호, 상태, 로그, 중단 회귀 테스트
- `docs/DESIGN.md`: 거의 바뀌지 않는 제품 기획
- `docs/STATUS.md`: 코디네이터만 갱신하는 통합 진행 상태
- `docs/feedback/INBOX.md`: 사용자가 넣는 최우선 지시. 자동 삭제하지 않는다.
- `logs/YYYY-MM-DD/<run-id>/`: 날짜별 바퀴·제공자·검토·검사 로그
- `output/cache/autonomous_loop/`: 락, 하트비트, 작업 명세, 승인 기록, 상태 스냅샷 같은 런타임 데이터

형식적인 시스템 코드는 저장소 배치 정책에 따라 `projects/ai-team/scripts/`에 둔다. `loop.sh`는 사용자 요구를 만족하는 안정된 진입점이자 얇은 실행 래퍼로 유지한다. `_shared/`는 수정하지 않는 것을 기본으로 하며, 불가피하게 수정하면 전체 회귀 검사를 수행한다.

사용자가 보는 저장소 루트는 런처가 문서를 읽는 곳일 뿐 Git 쓰기 작업공간으로 사용하지 않는다. STATUS 작성, 병합 결과 생성, 검증 커밋은 코디네이터가 만든 전용 detached 검증 작업공간에서만 수행한다. 작업자 프로세스는 코디네이터의 상태·로그·공용 `.git`에 쓰지 못하고, 표준 출력과 종료 코드만 부모 프로세스가 받아 로그로 저장한다.

코디네이터는 자유 형식 INBOX에서 작업을 뽑아야 할 때만 최상급 모델의 새 계획 세션을 한 번 호출해 최대 세 개의 작업 명세 후보를 받는다. 이미 검증 가능한 구조화 작업 명세가 있으면 별도 계획 호출을 생략하고 작업 세션으로 바로 간다. 처리할 지시가 없는 확인은 `idle poll`로 기록하며 바퀴 수에 포함하지 않는다. 실제로 카운트되는 모든 바퀴는 최소 한 개의 새 비지속 헤드리스 세션이 `loop/PROMPT.md`를 직접 읽는다. 계획 결과는 제안일 뿐이며, 필수 필드·경로·공유 자원·중복 여부는 코디네이터가 검사한 뒤에만 실행한다.

### 3.2 한 바퀴의 의미

한 바퀴는 아래 과정을 한 번 수행한 것이다.

1. 새 실행 ID와 문서 스냅샷을 만든다.
2. INBOX와 STATUS를 토대로 독립 가능한 작업을 고른다.
3. 한 작업이면 최적 작업자 한 명만 배정한다.
4. 독립 작업이 여러 개면 최대 세 제공자에게 하나씩 배정한다.
5. 각 작업자는 새 세션·새 브랜치·새 격리 복제본에서 하나의 결과만 만든다.
6. 각 결과를 다른 제공자의 새 세션이 검토한다.
7. 통과 결과만 `autonomous/integration` 최신 커밋 위에서 재검사하고 원자적으로 통합한다.
8. 코디네이터가 STATUS와 바퀴 요약을 갱신하고 커밋한다.

“한 바퀴에 하나만 만들기”는 작업자 기준이다. 한 작업자가 여러 기능을 섞지 않는다. 코디네이터는 서로 독립임이 결정론적으로 입증된 작업에 한해 한 바퀴에 최대 세 개를 병렬 처리할 수 있다.

## 4. 역할과 모델 정책

### 4.1 조직 역할과 모델 제공자를 분리

작업 명세에는 책임 역할과 실행 모델을 별도 필드로 기록한다.

- 책임 역할: 예원(정책·통합), 영숙(게이트웨이), 봄이(QA), 수리(구현), 테오(테스트), 백호(백엔드·밸런스), 미오(디자인), 나무(PM), 마루(게임 실행·성능), 별이(이미지 품질)
- 실행 제공자: Claude, Codex, Grok
- 기록 필드: `role`, `provider`, `requested_model`, `effective_model`, `selection_reason`

기본 파이프라인은 `증거 수집 → 분류·우선순위 → 작업 명세 → 격리 구현 → 독립 검증 → 통합 결정 → 재발 방지·인계`다. 기존 감사 에이전트는 읽기 전용 책임을 유지하고, 쓰기 작업은 별도의 구현 단계에서 수행한다.

중복을 막기 위한 역할 경계는 다음과 같다. 나무는 우선순위와 제품 목표, 봄이는 재현 가능한 기능 결함, 미오는 화면·UX, 마루는 Unity 실행·성능·게임성, 별이는 픽셀·스프라이트, 백호는 계약·밸런스 근거를 맡는다. 수리는 기능 수정에 필요한 최소 회귀 테스트까지 구현하고, 테오는 독립 핵심 흐름 E2E와 음성 대조를 소유한다. 예원 책임 단계만 최종 통합을 승인하며, 어떤 역할도 승인된 쓰기 범위를 스스로 넓히지 않는다.

### 4.2 품질 우선 모델

- Claude 작업자: `fable`을 기본 사용한다. 현재 CLI 계약은 `claude -p '<bootstrap>' --model fable --fallback-model opus5 --no-session-persistence --permission-mode acceptEdits --output-format stream-json --verbose`이고 resume/continue와 권한 우회 인자를 거부한다. 현재 CLI에 `--max-turns`가 없으므로 어댑터가 스트림 이벤트를 세고 설정된 최대 턴 또는 deadline에서 프로세스 그룹을 종료한다.
- Claude 대체: Fable 사용량 소진, 과부하 또는 사용 불가일 때만 `opus5`를 사용한다. 허용된 대체 사유와 실제 모델을 기계 판독 가능한 실행 메타데이터로 기록한다. 다른 하위 모델이 관찰되거나 실제 모델을 확인할 수 없으면 실패한다.
- Codex 작업자: 짧은 bootstrap을 stdin으로 주는 `codex exec --ephemeral --model gpt-5.6-sol --sandbox workspace-write --approve-for-me --json -c 'model_reasoning_effort="xhigh"' -`를 기본 계약으로 한다. 최고 난도·고위험 작업만 작업 명세에 근거를 남기고 `max`를 허용하며, resume와 danger-full-access·권한 우회 실행을 거부한다. 최대 턴은 JSON 이벤트와 deadline으로 외부 강제한다.
- Grok 작업자: 현재 설치된 CLI의 최상급 확인 모델은 `grok-4.6`이다. `grok --model grok-4.6 --no-memory --no-subagents --max-turns <N> --permission-mode auto --output-format streaming-json -p '<bootstrap>'` 계약으로 pin하고 resume/continue·bypassPermissions를 거부한다. `-p`의 필수 prompt 인자를 생략하지 않는다. 매 실행 전 모델 목록과 인증을 다시 점검하며 더 강한 모델로 바꾸는 것은 설정 변경과 검증을 거친다. 인증 또는 모델을 확인할 수 없으면 그 바퀴에서 Grok을 제외한다.
- 게임 코드, 설계, 밸런스, UX, 에셋 판정, 최종 검토에는 Ollama, Haiku, Luna 같은 소형·저가 모델을 사용하지 않는다.

Ollama는 기본값 `off`다. 켜더라도 원본을 보존할 수 있는 로그 정형화, 커밋 메시지 초안처럼 판단이 필요 없는 사무 작업에만 쓰며, 결과가 품질 승인이나 작업 분배에 영향을 주지 못한다.

`<bootstrap>`은 “격리 복제본의 `loop/PROMPT.md`를 먼저 읽고 지정된 manifest 한 건만 수행하라”는 짧은 한 줄과 검증된 상대경로만 담는다. 긴 지침을 argv에 복사하지 않는다. 모든 명령은 셸 문자열이 아니라 인자 배열로 실행해 경로·프롬프트 삽입을 막는다.

### 4.3 배정과 교차 검토

- 단일 작업: 가장 적합한 최상급 제공자 1명이 구현하고, 다른 제공자 1명이 검토한다. 세 번째는 호출하지 않는다.
- 다중 작업: 쓰기 범위와 공유 자원 태그가 겹치지 않는 작업만 최대 3개 병렬 실행한다.
- 자기 검토 금지: 구현 제공자와 승인 제공자는 반드시 다르다.
- 검토 세션 재사용 금지: 구현 대화를 이어받지 않은 새 헤드리스 세션이어야 한다.
- Claude는 세션 비저장, Codex는 ephemeral, Grok은 재개 ID를 전달하지 않는 어댑터를 사용한다. 어떤 제공자도 resume/continue 옵션을 쓸 수 없다.
- 한 검토 세션이 여러 후보를 다룰 수는 있지만 각 승인은 `base_sha`, `source_candidate_sha`, `integration_candidate_sha`, 검사 결과, 증거 해시에 개별 결합한다.
- 서로 다른 최상급 제공자가 둘 미만이면 후보는 보존하되 자동 통합하지 않는다.

## 5. 작업 명세와 충돌 방지

### 5.1 필수 작업 명세

각 작업은 실행 전에 JSON 명세로 고정한다.

- `task_id`, 목표, 합격 조건, 우선순위
- 재현·측정 절차와 현재 증거
- 책임 역할, 작업 제공자·모델, 검토 제공자·모델
- `base_sha`, 후보 브랜치, 격리 작업공간 경로
- 허용 쓰기 경로 목록 `write_set`
- 씬, 프리팹, 아틀라스, 세이브 스키마, 공용 UI 같은 `shared_resource_tags`
- 실행할 테스트와 시각 확인 계획
- 금지 경로와 사용자 작업 보호 조건

작업자는 허용된 쓰기 경로 밖을 수정하면 자동 실패한다. 범위 확대가 필요하면 현재 작업을 멈추고 새 명세를 받아야 한다.

### 5.2 결정론적 독립성 판정

LLM의 “안 겹친다”는 말만으로 병렬 실행하지 않는다. 코디네이터가 다음을 검사한다.

1. 정규화한 `write_set` 경로가 서로 겹치지 않는다.
2. 부모·자식 경로 관계도 겹침으로 처리한다.
3. `shared_resource_tags`가 하나라도 같으면 병렬 실행하지 않는다.
4. Unity 씬·프리팹·ProjectSettings·공용 아틀라스·세이브 스키마는 보수적으로 공유 자원으로 취급한다.
5. 불명확한 범위는 직렬 실행한다.

충돌 판정과 병합은 코드가 수행한다. 모델은 작업 제안과 의미 검토만 담당한다.

경로는 저장소 상대 literal 경로만 허용한다. `.`·`..`, 절대경로, Git pathspec magic, `.git`, submodule 경계, 저장소 밖을 가리키는 symlink를 거부한다. macOS 파일 시스템을 고려해 Unicode NFC/NFD와 대소문자 접기를 모두 비교한다. 실행 후에는 `git diff --name-status -z`의 rename 전·후 경로까지 실제 `write_set`과 대조한다.

### 5.3 작업자 격리, 검증 워크트리와 브랜치

- 작업 후보: `autonomous/<run-id>/<task-id>/<provider>`
- 자동 통합: `autonomous/integration`
- 중앙 임시 ref: `refs/autonomous-loop/<run-id>/<task-id>/<attempt-id>`
- 작업자 복제본: `.worktrees/autonomous/<run-id>/<task-id>/<provider>` 안의 독립 `.git` 복제본
- 검증 워크트리: `.worktrees/autonomous/<run-id>/verify/<task-id>`

모든 후보는 실행 시점의 `autonomous/integration` SHA에서 시작한다. 작업자 복제본은 `--no-local` 방식으로 공용 `.git`과 객체·ref 쓰기를 공유하지 않고, 원격 push 대상도 제거한다. 작업자는 복제본 안에서만 후보 브랜치를 커밋하며, 코디네이터가 검증 후 해당 객체를 `refs/autonomous-loop/*`의 실행 manifest 등록 ref로만 가져온다. `master`, 현재 사용자의 브랜치, 이미 존재하는 다른 AI 워크트리는 읽기만 가능하고 갱신하지 않는다. 대상 브랜치가 `autonomous/integration`이 아니면 자동 통합 함수가 즉시 실패하는 하드 가드를 둔다.

계획자·작업자·검토자 CLI는 macOS OS 수준 쓰기 샌드박스에서 실행한다. 쓰기 허용 대상은 해당 독립 복제본, 해당 세션의 임시 HOME·임시 디렉터리뿐이다. 저장소 루트, 공용 `.git`, 다른 워크트리, 코디네이터 상태·로그는 읽기 또는 접근 불가다. 위험한 sandbox/approval 우회 옵션은 사용하지 않는다. symlink의 실제 목적지도 허용 경계 안이어야 한다. OS 샌드박스를 적용할 수 없거나 보호 경로 쓰기 음성 대조가 성공하면 해당 제공자는 실패 폐쇄 방식으로 제외한다.

코디네이터는 실행 전후 보호 불변식을 비교한다. 소유 ref는 정확히 `refs/heads/autonomous/integration`과 실행 manifest에 등록된 `refs/autonomous-loop/*`만이다. 이 ref와 공용 Git 설정·hooks, 샌드박스 canary, 코디네이터 상태의 예상 밖 변경은 통합을 중단한다. `autonomous/member-style`처럼 다른 작업자가 만든 `refs/heads/autonomous/*`는 소유 범위가 아니다. `master` 이동은 다른 AI의 정상 변경일 수 있으므로 기준 변경으로 분류해 동기화·재검사 경로로 보낸다. 타 소유 ref와 기존 워크트리의 변화는 감사 로그에만 남기고 실패 사유로 삼지 않는다. 이 비교는 샌드박스의 대체가 아니라 추가 탐지 장치다.

최초 설치 시 `autonomous/integration`이 없으면 설치 시작 때 기록한 깨끗한 커밋 `bootstrap_sha`를 가리키게 한 번만 만든다. 작업 디렉터리의 미커밋 변경은 포함하지 않는다. 이미 브랜치가 있으면 임의로 되감거나 `master`에 맞추지 않는다. 이 브랜치는 상시 워크트리에 체크아웃하지 않고 Git 참조로만 유지해, 승인 후 기대 SHA 비교 갱신이 파일 시스템과 어긋나지 않게 한다.

최초 생성은 zero OID를 기대값으로 둔 ref 비교 갱신으로 경쟁을 막는다. 매 통합 직전에도 이 브랜치가 어떤 워크트리에도 체크아웃되지 않았음을 검사한다. 검증 워크트리는 detached HEAD와 실행별 임시 ref만 사용한다.

`master`의 커밋된 끝이 움직여 통합 브랜치가 낡았으면 코디네이터는 이를 읽기 전용 소스로 삼아 별도 동기화 시도를 만든다. 현재 통합 위에 새 `master`를 병합하고 전체 검사·독립 검토를 거친 정확한 결과만 같은 CAS 절차로 통합한다. 충돌은 즉시 중단하고 자동 해결하지 않는다. 이 절차도 `master` 자체를 이동시키거나 더러운 작업 내용을 읽어 들이지 않는다.

## 6. 상태 기계와 원자성

작업 시도는 다음 단방향 상태 기계로 관리한다.

`PLANNED → CLAIMED → RUNNING → CANDIDATE → CANDIDATE_VALIDATED → MERGE_PREPARED → MERGE_VALIDATED → COMMITTING → MERGED`

실패 경로는 `FAILED`, 임대 만료는 `EXPIRED`다. 재시도는 상태를 거꾸로 돌리지 않고 같은 `task_id`에 새 `attempt_id`를 만든다. 상태 파일은 임시 파일 작성 후 원자적 교체로 저장하고, 전이할 때 이전 상태, 시도 ID, 세대 fencing token을 함께 검사한다. 완료된 전이는 재실행해도 같은 결과가 나오는 멱등성을 가져야 한다.

코디네이터는 저장소당 하나만 실행된다. 프로세스 수명 동안 유지하는 `fcntl.flock` 또는 동등한 원자 락을 먼저 획득하고, 메타데이터는 별도 설명 파일에 기록한다. 메타데이터에는 임의 소유자 토큰, PID, 시작 시각, 하트비트, 세대 번호가 들어간다. PID만 보고 오래된 락을 빼앗지 않는다. 락 해제, 프로세스 부재, 하트비트 만료를 확인해 새 세대가 시작되며, 세대 fencing token이 다른 작업·승인·CAS는 거부한다.

작업 클레임은 임대 시간과 하트비트를 가진다. 세션이 죽으면 후보 복제본과 검증 작업공간은 증거로 보존하고, 코디네이터가 임의로 `reset --hard`하거나 사용자 파일을 삭제하지 않는다.

통합 직전에는 write-ahead intent에 `run_id`, `task_id`, `attempt_id`, fencing token, `expected_old_sha`, `game_result_sha`, `status_commit_sha`, 최종 `integration_candidate_sha`를 기록하고 동기화한다. 그 뒤에만 ref CAS를 수행한다. 크래시 복구 시 integration ref가 old SHA면 CAS를 멱등 재시도한다. 현재 integration이 `integration_candidate_sha`와 같거나 그 SHA를 조상으로 포함하고 작업·시도 ID가 확인되면 이미 `MERGED`된 것으로 확정한다. 둘 다 아니면 해당 시도를 `EXPIRED`로 닫고 새 기준에서 다시 만든다. 병합 커밋 메시지에도 작업·시도 ID를 넣어 중복 통합을 식별한다.

## 7. 구현·검사·커밋·통합 순서

사용자 지시의 “검사를 통과하면 화면을 보기 전에 일단 커밋”과 “읽기 → 만들기 → 실행해 눈으로 확인 → 커밋 → STATUS 갱신”을 모두 지키기 위해 커밋을 두 단계 체크포인트로 정의한다.

1. 읽기: 지침과 작업 명세를 읽고 `base_sha`를 확인한다.
2. 하나만 만들기: 허용 범위 안에서 한 작업만 구현한다.
3. 자동 검사: 빌드·관련 테스트·에셋 검사를 수행한다.
4. 체크포인트 커밋: 자동 검사가 통과하면 정확한 파일만 `git add <명시 파일>` 후 즉시 커밋한다.
5. 실제 실행·눈 확인: 체크포인트 커밋으로 게임을 실행하고 화면·조작·성능을 확인한다.
6. 보정: 시각 검증이 실패하면 같은 범위 안에서 수정, 자동 검사, 새 커밋, 시각 검증을 반복한다.
7. 통합 후보 생성: 최신 통합 SHA에서 검증 브랜치를 만들고 후보를 병합한다. 충돌 시 즉시 `merge --abort`하고 자동 해결하지 않는다.
8. 통합 결과 재검사: 병합 결과에 자동 테스트와 필요한 게임 실행·시각 검사를 다시 수행한다.
9. STATUS 체크포인트: 코디네이터가 검증 브랜치의 STATUS에 결과, 증거, 다음 작업을 기록하고 허용 문서만 별도 커밋한다. 자기 SHA는 기록하지 않고 실행 ID, 소스 후보 SHA, 게임 결과 SHA를 기록한다.
10. 독립 검토: 구현자와 다른 제공자의 새 세션이 STATUS 커밋까지 포함한 최종 `integration_candidate_sha`, 원본 캡처, 검사 증거를 검토한다.
11. 원자적 통합: `git merge-base --is-ancestor <source_candidate_sha> <integration_candidate_sha>`와 기대 기준 SHA를 확인하고, 승인된 정확한 SHA로만 `autonomous/integration` 참조를 CAS 갱신한다.

검토 중 통합 기준 SHA가 움직이면 기존 승인은 만료된다. 새 기준 위에서 병합 결과와 STATUS 체크포인트를 만들고 다시 검사·검토한다. 따라서 자동 통합 후 브랜치 끝은 검토자가 승인한 SHA와 정확히 같다. 한 바퀴가 어디서 중단돼도 작업자 복제본에 미커밋 변경을 남겨 성공으로 취급하지 않는다.

## 8. 게임·이미지 품질 검증

### 8.1 Unity 안전

- 오너가 연 Unity 프로세스를 강제 종료하지 않는다.
- Unity 배치 측정은 저장소의 `unity_meas` 관례를 따른다.
- 빌드 성공만으로 화면 합격을 선언하지 않는다.
- 새 E2E 검사는 연속 두 번 통과해야 하며, 검사가 실제 결함을 잡는지 음성 대조도 둔다.
- 콘솔 경고·오류, 플레이 화면, 입력 반응, FPS·렌더링 이상을 증거로 남긴다.

### 8.2 이미지와 스프라이트

- 새 그림 생성은 Higgsfield 또는 Grok Imagine만 사용한다.
- 생성 전 capability·인증·사용 가능 모델을 점검한다. 두 수단이 모두 불가하면 다른 생성기로 조용히 바꾸지 않고 인프라 보류로 남긴다.
- 생성 제공자, 실제 모델, 프롬프트 해시, seed 또는 재현 식별자, 생성 시각, 출처·라이선스 메타데이터를 기록한다.
- 생성 파일 존재가 아니라 실제 게임 통합을 확인한다.
- 런타임 에셋은 프로젝트 규칙에 맞는 경로와 소비 코드가 함께 있어야 한다.
- PNG와 `.meta` 쌍, 이름 검사, 미사용·낡은 에셋, 콘솔 경고를 검사한다.
- 스프라이트 시트는 프레임 간격, 중심축, 셀 크기, PPU, 게임 내 실제 크기, 애니메이션 흔들림, 흰색 잔여 비율을 확인한다.
- UI와 VFX는 스크린샷뿐 아니라 플레이 상태의 가독성, 겹침, 대비, 피드백 타이밍을 미오·마루·별이 책임 기준으로 검토한다.

시각 증거는 로그 디렉터리에 경로·해시·캡처 시각과 함께 남긴다. 사람이 볼 수 없는 자동 점수만으로 경쟁력 판정을 대신하지 않는다.

### 8.3 경쟁력 합격표

각 시각·플레이 작업 명세는 `docs/DESIGN.md`의 목표와 같은 장르·규모의 기준 화면 또는 비교 작품 1~3개를 지정한다. 비교 근거 없이 “좋아 보인다”는 판정은 무효다.

다음 다섯 항목을 5점 척도로 평가한다.

1. 기능 완결성과 플레이 명료성 — 25%
2. 조작감, 반응성, 피드백 타이밍 — 20%
3. 가독성, 시각 일관성, 화면 구성 — 20%
4. 폴리시, 개성, 비교작 대비 경쟁력 — 20%
5. 성능, 안정성, 에셋 통합 건전성 — 15%

치명 결함이 0개이고, 적용 가능한 모든 항목이 4점 이상이며, 가중 점수가 85점 이상이어야 합격한다. 비시각 작업은 적용 불가 항목과 이유를 명세에 고정하고 나머지를 100점으로 재정규화한다. 미오·마루·별이 중 해당 책임 평가와 구현자가 아닌 다른 제공자 평가가 모두 통과해야 한다.

검토 세션에는 파일 경로 문자열만 주지 않고 원본 스크린샷·프레임 시트·필요한 전후 비교를 실제 멀티모달 입력으로 전달한다. 실행 기록에 전달한 파일 해시와 제공자의 이미지 입력 확인이 없으면 시각 합격으로 인정하지 않는다.

## 9. 토큰 절약 원칙

품질 모델을 낮추지 않고 중복을 줄여 토큰을 아낀다.

- 동일 기능을 세 모델이 각각 구현하지 않는다.
- 한 명 구현, 다른 한 명 검토를 기본으로 한다.
- 독립 작업만 병렬화하고 충돌 가능 작업은 직렬화한다.
- 공통 지침은 파일에서 읽고 프롬프트에 반복 복사하지 않는다.
- 작업 명세에 관련 경로, diff, 실패 로그, 스크린샷만 제공한다.
- 검토자는 전체 저장소가 아니라 정확한 후보 SHA의 diff와 증거부터 본다.
- 정상 검사 로그는 요약하고 원문 파일 경로를 남긴다. 실패 로그는 필요한 구간을 보존한다.
- 제공자 장애는 다른 모델에게 같은 긴 작업을 무조건 재전송하지 않고 재시도 예산과 허용된 대체 정책을 따른다.

## 10. 실패, 재시도, 정지와 보안

### 10.1 실패 분류

- 작업 실패: 테스트, 시각 검증, 범위 검사, 독립 검토 불합격
- 인프라 실패: CLI 부재, 인증, 사용량, 네트워크, 과부하, 시간 초과
- 통합 경쟁: 기준 SHA 변경, 기대 SHA 불일치

인프라 실패를 기능 불합격으로 기록하지 않는다. 제공자별 지수 백오프와 최대 재시도 횟수를 적용한다. 제공자 회로가 열리면 프로세스는 비정상 종료를 반복하지 않고 STOP을 확인하는 제한된 대기에 들어갔다가 설정된 시각에 한 번만 half-open 점검한다. 처리되지 않은 코디네이터 예외는 비정상 종료해 launchd가 재시작하되, 지속 crash 기록이 임계값을 넘은 다음 실행은 같은 제한 대기 상태로 들어가 폭주를 막는다. 원인과 재점검 시각을 로그와 STATUS에 남긴다.

### 10.2 STOP과 종료 코드

- 바퀴 시작 전 STOP이 있으면 새 작업을 시작하지 않고 정상 종료한다.
- 바퀴 중 STOP이 생기면 drain 모드로 바뀐다. 새 작업과 새 재시도는 시작하지 않고, 이미 실행 중인 최대 세 작업만 각 작업의 설정된 deadline까지 안전한 후보 커밋·로그 상태로 마친다.
- STOP 뒤 아직 승인되지 않은 후보는 보존하되 통합하지 않는다. 이미 `COMMITTING`에 진입한 원자적 CAS만 복구 규칙에 따라 끝낸다.
- 모든 CLI는 별도 프로세스 그룹으로 실행한다. deadline이 지나면 그룹 전체에 정상 종료를 요청하고 유예 뒤 종료해 자식 프로세스가 남지 않았음을 확인한다.
- 바퀴 사이 대기 중에도 STOP을 짧은 간격으로 확인한다.
- 사용자 STOP과 최대 바퀴 도달은 종료 코드 0이다.
- 복구 불가능한 코디네이터 오류만 비정상 종료 코드로 launchd 재시작 대상이 된다.

### 10.3 보안

- 구독 CLI를 사용하고 새 유료 API 사용을 만들지 않는다.
- 루트 `.env` 외에 프로젝트별 비밀 파일을 만들지 않는다.
- 작업자 환경 변수는 명시 허용목록만 전달하고, 제공자 인증 자료는 읽기 전용 원본과 격리된 임시 HOME을 사용한다.
- 프롬프트, 로그, 작업 명세에서 토큰·키·쿠키·인증 헤더를 기존 시크릿 제거 규칙 또는 동등한 검사로 마스킹한다.
- 기존 중단된 autopilot 또는 session-watch 경로를 다시 켜지 않는다.
- 외부 알림이 필요하면 예원 경로를 거치며 작업자가 직접 텔레그램을 호출하지 않는다.

### 10.4 디스크와 보존

- 새 작업 전 가용 공간 기본 하한 20 GiB와 자율 루프 캐시 기본 상한 20 GiB를 검사한다. 넘으면 새 작업을 시작하지 않고 fail-closed 상태로 기다린다.
- 성공한 격리 복제본과 검증 공간은 후보 객체가 통합 ref에서 도달 가능하고 로그·해시가 보존됐음을 확인한 뒤 자율 루프가 만든 경로만 정리한다.
- 실패 복제본은 원인 분석 증거로 보존한다. 실패 공간의 개수·용량 상한에 닿으면 자동 삭제하지 않고 루프를 보류해 README의 수동 정리 절차로 넘긴다.
- 정리 대상은 realpath가 `.worktrees/autonomous/` 또는 `output/cache/autonomous_loop/` 아래이고 유효한 소유 manifest가 있는 실행 경로로 제한한다. symlink, 저장소 루트, 사용자·다른 AI 워크트리는 절대 정리하지 않는다.
- 날짜별 원문 로그는 자동 삭제하지 않는다. 용량 경고와 실행별 크기를 보드에 표시한다.

## 11. 로그와 관찰 가능성

각 바퀴는 `logs/YYYY-MM-DD/<run-id>/` 아래에 다음을 남긴다.

- `run.json`: 시작·종료 시각, 상태, 문서 해시, 통합 기준·결과 SHA
- `coordinator.log`: 스케줄, 클레임, 상태 전이, STOP, 실패 원인
- `<task-id>/manifest.json`: 작업 명세와 쓰기 범위
- `<task-id>/<provider>-worker.log`: 새 세션 명령, 실제 모델, 종료 코드, 후보 SHA
- `<task-id>/<provider>-review.log`: 검토 대상 SHA, 판정, 근거, 종료 코드
- `<task-id>/tests/`: 검사 명령별 원문과 요약
- `<task-id>/visual/`: 스크린샷·측정·에셋 검사 증거
- `summary.md`: 사람이 빠르게 읽는 바퀴 결과

명령 시작과 종료, 종료 코드, 시간 초과, STATUS 미갱신 이유까지 항상 기록한다. 기존 `loop/board.py`는 새 로그 위치를 읽도록 갱신하거나, 이행 기간에 호환 색인을 제공해 로그가 보이지 않는 문제를 없앤다.

## 12. launchd 운영

macOS LaunchAgent는 저장소의 plist를 `~/Library/LaunchAgents/`에 설치하되 구현 검증 동안 로드하지 않는다.

- 로그인 시 시작: `RunAtLoad=true`
- 비정상 종료만 재시작: `KeepAlive.SuccessfulExit=false`
- 재시작 폭주 방지: `ThrottleInterval`과 내부 회로 차단기
- 명시 PATH: 저장소 도구, Homebrew, 시스템 경로, Claude·Codex·Grok CLI 위치 포함. plist에는 `$HOME`, `~`, 미해결 환경 변수가 아닌 설치 시점 절대경로를 렌더링한다.
- 작업 디렉터리와 stdout/stderr 로그 경로 명시
- 정상 STOP 종료 후에는 사용자가 다시 시작하기 전까지 그대로 둔다.

README에는 설치, 켜기, 끄기, 상태, 로그, STOP, 재개 절차를 비기술 사용자도 실행할 수 있게 정리한다.

설치 후에는 `plutil` 문법 검사, 저장소 원본과 설치본 해시 일치, `launchctl print gui/<uid>/com.ailab.autonomous_loop`가 미등록을 반환하는지를 증거로 남긴다. 두 바퀴 사전 실행 동안 bootstrap/load 명령이 호출되지 않았음도 검사한다.

## 13. 테스트 전략

구현은 테스트 주도로 진행한다. 먼저 현재 실패를 재현하고 아래 테스트를 추가한 뒤 최소 구현으로 통과시킨다.

### 13.1 단위·통합 테스트

- 경로 부모·자식, 동일 파일, 공유 자원 태그 충돌 탐지
- Unicode 정규화·대소문자·symlink·rename·submodule·`.git` 경계 우회 거부
- 독립 작업 1개와 최대 3개 적응형 배정
- 같은 제공자 자기 검토 거부
- 승인 SHA와 실제 통합 SHA 불일치 거부
- `master`·사용자 브랜치 대상 통합 거부
- OS 샌드박스에서 저장소 루트·공용 ref·다른 워크트리 쓰기 음성 대조 실패 확인
- 실행 전후 ref·워크트리 스냅샷 변조 탐지
- integration 브랜치 checkout 상태와 zero-OID 초기화 경쟁 거부
- 최신 통합 SHA 변경 시 승인 만료와 재검사, 후속 통합 뒤 crash 복구의 조상 판정
- 세분된 상태 전이, 원자 락, fencing, write-ahead intent, CAS 전후 crash 복구, 멱등 재시도
- 범위 밖 수정과 스테이징 잔류 탐지
- 충돌 시 `merge --abort` 및 후보 보존
- STOP 전·중·대기 처리와 정상 종료 코드
- 제공자 장애, 재시도, 회로 차단기, 실제 모델 기록
- Claude Fable→허용된 Opus 5 외 대체, Codex Sol/xhigh 이탈, Grok 미확정 모델의 실패 폐쇄
- 실패 원인과 STATUS 미갱신 이유의 로그 보존
- 비밀값 마스킹과 로그 경로 호환성
- 루트 INBOX·DESIGN과 integration STATUS 원천 분리 및 다음 바퀴 기억 유지
- 다른 AI의 ref·워크트리 정상 변경 허용과 autonomous 보호 ref 변조 거부
- 성공 임시 공간의 제한 정리, 실패 증거 보존, 디스크 하한 fail-closed

### 13.2 두 바퀴 사전 실행

launchd를 로드하기 전에 최대 바퀴 수를 2로 고정해 실행한다. 사전 실행은 실제 저장소를 본뜬 일회용 fixture Git 저장소에서 운영 코디네이터와 제공자 어댑터를 그대로 사용하며, 각 세션 최대 턴과 5분 deadline을 둔다. fixture 안에서도 자동 통합 브랜치 이름은 `autonomous/integration`이다.

1. 첫 바퀴는 한 작업·한 구현자·다른 제공자 검토 경로를 확인한다.
2. 둘째 바퀴는 서로 독립인 작업의 병렬 경로와 겹치는 작업의 직렬화 또는 보류를 확인한다.
3. 매 바퀴 실제로 새 세션이 만들어졌고 세션 재개 옵션을 사용하지 않았음을 로그에서 확인한다.
4. `master` SHA가 실행 전후 동일함을 확인한다.
5. 로그, 후보 커밋, 검토 승인, 통합 SHA, STATUS 커밋을 보여준다.

첫 바퀴 fixture는 서로 다른 최상급 제공자의 단일 구현·검토를, 둘째 바퀴 fixture는 독립 파일 두 개의 병렬 후보와 의도적으로 겹친 한 후보의 사전 거부를 검증한다. idle poll은 두 바퀴에 포함하지 않고, 새 세션이 끝난 실행만 카운트한다. 실제 저장소의 `master`와 작업 파일은 읽기 스냅샷 외에는 사용하지 않는다. 실제 제공자 CLI·새 세션·격리 복제본·검토·로그·통합 보호 경로를 모두 거치며, 가짜 CLI 기반 테스트는 별도로 수행해 이를 대체하지 않는다. fixture가 일회용이어도 두 바퀴 원문 로그는 주 저장소의 `logs/YYYY-MM-DD/<run-id>/`에 보존한다. 이 두 바퀴는 운영 안전 검증이지 실제 게임 품질 합격의 대체 증거가 아니다.

마지막에는 관련 테스트, `python3 projects/ai-team/harness/check_all.py`, 변경 범위 검사를 새로 실행한 결과로만 완료를 선언한다.

## 14. 문서와 데이터 이행

- 기존 DESIGN·STATUS·INBOX 내용은 삭제하지 않고 필요하면 날짜가 있는 `docs/archive/`로 보존한다.
- 코디네이터만 STATUS를 수정해 동시 편집을 제거한다. 작업자는 작업별 결과 명세만 쓴다.
- INBOX 지시는 자동 삭제하지 않고 해시 또는 명시 ID로 처리 여부를 기록한다.
- 오래된 운영 문서의 플랫폼·로스터·모델·이미지 규칙은 원천 문서를 가리키게 하여 중복 사본을 줄인다.
- 기존 다른 AI 워크트리와 브랜치는 발견만 하고 수정·정리하지 않는다.

## 15. 최종 인수 조건

구현 완료는 다음 증거가 모두 있을 때만 선언한다.

1. 준비 폴더, 문서 틀, 5절 PROMPT, 설정 분리, 무한 루프와 STOP이 요구대로 존재한다.
2. Claude Fable→Opus 5, Codex Sol, 확인된 최상급 Grok 정책과 실제 모델 로그가 있다.
3. 단일·병렬 적응형 작업, 쓰기 범위·공유 태그 충돌 방지, OS 쓰기 격리, 독립 검토가 테스트로 증명된다.
4. 자동 통합은 `autonomous/integration`에만 일어나고 `master`는 변하지 않는다.
5. 검사 대상과 통합 대상의 SHA 일치가 보장된다.
6. 게임 실행·시각·스프라이트·에셋 품질 증거 규칙이 PROMPT와 검증기에 반영된다.
7. 실패 원인을 빠짐없이 남기고, 정상 STOP과 비정상 재시작이 구분된다.
8. launchd plist가 올바른 PATH와 재시작 정책으로 설치됐지만 로드되지 않은 상태다.
9. 실제 새 헤드리스 세션으로 두 바퀴를 완료한 날짜별 로그를 제시한다.
10. README에 파일 목록과 켜기·끄기·상태·로그·복구 방법이 정리돼 있다.
11. 관련 테스트와 전체 하네스가 최종 상태에서 통과한다.

이 설계의 핵심은 모델에게 협업 안전을 맡기지 않는 것이다. 모델은 게임을 만들고 의미를 검토하며, 코디네이터가 범위, 상태, 커밋, 검토 SHA, 통합을 결정론적으로 강제한다.
