### 실행 명령 (검증된 것)

> **2026-08-14: 맥이 유일한 운영 기계다.** 경로·프로세스 조회는 전부
> `skills/마루_게임개발/tools/game_platform.py` 한 곳에서 판정한다. 아래 명령을
> 손으로 치지 말고 도구를 쓰는 게 정답이다(도구가 버전·락·타겟을 알아서 본다).

```bash
# 권장 — 도구가 ProjectVersion.txt를 읽고 타겟(맥=StandaloneOSX)을 정한다
python3 projects/ai-team/skills/마루_게임개발/tools/game_regression.py --only w1

# 직접 부를 때 (맥). ⚠️ 버전을 문서에서 베끼지 말고 ProjectVersion.txt를 읽어라 —
#    한때 문서가 6000.0.36f1로 낡아 있었고, 그 버전으로 돌리면 전체 재임포트가 터진다.
# ⚠️ 에디터가 열려 있으면 배치는 "another Unity instance"로 즉시 죽는다(exit 21).
#    **죽이지 마라.** 오너가 Hub로 연 에디터일 수 있다 — 도구는 보고하고 중단한다.
#    확인은 `ps -Ao pid,command | grep -i 'Unity.app/Contents/MacOS/Unity'`.
V=$(awk '/m_EditorVersion:/{print $2}' projects/ashes-to-stars/unity/ProjectSettings/ProjectVersion.txt)
"/Applications/Unity/Hub/Editor/$V/Unity.app/Contents/MacOS/Unity" -batchmode -quit \
  -projectPath "$PWD/projects/ashes-to-stars/unity" -buildTarget StandaloneOSX \
  -executeMethod W1Runner.Build -logFile "$PWD/projects/ashes-to-stars/results/build.log"

# 블렌더 (반드시 --factory-startup — 설치된 애드온이 에러를 뿜는다)
/Applications/Blender.app/Contents/MacOS/Blender --background --factory-startup \
  --python projects/ashes-to-stars/blender/gen_props.py
```

Windows에서 돌려야 할 일이 생기면 도구가 알아서 `C:\Program Files\Unity\Hub\Editor\<버전>\Editor\Unity.exe`
와 `StandaloneWindows64`로 폴백한다 — 스크립트를 고칠 필요 없다.

## 5. 이 프로젝트에서 실제로 겪은 함정 (반복하지 말 것)

| 함정 | 무엇이 일어났나 | 어떻게 막나 |
|---|---|---|
| **빈 화면 700fps** | 텍스처 Read/Write 누락으로 아틀라스가 조용히 실패, 스프라이트를 하나도 안 그린 채 성능만 측정 | FPS와 **렌더 검증**(스크린샷의 유닛 픽셀 수가 몹 수에 비례하는지)을 짝지어 판정 |
| **낡은 빌드로 측정** | `W1.exe` 런처는 코드가 바뀌어도 타임스탬프가 안 변한다. 불가능한 수치(4초에 피격 10,508회)를 읽었다 | `*_Data/Managed/Assembly-CSharp.dll` 시각을 확인 |
| **유니티 크래시 오진** | 씬 생성이 두 번 죽어 TextMesh 탓으로 보고 멀쩡한 코드를 고쳤다. 진짜 원인은 **다른 Unity 인스턴스가 프로젝트를 잡고 있던 것** | 배치 실행 전 `taskkill /IM Unity.exe /F` + `Temp/UnityLockfile` 제거. 크래시는 스택을 먼저 읽을 것 |
| **runInBackground=false** | 창이 포커스를 잃자 Update가 멈춰 자동 봇 검증이 아예 안 돌았다 | 검증 빌드는 항상 `runInBackground = true` |
| **측정 상한에 걸린 결과** | W3 다섯 구성 중 넷이 45초를 완주해 생존 시간으로 구분 불가 | 상한에 닿은 결과는 통과가 아니라 **측정 실패**. 전멸까지 돌리고 압력을 점증 |
| **밝기로 배경 제거** | 시트 배경(밝기 13)보다 캐릭터 외곽선(0~4)이 더 어두워서, 임계값으로 지우니 캐릭터가 부서졌다 | 배경은 "어두운 색"이 아니라 **특정 색**이다. 색 비교 + 가장자리 flood fill |
| **대화 속 이미지** | 오너가 붙여넣은 이미지는 디스크에서 못 꺼낸다 | `Downloads` 등에서 파일을 찾거나, 저장 폴더를 안내할 것 |
| **Resources 밖 자산** | 픽셀아트를 프리팹에 연결하고 "적용 완료"라고 기록했는데 화면엔 안 나왔다. `Resources.Load`는 **`Assets/Resources/` 밖을 못 본다**. 게다가 W1~W3 빌드는 프리팹을 안 쓰고 SpriteBank를 쓴다 | 런타임이 실제로 읽는 경로에 넣었는지 확인. SpriteBank는 캐릭터가 하나도 안 잡히면 **LogError로 알린다** — 조용히 플레이스홀더로 굴러가지 않게 |
| **아군이 몹 스프라이트** | W3 파티 슬롯에 `{Player, Mob0, Mob1, Summon, Mob2}`를 꽂아 **파티원 5명 중 4명이 몬스터로 그려지고 있었다.** 수치 검증은 전부 통과했다 — 스프라이트가 뭐든 시뮬레이션은 돌기 때문 | 렌더 검증은 "픽셀이 있는가"만 보지 "**맞는 그림인가**"는 안 본다. 스크린샷을 사람 눈으로 한 번은 볼 것 |
| **에디터 락 ≠ 죽여도 되는 프로세스** | 배치 빌드가 exit 21로 죽어 `taskkill`을 하려 했는데, 그 Unity.exe는 **오너가 Hub로 열어둔 에디터**였다(자식 AssetImportWorker 2개까지) | 죽이기 전에 `wmic process where "name='Unity.exe'" get ProcessId,CommandLine`. `-useHub`가 붙어 있으면 사람이 연 것이다 |
| **IMGUI가 카메라 렌더를 덮는다** | 전투가 "검은 화면만" 나온다고 했는데 로그를 보니 **정상 작동 중**이었다. `GameScreen.OnGUI`가 매 프레임 화면 전체를 불투명 배경으로 칠하고 있었다 | "화면이 검다"를 렌더 실패로 단정하지 마라 — **로그가 먼저 말해준다**. 카메라 장면을 보여줄 화면은 배경을 깔지 않는다 |
| **투명해 보이는 체커보드** | 오너 시트가 투명 배경으로 보였지만 알파를 재보니 **전부 255**였다. 체커가 이미지에 그려져 있었다(스크린샷 저장 흔적) | 배경 제거 전에 `알파==0인 픽셀 수`를 먼저 세라. 0이면 투명이 아니라 **그려진 무늬**다 |
| **계산은 되는데 반영이 안 됨** | 보상이 계산만 되고 지갑에 안 쌓였고, 소지 상한은 보유량을 0으로 두고 판정해 **영원히 안 걸렸다** — 상한이 있다는 말만 있고 없는 것과 같았다 | 클래스가 있는 것과 **그 인스턴스를 가진 주체가 있는 것**은 다르다. "계산 → 저장 → 다음 판에서 읽힘"까지 이어졌는지 확인 |
| **버튼이 쿨다운만 푼다** | 스킬 버튼을 눌러도 발동 조건(밀집·부상자 수)이 안 맞으면 아무 일도 안 일어났다 | 수동 발동은 **조건을 건너뛰는 경로**여야 한다. "눌렀는데 왜 안 나가지"가 남으면 지휘가 성립하지 않는다 |
| **rename 루프가 meta를 깼다** | `.png.meta`를 확장자 분리로 처리하다 `.meta`로 만들어 32개 GUID가 전부 고아가 될 뻔했다 | 자산 rename 뒤엔 **반드시** png 수와 png.meta 수를 세어 대조. 고아 meta 0건을 확인하기 전엔 끝난 게 아니다 |
| **크기만 보고 그림을 안 봄** | 스프라이트 분할 결과를 픽셀 크기로만 검증해서, dps 폴더에 탱커 그림이 들어간 것(행 한 칸 밀림)을 못 잡았다. 파티원이 몹 스프라이트로 그려지던 것도 같은 계열이다 | 분할·연결 후에는 **대조 이미지를 만들어 눈으로 확인**한다. 색·복장이 그 역할과 맞는지까지 본다 |
| **flood fill 시작점 없음** | 배경 투명화가 가장자리에서 번지는 방식인데, 격자선이 crop 경계에 걸리면 시작점이 하나도 없어 **배경이 통째로 남는다** | 셀을 안쪽으로 물려 자르고, 시작점이 없으면 가장자리 최빈색을 배경으로 인정하는 폴백을 둔다 |
| **프레임별 타이트 크롭** | 프레임마다 내용 bbox로 자르면 캔버스 크기와 발 위치가 제각각이 되어 재생 시 캐릭터가 튄다 | 공통 캔버스 + 가로 중앙(본체 기준)·세로 바닥 정렬. 크기 정규화는 **서 있는 자세끼리만**(눕는 death를 같이 늘리면 거대해진다) |
| **에디터에 열린 씬이 재생된다** | 씬을 8개로 나눈 뒤 Result 씬을 열어둔 채 Play를 눌러 "결과만 나온다"고 오인 | 유니티는 빌드 세팅 0번이 아니라 **열린 씬**을 재생한다. `playModeStartScene`으로 진입점을 고정한다 |

## 6. 결정을 어디서 찾나 — "예전에 뭘 정했더라?"

세션이 바뀌면 대화 기록은 사라진다. **결정은 전부 파일에 있고, 종류별로 사는 곳이 다르다.**

| 알고 싶은 것 | 찾을 곳 |
|---|---|
| 게임 규칙이 어떻게 정해졌나 | `GAME_DESIGN_ASHES_TO_STARS.md` — **✅ 표시가 오너 확정**, 💡는 제안, ⚠️는 주의, 📌는 폐기된 안의 기록 |
| 수치가 왜 그 값인가 | 같은 문서 **§18 수치 밸런싱 기준표** — 앵커(T1 시간당 1골드·티어 ×1.6·스케일링 0.65)에서 유도된다 |
| 이 규칙이 왜 생겼나 | 같은 문서 **§19 악용 대응** + 각 절의 📌 — 감사에서 나온 구멍과 대응이 근거와 함께 있다 |
| 아트 규격·물량 | `GAME_ART_RESOURCES.md` — §0-A가 최신 방침(픽셀아트), **§0-B(최소화)가 물량의 최종 권위**, §1~6은 그 이전 산정 |
| 몬스터가 몇 종이고 뭐가 나오나 | `GAME_MONSTERS_ASHES_TO_STARS.md` — 잡몹 20·정예 30·보스 45종 명단, 계열 배율, 티어별 웨이브 편성표 |
| 스프라이트를 어떻게 만드나 | `GAME_MONSTER_ANIM_SPRITE_PROMPTS.md` — 애니메이션 상태·프레임 길이(밸런스 수치와 직결), 생성 프롬프트. **§0을 먼저 읽을 것** — 종수와 작화 단위를 혼동하면 물량이 4배가 된다 |
| 검증 결과 수치 | 기획서 **§21 프로토타입** + `output/qa/ashes-to-stars/` 리포트 |
| 왜 이렇게 구현했나 | **커밋 메시지** — `git log --oneline --grep=game` 로 훑는다. 사고와 교훈을 본문에 적어 뒀다 |
| 코드가 왜 이런가 | 소스 파일 상단 주석 — 각 스크립트가 "왜 이 방식인가"를 적고 있다 |

- ⚠️ **문서와 코드가 다르면 문서가 맞다**고 가정하지 마라. 실제로 `W3Party.cs`의 잡몹 속도가
  기획서 §18-11과 어긋난 적이 있다(정합성 감사로 발견). 둘이 다르면 **기획서를 기준으로 코드를 고친다**
- ⚠️ 이 문서가 최신이 아닐 수 있다. **§3·§4가 마지막 커밋과 맞는지** `git log -3` 으로 먼저 대조하라

## 7. 작업 방식 (오너 지시)

- **작업 하나 끝낼 때마다 커밋**하고, 다음 작업을 정한 뒤 실행한다. 이걸 반복한다
- 병렬 가능한 일은 **에이전트를 만들어 동시에** 돌린다
  (단 유니티는 프로젝트 락 때문에 **한 번에 하나만** — 에이전트에 유니티 실행 금지를 명시할 것)
- **항상 기획서를 참고**한다. 수치·규칙의 출처는 언제나 `GAME_DESIGN_ASHES_TO_STARS.md`
- 커밋·푸시는 master 직행. 푸시가 403이면
  `git config --local credential.https://github.com.username crossx362-commits` 후 `gh auth setup-git`
