## 1. 결정 요약

### 1-1. 채택: **미션 그래프 + 손으로 만든 아레나 템플릿** (Dead Cells / Enter the Gungeon 계열 하이브리드)

| 층위 | 기법 | 근거 |
|---|---|---|
| **플로어 구조** | 미션 그래프(노드+간선, 사이클 1개 허용) — Dormans의 mission/space 분리에서 **mission만** 차용 | [Dormans 2010](https://pcgworkshop.com/archive/dormans2010adventures.pdf), [Ludomotion devblog](https://www.ludomotion.com/blogs/level-generation/), [Dead Cells devlog](https://deepnight.net/tutorial/the-level-design-of-dead-cells-a-hybrid-approach/) |
| **노드 내용** | 손으로 만든 **아레나 템플릿** 집합에서 제약 만족 선택 + 내부 청크 랜덤화 | [Spelunky (Derek Yu)](https://makegames.tumblr.com/post/4061040007/the-full-spelunky-on-spelunky), [Enter the Gungeon (Dodge Roll)](https://www.gamedeveloper.com/design/q-a-the-guns-and-dungeons-of-i-enter-the-gungeon-i-) |
| **아레나 지형·장식** | 기존 `NoiseTerrain`·`FieldDecor`를 노드별 시드로 재사용 (신규 아트 0장) | 이미 프로젝트에 있음 — 재설계하지 않는다 |
| **연결성** | **구성적 보장** — 척추(spine)를 먼저 깔고 그 위에 붙인다. 사후 검증은 테스트에서만 | Spelunky 경로 우선 · Brogue 방 접합 |

### 1-2. 왜 이것인가 (이 게임의 요구에 묶어서)

1. **웨이브 아레나는 곧 "손으로 만든 방"이다.** 스폰 링·엄폐물·카이팅 레인·쿼터뷰 가독성은
   생성기가 우연히 맞출 수 없다. Dodge Roll은 이 결론에 **실측으로 도달해 손 제작으로 되돌렸다**
   ("more fun and more fair if we hand designed the rooms"). Enter the Gungeon은 이 게임과
   가장 가까운 출시작(탄막 아레나 + 방 그래프)이다.
2. **작은 아트 예산이 이유다.** Spelunky의 "템플릿 안의 랜덤 청크"는 적은 저작물로 다양성을
   내는 문서화된 방법이고, 그게 **100층 문제의 정답**이다. 절차 지형(셀룰러 오토마타)은
   임의의 들쭉날쭉한 실루엣을 감당할 타일셋을 요구한다 — 우리에게 가장 없는 자원.
3. **영구사망이 결정성·감사를 요구한다.** 런 하나가
   `시드 → (템플릿 id, 청크 id, 웨이브 편성 id)`로 환원되면 로그 한 줄로 재현·검증된다.
   ✅ 기획서 §22-2가 이미 "**던전 시드는 반드시 서버**"라고 못 박았다 — 시드가 재현 가능한
   1차 산출물이라는 전제 자체가 기획서 결정이다.
4. **그래프는 훔치고 문법은 버린다.** Unexplored 2는 Ludoscope라는 전용 저작 도구 위에
   ~10단계 문법 패스를 쌓는다. 1인 개발에서 그 도구가 곧 프로젝트가 된다.
   페이싱(아레나→정예→강화→지름길→보스)만 그래프로 받고, 공간은 아레나 템플릿이 채운다.

### 1-3. 폴백: **BSP 분할** — 단, "아레나 슬롯 배치기"로만

그래프 저작이 100층을 감당 못 하면 BSP로 겹치지 않는 방 슬롯을 나누고 리프에 아레나 템플릿을
꽂는다(트리라 연결성은 구성적으로 보장). 대신 페이싱 제어를 잃는다.
⚠️ **BSP를 쓴 출시작의 1차 근거는 이번 조사에서 찾지 못했다** — Diablo 1 귀속설은 전부
제3자 역공학 글이라 근거 기준 미달. 폴백을 실행한다면 프로토타입 시간을 따로 잡아야 한다.

⚠️ **셀룰러 오토마타 캐이브로는 폴백하지 마라.** Brogue도 CA를 **방 하나의 유형**으로만 쓰고
레벨 전체에 쓰지 않는다. 유기적 블롭은 웨이브 스폰 링·포위 판정·쿼터뷰 가독성을 전부 예측 불가로 만든다.

### 1-4. 조사 결과가 기획서와 충돌하는 지점 — 전부 기획서를 따랐다

| 조사가 시사한 것 | 기획서 결정 | 처리 |
|---|---|---|
| 던전 = 걸어다니는 공간(방+복도 기하) | ✅ §7 "진행 방식은 **뱀서류** — 웨이브 생존 + 처치" | **기획서 채택.** 던전은 걸어다니는 미로가 아니라 **아레나 노드의 연쇄**다. 복도·문 기하는 만들지 않는다 |
| 그래프 문법으로 자물쇠·열쇠 배치 | ✅ §7 "입장 제한·열쇠 없음(숙제 금지 원칙)" | **기획서 채택.** 열쇠·자물쇠 비트는 쓰지 않는다. 사이클은 "지름길/위험 우회"로만 |
| 층마다 다른 기하 생성으로 다양성 확보 | ✅ §10-6 "스케일링은 곱연산이 아니라 **패턴 추가 + 밀도 증가**" | **기획서 채택.** 층 다양성의 1차 축은 기하가 아니라 **웨이브 편성**(계열·AI·정예 비율) |

## 3. 던전 생성 알고리즘 명세

### 3-0. 전제 — 이 게임에서 "던전"이 무엇인가

- ✅ §7: 필드 안에 존재, **진입할 때마다 구조·웨이브 구성이 바뀜**, 뱀서류(웨이브 생존+처치),
  진행 중 임시 강화 선택, 최대 5인, 입장 제한·열쇠 없음
- ✅ §18-2: **일반 던전 1판 = 10분**, 입장 비용 0.02 G/h
- ✅ §10-1: 던전 보스는 **랜덤 던전 종점**, 기믹 1개 + 쫄 소환
- ✅ §5: **보스가 등장하면 지휘 조작이 열린다** — 잡몹 노드는 자동, 종점 보스 노드에서 손이 들어간다
- 💡 따라서 던전 = **아레나 노드 7~9개의 방향성 그래프**. 노드 하나가 한 아레나(현 `W3Party` 판)이고,
  간선은 "다음 아레나로 이동"이다. 걸어다니는 복도 기하는 없다.

### 3-1. 데이터 구조 (순수 C#, MonoBehaviour 아님 — 씬 없이 테스트 가능해야 한다)

```
DungeonPlan                 한 던전 런의 전체 계획. 생성 후 불변(immutable).
  uint      RunSeed         런 시드(0 금지). 화면·로그에 그대로 노출한다
  int       Tier            §10-6 티어(0~9) = GameState.Tier
  MobFamily Family          ✅ §10-3 "진입 전 계열 표시" — 진입 전에 확정·표시
  DungeonKind Kind          일반 / 레이드급(§7)
  Node[]    Nodes           7~9개
  int[][]   Edges           인접 리스트. Nodes[0]=입구, Nodes[^1]=보스(종점)
  int       BossCount       1~3 (§10-7 확률 60/30/10)

Node
  int          Index
  NodeKind     Kind         아래 3-4 표
  string       TemplateId   아레나 템플릿 id
  int[]        ChunkIds     템플릿 내부 랜덤 청크(Spelunky식)
  WavePlan     Wave         null이면 전투 없는 노드
  uint         TerrainSeed  NoiseTerrain·FieldDecor에 넘길 노드 전용 시드
  bool         Optional     막다른 보상 분기인가(들르지 않아도 클리어 가능)

WavePlan                    §18-11·몬스터문서 §5에서 유도된 값만 담는다
  int        StartCount     시작 동시 몹 수
  int        TargetCount    이 노드 종료 시점의 목표 동시 몹 수
  float      DurationSec    목표 지속 시간
  float      ElitePercent   §18-11 정예 비율(T1 5% → T10 12%)
  float      RangedPercent  §18-11 원거리 비율(T2부터 15~25%)
  MobAi[]    UnlockedAi     티어별 해금 AI(몬스터문서 §5)
  EliteKind[] EliteKinds    ✅ §10-2 "웨이브당 정예 유형은 1~2종"

RunState                    런 진행 중 변하는 것(계획과 분리한다)
  int   CurrentNode
  List<BoonId> Boons        ✅ §7 "던전을 나가면 초기화" — 저장하지 않는다
  int   ElitesKilled        💡 §10-2 다음 웨이브 드랍 배율의 근거
```

⚠️ **`DungeonPlan`을 런 도중 수정하지 마라.** 계획은 시드에서 나오고, 진행 상태는 `RunState`에만
쌓인다. 둘이 섞이면 "이 죽음을 시드로 재현할 수 있는가"가 깨지고, 그게 영구사망 게임에서
가장 비싼 버그다.

### 3-2. 시드 처리 (영구사망 = 결정성과 감사가 기능 요구사항이다)

**규칙 1 — `UnityEngine.Random`을 생성기에 쓰지 마라.** 공식 문서상 전역 정적 상태이고
"시드는 한 번 설정하면 회수할 수 없다". 이펙트·데미지 편차·에디터 도구 등 **아무나** 그 사이에
`Random.value`를 부르면 던전이 조용히 달라진다.

**규칙 2 — 서브시스템마다 독립 스트림.**

```
uint Stream(uint runSeed, int floorOrNode, SeedChannel ch)
    = Hash(runSeed, (uint)floorOrNode, (uint)ch)      // 0이면 1로 보정
```

| 채널 | 값 | 소비처 |
|---|---|---|
| `Layout` | 1 | 노드 수·그래프 형태·사이클 위치 |
| `Template` | 2 | 노드별 아레나 템플릿·청크 선택 |
| `Wave` | 3 | 웨이브 편성(계열·AI·정예 유형) |
| `Boon` | 4 | 강화 3택 후보 |
| `Drop` | 5 | 드랍 판정(§10-8·§18-4) |
| `Terrain` | 6 | `NoiseTerrain` 노이즈 |
| `Decor` | 7 | `FieldDecor` 프랍 배치 |
| `Boss` | 8 | 보스 종류·마릿수(§10-7) |

**규칙 3 — 소비 순서가 프레임 타이밍·부동소수 누적·`Dictionary` 순회 순서에 의존하면 안 된다.**
(현 `Economy.RollDrop`이 `DropRates` 딕셔너리를 순회하며 첫 히트를 반환한다 — §8-4 참조)

**규칙 4 — 런 감사 로그.** 진입 시 `RunSeed`·`Tier`·`Family`·`Kind`·노드 종류 나열을

**구현 선택** — 💡 `com.unity.mathematics` 패키지를 추가하지 말고 **10줄짜리 xorshift32 구조체를

### 3-6. 실패·재시도 규칙

> Brogue CE가 `failsafe = 10` 상한 재시도 + "실패하면 그 요소만 건너뛰고 레벨은 그대로 출고"를
> 쓴다. Dead Cells도 노드 단위로 재시도한다. **플로어 전체를 다시 만드는 재시도는 금지한다** —
> 영구사망 게임에서 생성 정지·생성 불가 시드는 런을 통째로 날리는 버그다.

| 규칙 | 내용 |
|---|---|
| **R1 재시도 단위** | 항상 **최소 단위**(노드 하나·템플릿 하나). 플로어 전체 재생성 금지 |
| **R2 상한** | 단위당 시도 **10회**. 소진하면 실패가 아니라 **폴백**으로 내려간다 |
| **R3 폴백** | 노드 종류마다 "무조건 유효한" 기본 템플릿 1종을 지정(`open_ring`). 품질이 떨어질 뿐 던전은 나온다 |
| **R4 폴백 계측** | 폴백을 탄 횟수를 `RunState`에 세고 런 로그에 남긴다. **0이 아니면 경고** — 조용한 품질 저하 금지 |
| **R5 연결성** | 런타임 검사 안 함(G2가 구성적으로 보장). 대신 **테스트에서 1만 시드에 flood fill 단언** |
| **R6 시드 0** | `RunSeed == 0`이면 1로 보정하고 로그에 남긴다(xorshift는 0 상태에서 고정점) |
| **R7 예산 초과** | `TargetCount`가 `BalanceConfig.잡몹상한`을 넘으면 상한으로 자르고 경고 로그 |

## 7. 검증 방법 — 각 단계를 무엇으로 증명하나

> ⚠️ **이 저장소의 규칙**: 새 검증 절차는 반드시 **네거티브 컨트롤**(고의로 망가뜨린 입력)을
> 한 번 넣어 빨간불이 뜨는지 확인한다. 통과만 보고 신뢰하지 마라.
> 📌 이 프로젝트는 이미 "빈 화면 700fps"(§21-1b)와 "파티원 4명이 몹 스프라이트"를 겪었다 —
> 수치가 나온다고 그림이 맞는 게 아니다.

### 7-1. 핵심 네거티브 컨트롤 — **"생성기가 아무것도 안 했는데 통과하지 않는가"**

이 질문에 답하는 단언 4개를 **한 세트로** 건다. 하나만 걸면 상수를 반환하는 생성기가 통과한다.

| # | 단언 | 상수 반환 생성기를 어떻게 잡나 |
|---|---|---|
| N1 | 같은 시드 → **완전히 같은 계획**(직렬화 문자열 비교) | 통과함(이 단언만으론 부족) |
| N2 | **다른 시드 1,000개 → 서로 다른 계획이 900개 이상** | ← **여기서 잡힌다.** 상수면 1개 |
| N3 | 노드 종류 분포가 3-4 배합표 범위 안 | 상수면 범위를 벗어나거나 분산 0 |
| N4 | 생성 중 실제로 소비한 난수 호출 수 > 0 (계측 카운터) | 상수면 0 |

- 💡 **N2를 "다르다"만으로 재지 마라** — 시드 앞 두 자리만 반영해도 통과한다.
  노드 종류 시퀀스·템플릿 id 시퀀스를 각각 따로 세어 **엔트로피가 붕괴하지 않았는지**를 본다.
- 💡 화면 쪽 네거티브 컨트롤: **같은 던전을 두 번 진입해 노드 맵 스크린샷을 찍는다.
  두 장이 픽셀 단위로 같으면 시드가 안 바뀐 것이다**(진입마다 바뀌어야 한다, ✅§7).

### 7-2. 단계별 검증

| 단계 | 증명 방법 | 네거티브 컨트롤 |
|---|---|---|
| S1 | `LifeSystem.GetCharacters().Count > 0`을 화면에서 육안 확인. 부활초를 하나 소비하고 **재시작 후에도 줄어 있는지** | `Initialize()` 호출을 지우면 화면이 "캐릭터 없음"으로 바뀌어야 한다(조용히 빈 목록 금지) |
| S2 | 회복 중 캐릭터가 회색으로, 남은 시간이 감소하는지 스크린샷 2장 비교 | `RecoveryEndTime`을 과거로 밀면 즉시 "출전 가능"으로 바뀌어야 한다 |
| S3 | 편성한 5인이 **전투 화면에 그 직업 스프라이트로** 나오는지 **눈으로** 확인 | 힐러를 빼고 출전 → 전투 HUD에 힐러 슬롯이 없어야 한다. (📌 "파티원이 몹 스프라이트" 사고 재발 방지 — 크기·개수가 아니라 **그림**을 본다) |
| S4 | 생성 사이에 `Random.value`를 1,000번 호출해도 계획이 **동일**한지 | 전역 `UnityEngine.Random`으로 되돌리면 이 테스트가 **실패해야** 한다 |
| S5 | 시드 10,000개 생성 → ①전부 입구→보스 도달 가능(flood fill) ②노드 수 7~9 ③폴백 카운터 0 ④생성 시간 p99 < 16ms | 척추 부설(G2)을 건너뛰게 하면 flood fill이 실패해야 한다 |
| S6 | 노드 맵에 그려진 카드 수 == `Plan.Nodes.Length`, 간선 수 == `Edges` 합 | 계획을 하나 지우면 화면에서도 하나 사라져야 한다 |
| S7 | T1과 T8 던전을 각각 돌려 **실제 스폰된 몹 수·정예 수·원거리 수**를 로그로 세어 3-5 표와 대조 | 📌 fps만 보지 마라(§21-1b "빈 화면 700fps"). **스폰 카운터 + 스크린샷 픽셀**을 짝지어 본다 |
| S8 | 강화를 3개 먹고 던전을 나갔다 다시 들어와 **강화가 0인지** | 저장하도록 바꾸면 이 테스트가 실패해야 한다(✅§7 초기화) |
