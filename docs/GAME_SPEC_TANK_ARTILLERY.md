## 2. 기획서 검토 — 그대로 가면 깨지는 것

### 2-1. ❌ 턴 15~20초 × 3인칭 직접 조작 = 시간이 안 맞는다

기획서 §4는 턴 15~20초, §5는 WASD 이동 + 마우스 카메라 회전, §9는 포탑·포신 마우스 조작, §11은 파워 게이지 차징을 한 턴 안에 요구한다.

원작 포트리스가 20초로 되는 이유는 **2D라서 카메라 회전이 없고, 이동이 좌/우 두 방향뿐**이기 때문이다. 3D에서는 같은 20초에 (a) 주변 지형 파악을 위한 카메라 회전, (b) 3D 이동, (c) 포탑 야우 정렬, (d) 피치 조절, (e) 파워 차징이 들어간다. 20초는 초보가 이동만 하다 끝난다.

**💡 확정안 — 2페이즈 턴**

```
턴 시작
 ├─ MOVE 페이즈 (최대 12초, 스페이스로 즉시 스킵)
 │    WASD 이동 + 자유 카메라. 이동 게이지 소비.
 │    ⚠️ 우클릭(조준 진입)을 누르는 순간 MOVE 페이즈는 되돌릴 수 없이 종료된다.
 │
 └─ FIRE 페이즈 (15초, 타이머 표시)
      카메라가 포신 뒤로 자동 스냅(수동 회전 불필요) → 야우/피치/파워 → 발사
      시간 초과 시 현재 조준 상태로 강제 발사 (포트리스 동일)
```

이유: 이동 페이즈에서 **카메라를 자유롭게 돌려도 FIRE 진입 시 자동 스냅**되므로, 조준 시간에서 카메라 조작 비용이 사라진다. 기획서 §8의 "우클릭 = 조준 모드"를 되돌릴 수 없는 페이즈 전환으로 승격시킨 것뿐이다.

총 턴 상한 27초, 평균 예상 15~18초(대부분 이동을 스킵). 3v3 6명 × 라운드 → 한 라운드 약 100초, 8~12라운드 = **13~20분**. 기획서 목표(8~15분)보다 길다 → §2-5 참조.

> 🚨 **위 산술은 무효다 (2026-09-19).** 팀이 **4:4 (8명)** 로 늘었다(§1-1). 같은 평균 턴이면
> 한 라운드는 6명×~16.6초 ≈ 100초 → **8명 ≈ 133초로 33% 길어진다.** 8~12라운드면 **18~27분**이 되고
> 기획서 목표(8~15분)와의 거리가 두 배가 된다.
>
> ✅ **2026-09-19 에 실제로 쟀다(오너 허가). 결론: 산술은 맞았고, 걱정은 빗나갔다.**
> 같은 맵·같은 시드로 3:3 을 나란히 재니 4:4 가 **+30~43%** 길어진다(산술 +33% 와 일치).
> 그런데 **게임 기본 난이도(중급)에서 11.1분** 으로 **목표 8~15분 안이다** — 3:3 때는 7.8분으로 오히려
> 목표보다 짧았다. 즉 4:4 가 템포를 목표 **한가운데로** 옮겼다. 표와 조건은 **§2-5-0**.
> (양 끝은 목표 밖이다 — 상급 이상 7.0분 이하, 초급 15.7분.)
> 🛑 여기까지가 허가 범위다. 이 결과로 **수치를 움직이는 것은 여전히 금지**.

### 2-2. ✅ 지형은 Heightfield가 아니라 **SDF 볼륨** (오너 지시 2026-09-15 "힉스필드 쓰지말어 코드로 그려")

> **초안 뒤집힘.** 이 문서 초안은 Heightfield를 채택하고 "오버행은 기획에서 뺀다"고 했다. 오너가 그 타협을 거부했고, **그게 맞았다.**

기획서 §21은 **구형 폭발**, §28은 **적 발밑을 도려내 떨어뜨리기**를 요구한다. Heightfield(컬럼당 높이 1개)로는 둘 다 흉내만 낼 수 있다. SDF 볼륨(부호거리장)으로 가면 기획서 원본이 **그대로** 성립한다.

| 기획서 요구 | Heightfield | **SDF 볼륨** |
|---|---|---|
| 지면 크레이터 | ✅ | ✅ |
| 언덕 옆면 깎기 | ⚠️ 눌림 | ✅ 진짜 구형 |
| **오버행·처마** | ❌ 불가 | ✅ **실측: 처마 1.5m / 공동 11.5m** |
| **동굴·터널** | ❌ 불가 | ✅ **실측: 천장 1.2m** |
| **발밑 도려내 떨어뜨리기(§28)** | ❌ 불가 | ✅ **실측: 2발로 지면 14.9m 붕괴** |

지불하는 값(§7-4 실측): 삼각형 3.4배, 폭발당 비용 1.6배, 메모리 10.4MB. **치를 만하다** — 기획서 §94가 "게임의 존재 이유"라 부른 순간이 이쪽에만 있다.

### 2-3. ❌ 매 프레임 적분은 필요 없다 (그리고 해롭다)

기획서 §12는 매 프레임 `Velocity += Gravity × DeltaTime`을 제안한다. 그런데 기획서 §13이 **공기 저항을 쓰지 않기로** 확정했다. 공기저항이 없으면 가속도는 중력+바람의 **상수 벡터**이고, 궤적에는 **닫힌 해**가 존재한다.

오일러 적분을 쓰면 잃는 것:
- 프레임레이트에 따라 탄착점이 달라진다(결정론 파괴 → 서버/클라 불일치)
- AI 조준·궤적 프리뷰·리플레이가 각자 다른 코드가 된다
- 누적 오차로 200m 사격에서 수 m가 틀어진다

**💡 확정: 해석해 1개 함수를 전 시스템이 공유한다.** 렌더는 그 함수를 t로 샘플링만 한다. (유도 미사일만 예외 — §5-6)

### 2-4. ⚠️ 폭발 반경과 피해 표가 서로 안 맞는다

기획서 §24는 일반탄 반경 4m, §39는 "4m에서 150, 6m에서 40"이라 적었다. 반경 4m이면 6m에서 피해는 0이어야 한다. 표는 실제로 **반경 7m짜리 곡선**이다.

**💡 §6에서 Inner/Outer 2단 감쇠로 통일**했고, 계산 결과가 기획서 표와 거의 일치한다(300/263/135/32 vs 300/250/150/40). 기획서 표를 의도로, 반경 숫자를 오타로 본다.

### 2-5. ✅ 한 판 길이 — **전제가 뒤집혔다 (AI 자동 대전 실측)**

> ⚠️ **이 절의 표는 3:3 · 옛 하네스 언덕 값이다(2026-09-15).** 팀은 그 뒤 4:4 가 됐고 맵도 바뀌었다 —
> 지금 게임의 한 판 길이는 **아래 §2-5-0 의 2026-09-19 실측**을 봐라. 이 표는 역사다.

#### 2-5-0. ✅ **4:4 한 판 길이 실측 (2026-09-19, 오너 허가 범위 안)**

> 오너가 **"4:4 에서 한 판이 몇 턴/몇 분인가를 재는 것"** 하나만 허가했다(2026-09-19).
> 여기 있는 것은 **읽고 기록한 값**이다 — 이 표를 근거로 수치를 움직이는 것은 여전히 금지다.

**조건**: 맵 `TwinHills`(게임 기본) · 난이도별 40판 · 기본 시드 · 아이템 2슬롯 · 서든데스 6R ·

### 2-5-1. 🚨 진짜 원인 — **지형 파괴 되먹임 나선**

"그럼 판 길이는 선형인 HP 로 맞추면 된다"고 적었다가 **실측으로 뒤집혔다. HP 도 선형이 아니다.**

| HP | 상급 1.5% | 중급 3% |
|---|---|---|
| 1000 | 4.9분 / 명중 99% | 10.6분 / 70% ✅ |
| 1400 | 6.2분 / 96% | 37.0분 / 26% |
| 1800 | 10.8분 / 78% ✅ | 89.8분 / 12% |
| 2200 | 20.5분 / 43% | 84.1분 / 12% |

같은 AI · 같은 오차 · 같은 시작 지형인데 **HP 만 1000→1800 으로 올리자 명중률이 70%→12%** 로 무너진다.
차이는 판 길이뿐이다. 즉 **누적된 지형 파괴가 명중률 자체를 떨어뜨린다**:

> 판이 길어진다 → 크레이터가 쌓인다 → 탄도가 막히고 탱크가 구덩이에 잠긴다 →
> 명중률이 떨어진다 → 판이 더 길어진다 → …

**나선은 예상보다 훨씬 빨리 돈다.** 같은 판 안에서 턴 구간별 명중률을 재면(HP 1800·오차 3%·40판):

| 턴 구간 | 0-19 | 20-39 | **40-59** | 60-79 | 80-99 | 140+ |
|---|---|---|---|---|---|---|
| 명중률 | 75.8% | 22.8% | **4.2%** | 5.5% | 7.5% | 3.8% |

**40턴(약 7라운드)이면 명중률이 18배 떨어진다.** 탱크 6대가 7라운드 사격 = 크레이터 약 42개.
그 시점에 200m 맵은 사실상 못 쓰는 상태가 된다. **이게 이 게임의 실질적 수명 상한이다.**
(100~139턴에서 17~20%로 잠깐 회복하는 건 지형이 완전히 평탄화돼 근거리 난전이 되기 때문으로 보인다.)

**판을 늘리는 모든 손잡이(HP·오차·라운드)가 이 나선을 건드린다.** 그래서 §2-5 의 오차 창이
0.7%p 로 좁았던 것이고, HP 스윕도 같은 벽에 부딪힌 것이다. 손잡이가 잘못된 게 아니라
**나선 자체를 끊지 않으면 어떤 손잡이도 안 듣는다.**

⚠️ 이건 AI 만의 문제가 아니다. **사람이 하는 긴 판도 똑같이 달 표면이 된다.**
§21(구형 크레이터)·§28(발밑 지형 끊기)은 확정 설계라 약화할 수 없으므로, 나선은 다른 데서 끊어야 한다:

1. **라운드 상한 + 서든데스** (§2-5 옛 레버 2 — 실측 후에도 유일하게 살아남은 레버).
   나선이 폭주하기 전에 판을 끝낸다. 6% 무승부 28/40 도 이걸로 구제된다.
2. 크레이터 반경·깊이의 **누적 상한** — 같은 자리를 계속 파도 일정 깊이에서 멈춘다.
3. 맵 가장자리 축소(서든데스와 결합) — 전장을 좁혀 남은 성한 지형으로 몰아넣는다.

⚠️ **"라운드마다 안식각 완화를 돌려 크레이터를 눕힌다"는 쓸 수 없다.** 그 코드는 Heightfield 시절
것이고 SDF 볼륨에는 존재하지 않는다(`TankGroundProbe.cs` 머리말). 지금 구조는 지형을 되돌리는 대신
**이동 규칙**(1.2m 턱 자동 등반)으로 갇힘을 푼다. 그리고 같은 파일이 **자동 지형 복구를 명시적으로 금지**한다 —
"포격으로 만든 지형이 무의미해진다". 즉 1·2·3 중 **지형을 되돌리지 않는 것**만 설계와 양립한다.

**옛 레버 1·3(HP 1000→800, FIRE 15→12초)은 폐기.** 둘 다 이미 짧은 판을 더 줄이는 방향이다.

### 2-6. ⚠️ "적 예상 탄착점 금지"(§58) vs "숫자로 학습"(§60)이 충돌한다

기획서는 탄착 보조선을 금지하면서, 동시에 "저 거리면 45도 파워 65"라는 학습이 쌓이길 원한다. **거리를 모르면 그 학습이 성립하지 않는다.**

**💡 절충: 거리계는 준다, 탄착점은 안 준다.**
- 조준 방향으로 레이캐스트 → 지면에 닿는 지점까지의 **수평거리·고도차**를 숫자로 표시 (`↔ 134m  ↕ -12m`)
- 이건 포트리스의 좌표 눈금에 대응하는 정보이고, 바람·탄도 계산은 여전히 플레이어 몫이다
- 금지 유지: 예상 탄착 마커, 전체 궤적선, 자동 보정선

**실험 5 — 듀크탱크 독구름을 장판으로**: 원작 독구름은 자리에 남아 지속 피해를 주는 구름인데 "맞은 유닛에 독"(Poison 35×3)으로 옮겨져 있었다 → 2번탄/판 0.9·승률 29%(꼴찌). `EffectType.PoisonCloud`(장판 40/턴 × 3턴, 반경 = 폭발 반경, `HazardField.PlaceFire` 와 같은 구조, 바람 흐름 미구현)로 바꾸고 그 행만 재측정(셀당 40판): **30%**(29%→30%, 오차 안), 2번탄/판 0.9→2.1, 장판 피해 63/판(네거티브 컨트롤 살아 있음). 구름은 원작대로 동작하지만 **꼴찌의 원인이 아니다** — 듀크는 평균 34턴(최장)으로 판을 끌다 진다. 다음 판별: 명중률·사격당 피해 열을 표에 추가해 "못 맞추는가 / 맞춰도 약한가"를 가른 뒤, 각도 상한 40°(언덕 너머 사격 불가 가설)를 단일 변수로 잰다.

#### 2-9-6. 🗺️ 맵 3종 실제 게임 연동 + Unity 6.6 업그레이드 + TwinHills 미러 편차의 정체 (2026-09-16)

**맵 통합**: 매치업 하네스(`BattleSimVerify.cs`)가 §2-9-4 까지 전부 임시 하네스 전용 언덕(22m·20m 가우시안)으로 쟀다 — 실제 게임은 §맵 3종(`MapHeightFunction.cs`, 기본 TwinHills)을 쓰므로 하네스 수치가 게임의 실제 승률과 다를 수 있었다. `TANKFALL_MAP=TwinHills(기본)|Crater|Terrace|Legacy` 환경변수로 게임과 같은 지형·스폰에 연결했고, `Legacy` 로 §2-9-4 수치를 정확히 재현함을 회귀 확인했다(듀크 30%/42%/명중46 그대로). **맵 3종 게이트(`verify.sh map`) 남아있던 실패 2건도 이번에 해결**: (1) Crater 스폰 높이 좌우 비대칭 — 디테일 리플 항이 `sin(x*k)`(x=100 기준 홀함수)였던 걸 `cos((x-100)*k)`(짝함수)로 바꿔 대칭 확보. (2) 저각 네거티브 컨트롤(옛 언덕이 40° 를 막아야 함)이 안 막히던 문제 — 원인은 좌표가 아니라 **물리**였다: 40°·최대파워 궤적의 상승 기울기(tan40°=0.839)가 이 가우시안 언덕의 최대 경사(≈0.628)보다 항상 커서 어떤 좌표를 골라도 기하학적으로 못 막힌다(해석·실측 확인). 근거리 조준을 흉내낸 저파워(0f) 샷으로 검사를 바로잡았다.

**Unity 에디터 6000.3.14f1 → 6000.6.0f1** (오너 지시 "최신버전으로"). csc.dll 경로가 버전마다 달라 `verify.sh` 가 둘 다 찾아보게 고쳤고, `UnityEngine.ScriptingModule` 참조를 추가(6000.6부터 `RuntimeInitializeOnLoadMethodAttribute` 가 이걸 끌어옴 — 안 걸으면 View 컴파일 실패). 동일 시드로 6000.3/6000.6 양쪽에서 매치업 수치가 바이트 단위로 같음을 확인 — Sim 레이어가 정말 에디터 내부에 안 기댐을 재확인.

**TwinHills 미러 편차(v5)의 정체 — 지형이 아니라 선공권**: 게임과 같은 맵으로 12×12 를 다시 재자(v5) 격차가 v4(29~77%)보다 커졌다(21~91%, 특히 레이저 90%·듀크 74%·캐터펄트 74%). 캐롯 전용 [6-1] 판별([6-1]: 순차/교대/B선공/스폰교환)은 "대칭"으로 나와 범용 판별로는 못 잡았다. 그래서 편차가 큰 레이저·듀크·캐터펄트 각각에 같은 판별을 [6-2]로 돌렸다:

| 기종(평균턴) | 순차 | 교대 A선공(현행) | 교대 B선공 | A선공+스폰교환 |
|---|---|---|---|---|
| 레이저(6턴) | 90% A유리 | 85% A유리 | **45% 대칭** | 90% A유리 |
| 캐터펄트(15턴) | 62% 대칭 | 80% A유리 | **37% 대칭** | 47% 대칭 |
| 듀크(34턴) | 42% 대칭 | 63% 대칭 | 33% B유리 | 50% 대칭 |

읽는 법(§2-9-1과 동일): **스폰 교환**에서 안 뒤집히고(레이저·캐터펄트 계속 A 유리) **B선공**에서 대칭으로 돌아오면 원인은 지형이 아니라 **선공권**이다. 정확히 이 패턴이 나왔다. 근본 원인: 실제 게임(`BattleDemo.cs`, §52)은 턴 순서 동률(전원 누적 지연 0에서 시작)을 등록 순서로 깨는데, 유닛 정렬이 항상 `Team` 오름차순(`(a.Id%3)*2+a.Team`)이라 **팀A가 항상 선공**이다 — 이건 버그가 아니라 §52 설계(플레이어=A팀 고정 선공)다. 그런데 매치업 하네스의 미러 측정(`Matchup()`)은 스폰 자리는 홀짝으로 상쇄하면서 **선공은 상쇄한 적이 없어서**, "미러=50%면 탱크 수치가 대칭"이라는 표의 전제에 선공 편중이 섞여 들어갔다. 판이 짧을수록(레이저 6턴) 선공 이점이 상쇄되기 전에 판이 끝나 미러가 크게 벌어진다는 가설이 확인됐다.

**조치**: 게임 코드(§52, 선공권 자체)는 설계대로 유지하고 건드리지 않았다. 대신 `Matchup()`의 미러/승률 측정만 스폰 교환과 별도로 **선공도 2판마다 교차**하도록 고쳤다(`RunMatch(... firstTeam: (m>>1)&1 ...)`) — "탱크 수치만의" 대칭성을 선공 효과와 분리해서 잰다. 재측정(v6, TwinHills, n=20/셀) 결과 미러 범위가 **21~91% → 41~60%대로 수렴**. **탱크 수치는 변경하지 않았다** — 편차의 정체가 측정 방식이었지 탱크나 맵이 아니었기 때문이다.

> ⚠️ **후속 정정(§2-9-8)**: 여기서 쓴 "선공 교차" 보정은 **3개 결투쌍 중 1쌍에만 걸린 반쪽짜리**였다(등록 인덱스를 한 칸 회전시키는 방식이라 나머지 두 쌍은 그대로 A 선공). 위 v6 수치에는 그만큼의 잔여 A 편향이 남아 있다. 세 쌍 전부에서 선공이 넘어가게 고친 뒤 12종 미러 평균은 **48.3%(±1.9%p)** 다 — 결론(원인=선공권, 탱크·맵 아님)은 그대로지만 **수치는 §2-9-8 쪽을 믿어라.**

#### 2-9-8. 🪜 난이도 사다리 검증 + **선공 대조군이 반쪽짜리였다**(두 번째 하네스 버그) (2026-09-16)

**난이도는 한 번도 "사다리인지" 검증된 적이 없었다.** 지금까지 난이도는 같은 값끼리만 재서(AI vs AI 대칭) "오차가 크면 판이 길어진다"만 알았지, **강한 난이도가 약한 난이도를 실제로 이기는지**는 잰 적이 없다 — 같은 난이도끼리는 당연히 50% 라 사다리 여부를 증명하지 못한다. `RunMatch` 에 팀별 조준 오차(`errorRatioB`)를 붙이고 `[6-3]` 라운드로빈을 추가했다(TwinHills, 캐롯 자기전).

| A \ B | 대조 0% | 에이스 0.75% | 상급 1.5% | 중급 2.5% | 초급 4.0% |
|---|---|---|---|---|---|
| 대조 0% | 55 | 70 | 80 | 100 | 100 |
| 에이스 0.75% | 50 | 75 | 85 | 100 | 100 |
| 상급 1.5% | 20 | 50 | 90 | 95 | 100 |
| 중급 2.5% | 0 | 15 | 30 | 55 | 90 |
| 초급 4.0% | 0 | 0 | 0 | 20 | 55 |

인접 칸이 전부 한 방향으로 정렬돼 **사다리는 성립한다**. ⚠️ 이는 §2-5 의 "AI 조준 오차는 난이도 손잡이로 쓸 수 없다 — 쓸 수 있는 폭이 0.7%p" 라는 결론이 **옛 맵에서만 참**이었음을 뜻한다. 게임이 쓰는 TwinHills 에서는 0.75~4.0% 전 구간이 매끄럽게 갈리므로 기획서 §67 의 난이도 사다리가 성립한다.

**그런데 대각선(같은 난이도끼리)이 50% 를 벗어나 있었다 — 파고 들어가니 하네스 버그였다.**
2×2(선공 × 스폰)로 갈라도 A 가 전 조건에서 이겼고, **조준 오차 0% 대조군에서조차 B선공인데 A 가 68% 이겼다**. 난수가 조준에 쓰이지 않는 조건이라 원인은 난수가 아니라 구조였다.
원인: `alternate` 교대 리스트(A0 B0 A1 B1 A2 B2)를 만든 뒤 "B선공"을 등록 인덱스 **한 칸 회전**(`(i+firstTeam)%6`)으로 만들었다. 그런데 조준 AI 는 가장 가까운 적을 쏘므로 같은 슬롯끼리 **1:1 결투 3쌍**이 된다(A0↔B0, A1↔B1, A2↔B2). 한 칸 회전은 **첫 쌍의 선공만 뒤집고 나머지 두 쌍은 그대로 A 가 먼저 쏜다** — 즉 3쌍 중 1쌍에만 걸린 반쪽짜리 대조군이었다. §2-9-6 의 "선공 교차" 보정도 그만큼만 들었다.
수정: 팀 순서 자체를 뒤집어(정렬 키의 `Team` → `1-Team`) 세 쌍 전부에서 선공이 넘어가게 했다. 결과 — 전 난이도에서 A선공/B선공의 **중간값이 정확히 50%** 가 됐다:

| 난이도 | A선공 | B선공 | 중간값 | 선공 가치 |
|---|---|---|---|---|
| 대조 0% | 72% | 28% | **50.0** | ±22%p |
| 에이스 0.75% | 72% | 27.5% | **49.8** | ±22%p |
| 상급 1.5% | 67% | 33% | **50.0** | ±17%p |
| 중급 2.5% | 59.5% | 40.5% | **50.0** | ±9.5%p |
| 초급 4.0% | 60.5% | 39.5% | **50.0** | ±10.5%p |

(각 칸 n=120, ±5%p) 읽기: **선공의 가치는 판이 짧을수록 커진다**(오차 0% 22%p → 중급 9.5%p). §2-9-6 의 가설("판이 짧은 기종일수록 미러가 벌어진다")이 난이도 축에서도 같은 모양으로 확인됐다.

**[6-2-1] 미러 게이트 신설.** 미러 칸은 셀당 20판이라 ±11%p 로 흔들려 한 칸만 보고는 "편향"과 "운"을 못 가른다 — 실제로 이 세션에서만 두 번 오진했다(처음엔 n=20 으로 "구조적 편향"이라 판단, 다음엔 0% 대조군 55% 를 보고 "깨끗하다"고 판단, 둘 다 틀렸다). 그래서 12종 전부를 매치업과 **똑같은 교차 패턴**으로 셀당 60판씩 재고 **평균**을 게이트로 건다. 현재: **12종 평균 48.3%(±1.9%p) ✅** — 매치업표를 탱크 비교로 읽어도 된다. 벗어나면 종료 코드 1 로 `verify.sh` 가 실패한다.

**게임에 난이도 선택을 붙였다.** 사다리가 검증됐는데 게임은 중급 하나로 하드코딩돼 있어 사다리가 닿지 않았다 — `-difficulty 초급|중급|상급|에이스`(영문 별칭 novice/normal/expert/ace 도 받음), 게임 중 **F1 로 순환**, HUD·개시 로그에 표시. `AiDifficulty` 는 캐시 없는 프로퍼티라 바꾸면 다음 AI 조준부터 바로 반영된다. 모르는 이름은 경고 후 중급으로 떨어진다(빌드 실행으로 확인). `AiGunner` 의 난이도 상수 주석도 옛 하네스 언덕 수치에서 **TwinHills 실측치로 갱신**했다.

⚠️ **오너 판단이 필요한 설계 질문**: 실제 게임(§52)은 팀A 가 항상 선공이고, 위 실측대로 중급 난이도에서 그 가치가 **약 ±10%p** 다(고수끼리 붙으면 ±22%p 까지 커진다). PvP 에서 한쪽이 고정으로 이 이점을 갖는 게 의도인지, 선공을 무작위·교대·혹은 보정(후공에게 딜레이 이득 등)으로 갈 것인지는 **수치가 아니라 규칙 결정**이라 손대지 않았다.

#### 2-9-9. 🎯 연습장 구현 (§68) (2026-09-16)

오너 지시로 **밸런스는 멈추고 미구현 기능부터** 만든다. M4 목록의 연습장(§68)을 구현했다.

**설계**: 전투와 같은 탄도·지형·바람을 쓰되 세 가지가 다르다 — 적이 **반격하지 않고**, 표적이 **되살아나며**, 턴이 **항상 플레이어에게 돌아온다**. 서든데스·승패 판정도 돌지 않는다. 연습장은 이기는 곳이 아니라 같은 일을 반복해 §1("포격 감각이 실력을 결정한다")을 몸에 붙이는 곳이기 때문이다. 매 발 바람이 새로 불고, **표적은 매 발 자리를 옮긴다**. 지형 파괴는 그대로 남긴다(전투와 같은 전장에서 연습해야 감각이 옮겨간다).
**HUD**: 명중/발수·명중률·이번 오차·최고 오차. `-practice` 로 진입.
**"정답 보기"(F2)**: §5-7 역산으로 지금 바람·지형에서 표적을 맞히는 각도·파워·야우를 보여준다. ⚠️ 기획서 §58 에 따라 **PvP 에는 절대 노출 금지**라 호출부가 `_practice` 로 잠겨 있다 — 이 조건을 풀지 마라.

**자체검사(`-practiceselftest`)** — 사람 입력이 필요한 모드라 이게 없으면 자동 검증이 불가능하다. 정답 보기가 낸 해로 자동 발사해 채점까지 돌린다(정답 기능의 네거티브 컨트롤: 정답대로 쐈는데 안 맞으면 역산이나 채점이 고장난 것이다). 현재 **검증통과 해 19~20/20발 100% 명중, 최소 오차 0.00m ✅**.
⚠️ 게이트는 전체 명중률이 아니라 **"검증통과라고 말한 해"의 명중률**이다. 지형·각도 범위 때문에 애초에 해가 없는 배치도 나오는데(폴백), 그걸 못 맞혔다고 역산이 틀린 건 아니다 — 주장한 것만 재야 거짓말이 안 된다.

**구현하며 잡은 버그 넷** (전부 자체검사가 잡았다):
1. **야우 규약**: `FireFrom` 의 turretYaw 는 차체 기준 **상대각**(worldYaw = Heading + turretYaw)인데 역산이 주는 월드 야우를 그대로 넘겨 20발 전부 엉뚱한 데로 날아갔다.
2. **§5-7 5단계 누락**: "두 해를 시뮬해서 지형에 안 막히는 쪽을 택한다"를 빼먹어 막힌 저각 해를 "정답"이라고 내놨다(명중률 75%).
3. **허용 오차가 폭발 반경**이었다: 5m 씩 빗나간 해도 정답으로 통과시켰다 → **탱크 반경**으로 조였다.
4. **표적이 제자리 부활**: 같은 곳을 계속 쏘니 크레이터가 깊어져 표적이 구덩이에 잠겼고, 캐롯(0~40°)으로는 닿지 않는 자리가 됐다 → 매 발 재배치.
5. **채점 시점**: 턴이 넘어간 뒤에 쟀더니 포탄이 판 크레이터로 표적이 떨어진 거리까지 오차로 세어 5m 씩 부풀었다 → **착탄 순간**(지형이 깎이기 전)에 확정하도록 바꿨다.

빨간불도 확인했다 — 획득 경로를 강제로 막고 다시 빌드하니 `❌ 600프레임 걸어도 못 주웠다`, **rc=1**. 통과가 공짜가 아님을 확인한 뒤에 초록불을 믿었다.

#### 2-9-14. 🌀 화면 방해·조작 봉인 탄 6종 + 눈이 불을 끈다 (2026-09-17)

**출처**: <https://namu.wiki/w/포트리스2/아이템>, <https://namu.wiki/w/포트리스2> (2026-09-17 조회). 코드 머리말(`Sim/Impair.cs`)에도 남겼다. §2-9-10 에서 "렌더링이 있어야 말이 된다"며 보류했던 것들인데, 오너 지시("게임 먼저 다 만들어")로 렌더링까지 만들었다. **지속 턴은 [추정]이 아니라 원작 값이다.**

| 탄 | 원작 서술 | 지속 | 턴 소모 |
|---|---|---|---|
| 반전탄 | "화면이 상하로 뒤집힌다" | 3턴 | O |
| 멀미탄 | "화면이 물결치듯이 울렁거린다" | 4턴 | O |
| 안개탄 | "안개가 껴서 고립된다" | 3턴 | O |
| 바보탄 | "모든 탱이 자기 자신의 탱+아이디로 보이며 자신의 턴이 와도 화면이 자신의 위치로 오지 않는다" | 4턴 | O |
| 각도고정탄 | "각도를 조절할 수 없다" | 3턴 | O |
| 파워고정탄 | "50% 이하의 힘으로 발사할 수 없게 된다" | 3턴 | O |

**구현**: 쏴서 **맞은 적에게** 건다(원작이 '탄'이다). 반전=카메라 롤 180°, 멀미=카메라 흔들기, 안개=화면 흰 덮개 + **적 탱크 렌더러만 끔**(원작 기후 안개: "자신과 팀원을 제외한 탱들의 모습은 볼 수 없고 단지 포탄이 날아오는 것만 볼 수 있게 된다"), 바보=자기 턴에도 카메라가 엉뚱한 탱크에 머문다. 각도고정은 상하 조절만 막고 좌우 회전은 둔다(원문이 '각도'만 말한다). 파워고정은 발사 직전에 하한을 건다.

**⚠️ 정직하게 적어둔 한계 — 앞의 넷은 AI 에게 효과가 0 이다.** AI 에게는 화면이 없다. 그런데 원작에서 이 탄들은 **턴을 소모**하므로 AI 가 AI 에게 쓰면 순손해다. 그래서 AI 정책은 **"사람이 표적일 때만 쓴다"** [추정] — 매치업 하네스(AI 대 AI)에서 이 넷이 안 나오는 건 **죽은 시스템이 아니라 의도된 정책**이고, 값어치는 하네스가 아니라 실제 게임에서만 판정된다. 코드가 이 구분을 강제한다(`Impair.IsScreenOnly`). 반대로 **각도·파워 고정은 조준을 묶으므로 AI 에게도 진짜 효과가 있어** 하네스가 잰다 — 매치업표 `방해` 열 실측 **0.7 적중/판**(12×12 전체표).

**네거티브 컨트롤 `-impairselftest`**: 6종 각각에 대해 ① 원작 지속 턴이 그대로 들어갔는지 ② **화면이 실제로 달라지는지**(카메라 회전이 변하는가, 안개가 적 렌더러를 끄고 풀리면 되돌아오는가, 바보탄이 카메라를 내 자리에서 떼어놓는가) ③ 수명이 다하면 풀리는지를 재고 실패 시 **rc=1**. "상태가 켜졌다"로 끝내면 선언만 하고 죽은 값이 되기 때문에 **화면 변화까지** 재는 게 핵심이다. 빨간불도 확인했다 — 반전 적용 줄을 지우고 다시 빌드하니 `❌ 반전탄: 카메라가 그대로다`, rc=1.

**같이 구현한 원작 규칙 — 눈이 불·독가스를 끈다**: "눈이 내리면 포세이돈의 파워가 증폭되며, **카터펄트의 불과 듀크탱크의 독가스는 사라진다**"(<https://namu.wiki/w/포트리스2>). 포세이돈 보정만 있고 이 절반은 구현돼 있지 않았다. 눈으로 바뀌는 순간 기존 장판을 지우고, 눈 오는 동안은 새로 놓지도 않는다. 게임·하네스 양쪽에 같이 넣었다(눈내리기 아이템 경로 포함).

#### 2-9-15. 🌪 기후 — 증폭벽·회오리 (2026-09-17)

**출처**: <https://namu.wiki/w/포트리스2> (2026-09-17 조회). 코드 머리말(`Sim/AirFeatures.cs`)에도 남겼다.

| 기후 | 원작 서술 |
|---|---|
| 증폭벽 | "포탄이 이 증폭벽을 지나가면 포탄에 별똥이 생긴다. 이 별똥이 생긴 포탄은 **대미지가 50% 증폭**된다." |
| 회오리 | "포탄이 이 회오리에 걸리면 나선형으로 휘말려 올라가다가 포탄이 화면 위까지 넘어가면 **높이 뜨다가 떨어진다**." |

배율 1.5 는 원작 값이고, **위치·크기·발생 확률은 원문에 없어 전부 [추정]**이다(`AirField` 상수에 모아뒀다). 한쪽 진영에만 생기면 그게 곧 진영 유불리라, 맵 한가운데 띠(양 팀 사이)에만 둔다.

**⚠️ 회오리를 닫힌 해와 어떻게 화해시켰나.** 이 게임의 궤적은 닫힌 해다(§5-4). 회오리가 비행 중에 힘을 더하면 닫힌 해가 깨지고 §5-7 조준 역산까지 같이 무너진다. 그래서 원작 서술("빨려 올라갔다가 떨어진다")을 그대로 **두 토막의 닫힌 해**로 풀었다 — 기둥에 걸린 지점에서 한 번 끊고, 꼭대기에서 수평 속도를 거의 죽인 채 **다시 쏜 것처럼** 이어 붙인다. 그림은 원작과 같고 계산은 닫힌 해로 남는다. 꼭대기(62m [추정])보다 높이 나는 탄은 안 걸린다 — 원작의 "고각샷으로 회오리를 넘긴다"가 그대로 성립한다.

**연출**: 증폭벽은 노란 반투명 판, 회오리는 도는 파란 기둥. **보이지 않으면 피할 수도 노릴 수도 없어서 규칙만 있고 죽은 값이 된다** — 그래서 연출을 같이 넣었다.

**네거티브 컨트롤 ①** — 매치업표에 `증폭`·`회오리` 열. 12×12 전체표 실측 **증폭 0.4~0.5 / 회오리 0.4~0.8 (판당)**, 0 이 아니다. (⚠️ 단일 행 실험에서 잠깐 증폭 2.6 이 나왔는데 그건 한 기종·다른 시드의 값이다 — 표에 적는 수는 전체표 값이다.) `TANKFALL_CLIMATE=0` 으로 끄고 도입 전과 비교할 수 있다.

**네거티브 컨트롤 ②** — 게임 빌드 `-climateselftest`. **같은 사격을 기후 켠 채 / 끈 채 나란히** 쏴서 비교한다:

```
기후 자체검사 증폭벽 — 통과 시 피해 ×1.5 (안 지나면 ×1)
기후 자체검사 회오리 — 착탄이 98m 밀려 회오리에서 13m 지점에 떨어짐
✅ 기후(§2-9-15) — 증폭벽·회오리가 실제로 탄에 작용한다
```

회오리는 "휘말렸다"는 플래그만 보지 않고 **착탄점이 원래 자리에서 밀렸는지 + 회오리 근처에 떨어졌는지**까지 잰다. 플래그만 보면 "켜졌는데 궤적은 그대로"를 통과시킨다.

#### 2-9-16. 💥 Boom 모드 — 지뢰밭·지진·유성 (2026-09-17)

**출처**: <https://namu.wiki/w/포트리스2> (2026-09-17 조회). 코드 머리말(`Sim/BoomMode.cs`)에도 남겼다.

| 요소 | 원작 서술 |
|---|---|
| 지뢰밭 | "곳곳에 마인랜더의 지뢰가 드문드문 깔린 상태로 게임이 시작된다." |
| 지진 | "턴이 시작되기 전에 확률적으로 지진이 일어난다. 지진이 일어나면 **각이 랜덤하게 변하고 탱의 위치가 미세하게 이동**된다." |
| 유성 | "턴이 시작되기 전에 확률적으로 **플레이어 중 한 명의 탱이 있는 곳과 그 근처**에 메테오가 떨어진다." |

확률·개수·세기는 원문에 없어 전부 `[추정]`이고 `BoomMode` 상수에 모아뒀다(지진 12%, 유성 10%, 지뢰 14발, 유성 3발). 셋 다 **이미 도는 시스템의 재사용**이다 — 지뢰밭=`HazardField.PlaceMine`, 지진=유닛 좌표·포각 흔들기, 유성=**착탄 처리와 같은 경로**(굴착 → 천장 붕괴 → 메시 갱신 → 피해). 유성을 따로 만들면 지형만 파이고 피해가 안 들어가는 반쪽이 되기 쉬워서 일부러 같은 경로를 쓴다.

**Sim 이 무엇을 하고 안 하는가**: `BoomMode` 는 **무엇이 어디서 일어나는지만** 정해 돌려주고, 굴착·피해 적용은 호출부가 한다 — Sim 은 `SdfDeformer` 를 쥐지 않고 UnityEngine 도 못 본다(asmdef §4-1). 그래서 게임과 하네스가 같은 규칙·같은 확률을 쓰면서도 구조 규칙이 깨지지 않는다.

**실행**: `-boom` 으로 켠다(모드라서 기본은 꺼짐). 매치업 하네스는 기본 측정을 흐리지 않도록 지금은 게임 전용이다 — 규칙이 `Sim/` 에 있으므로 밸런스 단계에서 하네스가 그대로 가져다 쓰면 된다.

**네거티브 컨트롤 `-boomselftest`**: 지진·유성은 확률이라 한 번 불러선 안 나온다 — **나올 때까지 돌려서 효과를 잰다**(끝내 안 나오면 그것도 실패다). 상태 플래그가 아니라 **실제 변화**를 본다:

```
Boom 자체검사 지뢰밭 — 14발 매설 확인
Boom 자체검사 지진 — 최대 이동 2.40m, 각 변화 4.7°
Boom 자체검사 유성 — 팀 전체 체력 5609 → 5445, 삼각형 414466 → 422544
✅ Boom 모드(§2-9-16) — 지뢰밭·지진·유성 전부 동작한다
```

#### 2-9-17. 🎯 탱크 고르기 — 13종을 다 만들어 놓고 셋만 쓰고 있었다 (2026-09-17)

오너 질문("탱크 다 만들었어?")에 답하려고 코드를 확인하다 나왔다. **수치·2번탄·다탄두 패턴·외형·색·궁극기는 13종 전부 있었는데, 게임은 늘 캐논·캐롯·레이저 셋만 세우고 있었다** — 나머지 열 종은 매치업 하네스에서만 돌던 셈이다. 고르는 화면이 없고 `-roster` 명령줄 인자뿐이었다. 원작 목록과 대조한 결과 13종 구성 자체는 정확히 맞다(<https://namu.wiki/w/포트리스2/등장탱크>, 2026-09-17 조회).

**만든 것**: 전투 시작 전 고르기 화면(12종 버튼 · 되돌리기 · 랜덤 3종 · 시작). 고르면 지형·날씨는 그대로 두고 탱크만 다시 세운다.

**⚠️ 슈퍼탱크 — 근거 없는 주석을 정정한다.** 코드에 "원작: 랜덤에서만 낮은 확률로 등장이라 선택 불가"라고 적혀 있었는데 **조사로 확인되지 않았다** — namu.wiki 포트리스2 문서와 등장탱크 문서 둘 다 슈퍼탱크 서술이 없고, 별도 문서 링크만 있다. 그러니 `Hidden` 취급과 확률 6% 는 원작이 아니라 `[추정]`이다. 확실한 건 하나뿐 — **그대로 두면 한 판도 안 나오는 죽은 탱크**라서 랜덤 뽑기 경로라도 열어뒀다.

**같이 정정한 낡은 주석 4곳**: 탱크 표에 "설치물 미구현"(마인랜더)·"멀티샷 미구현"(멀티미사일)·"수직 낙하 미구현"(이온어태커)·"이동금지 미구현"(포세이돈)이 남아 있었는데 **전부 지금은 동작한다**.

**🚨 그리고 이 검사를 만들다 내가 낸 사고 하나** — `-rosterselftest` 를 추가했더니 **빌드는 성공하는데 검사가 영영 안 끝났다**. 고르기 화면을 띄울지 판정하는 조건이 `!_autoShot && !_gallery && !_perf && !_supplySelfTest && ...` 처럼 **모드를 하나하나 나열**하고 있었고, 새 모드를 거기 빼먹어서 자체검사가 고르기 화면에 갇혔다. 모드가 늘 때마다 재발할 조건이라 목록을 없애고 **플래그 하나**(`_autoMode`, 사람 없는 모드는 인자 파싱에서 켠다)로 바꿨다 — 앞으로 모드를 추가해도 이 줄은 손댈 일이 없다.

**네거티브 컨트롤 `-rosterselftest`**: "표에 줄이 있다"와 "게임에 세울 수 있다"는 다르다. 13종을 실제로 스폰해 **기종·체력·외형 메시 수·2번탄 이름과 발수·궁극기**가 다 붙는지 재고 하나라도 어긋나면 rc=1.

```
로스터 자체검사 캐터펄트  체  950 · 메시 8 · 2번탄 화염바위×1 · 궁 지진
…
로스터 자체검사 슈퍼탱크  체 1000 · 메시 8 · 2번탄 구연유도×9 · 궁 벙커
✅ 원작 13종 전부 게임에 세울 수 있다(수치·외형·2번탄·궁극기)
```

#### 2-9-13. 🚨 미러 게이트의 표준오차가 거짓말이었다 (2026-09-17)

보급(§2-9-11)을 켠 뒤 `[6-2-1]` 미러 게이트가 43.2% 로 떨어졌다. **"보급이 진영 대칭을 깼다"고 결론 낼 뻔했다.** 원인 단정 전에 판별부터 했다 — 먼저 스위치로 범인을 좁히고(아이템 OFF 49.6% / 아이템만 ON 49.4% / 보급까지 ON 43.2%), 팀별로 분해하니 **획득 A 0.23 : B 0.20, 주우러 간 턴 A 1.20 : B 1.32 로 접근 기회는 대칭**이었다. 여기서 "범인이 보급인데 기회는 대칭"이라는 모순이 나왔으므로 시드를 바꿔 다시 쟀다:

| 시드 | 기종별 시드 분리 **전** | 분리 **후** |
|---|---|---|
| +0 | 44.9% ❌ | 51.7% ✅ |
| +7 | 54.2% | 50.8% ✅ |
| +13 | 45.7% | 49.7% ✅ |
| +29 | 49.6% | 53.1% ✅ |
| **표준편차** | **4.2%p** | **1.5%p** |

**진짜 원인은 게이트 자신이었다.** 12종 전부에게 같은 시드열(`1000 + m*77`)을 먹이고 있어서, 같은 바람·같은 나이스샷·같은 투하가 12종에 통째로 걸렸다. 720판이 서로 독립이 아닌데 표준오차는 독립인 양 √720 으로 계산했다 — **±1.9%p 라고 주장하면서 실제로는 ±4%p 로 흔들렸다.** 기종마다 시드열을 떼어놓자(`+ (kind+1)*9973`) 12개가 진짜 독립 표본이 되어 네 시드 전부 50% 근방으로 모였고 식과 실측이 맞았다. **보급은 무죄.**

**교훈**: 이 프로젝트에서 표본을 과신해 오진한 게 세 번째인데, 앞의 둘은 "표본이 작았다"였고 이번은 **"오차 추정 공식이 데이터의 구조와 안 맞았다"** 였다. 게이트가 내놓는 ±값은 가정(독립)이 성립할 때만 참이다 — **게이트를 새로 만들면 시드를 흔들어 그 ±가 진짜인지 먼저 확인할 것**. 그래서 `TANKFALL_SEED=<n>` 손잡이를 상설로 남겼다.

**절차 사고도 같이 기록한다**: 보급 커밋(a247b6d9)을 `TANKFALL_ROW=Carrot` 으로만 돌려 "전체 통과"라고 보고했는데, **행 필터를 걸면 미러 게이트가 건너뛰어진다.** 기능 커밋은 반드시 필터 없는 `verify.sh battle` 로 한 번 돌린다.

## 5. 탄도 계산식 (확정)

### 5-1. 상수

| 기호 | 값 | 근거 |
|---|---|---|
| `g` | **30.0 m/s²** | 현실 3배. 탄도를 굽혀 포트리스 감각을 만들고 비행시간을 3~4초로 줄인다(템포) |
| `v_min` | **25.0 m/s** | 파워 0에서의 초기속도 → 45°에서 사거리 21m |
| `v_max` | **81.2 m/s** | 파워 100, 45°에서 **사거리 220m** 목표 역산: `v = √(R·g) = √(220×30)` |
| `k_wind` | **0.35** | 바람 1당 최대사거리 사격에서 **≈2.6m** 편차 |
| `W` | 0.0 ~ 10.0 | 바람 세기. **수평 2성분만** (Y=0, §5-3) |
| 맵 크기 | 200m × 200m | 최대사거리 220m < 대각선 283m → 위치 선정이 의미를 가진다 |

> ⚠️ **미측정**: 위 값은 전부 산술 설계값이다. M1 게이트(§11)에서 실제 플레이로 재조정해야 한다. 특히 `g=30`은 체감이 "너무 무겁다"고 나올 가능성이 있다(대안: 25).

**검증(계산)**: 파워 100 · 45°
```
v0 = 81.2 m/s   사거리 220m   비행시간 3.83s   정점 고도 55m
```
비행 3.8초는 §18 포탄 카메라 3단 연출(발사→추적→착탄)에 딱 맞는 길이다.

### 5-2. 파워 → 초기속도 💡 **제곱근 매핑을 쓴다**

사거리는 `R = v₀²/g`로 속도의 **제곱**에 비례한다. 선형 매핑(`v₀ = lerp(v_min, v_max, p)`)을 쓰면 "파워 50 = 사거리 절반"이 성립하지 않아 학습이 어렵다.

```csharp
// power: 0..1
float v0 = Mathf.Sqrt(vMin*vMin + (vMax*vMax - vMin*vMin) * power);
```

이러면 **사거리가 파워에 정확히 선형**이 된다(계산 확인: power 0.5 → 120.4m = 21 + (220−21)×0.5). 플레이어가 쌓는 "이 거리엔 파워 60" 감각이 선형이라 학습 곡선이 훨씬 빠르다.

### 5-3. 가속도 벡터

```
a = (k_wind · W · Wx · weapon.WindScale,   −g · weapon.GravityScale,   k_wind · W · Wz · weapon.WindScale)
```
- 바람은 **수평 전용**. 수직 바람은 직관을 파괴하므로 금지(기획서 §14의 "3D 360도"는 수평 360도로 해석).
- `a`는 비행 중 **상수**다. 이게 §5-4 전체를 가능하게 한다.

### 5-4. 궤적 — 닫힌 해

```
P(t) = P₀ + V₀·t + ½·a·t²
V(t) = V₀ + a·t
```

적분 없음. 임의의 `t`에 O(1)로 위치를 얻는다.

```csharp
public static Vector3 PositionAt(in BallisticState s, float t)
    => s.P0 + s.V0 * t + 0.5f * t * t * s.Accel;
```

**이 함수 하나를 서버·클라 프리뷰·AI·리플레이·킬캠이 전부 쓴다.** 결정론이 구조적으로 보장된다.

### 5-5. 충돌 판정

궤적이 닫힌 해라도 **충돌은 이산 검사**가 필요하다.

```
고정 스텝 Δ = 1/120 s 로 t를 전진 (프레임레이트 무관)
각 세그먼트 [P(t), P(t+Δ)] 에 대해:
  1) 탱크: 세그먼트 vs 캡슐 최단거리 < 캡슐반경 → 직격
  2) 프롭: Physics.Linecast (프롭만 콜라이더를 가진다)
  3) 지형: SdfVolume.SampleWorld(P(t)) 의 부호가 양(공기)→음(땅)으로 바뀌면 교차
           → 이분 탐색 8회로 교차 t 정밀화 (오차 < 1cm)
           ⚠️ 오버행·동굴이 있으므로 "포탄이 지면 아래로 내려갔다"는 판정은 못 쓴다.
              부호 변화만이 유일한 기준이다 — 동굴 안으로 쏘아 넣는 사격이 성립한다.
  4) 맵 밖 / t > 15s → 불발 처리
```

⚠️ **함정**: 세그먼트가 얇은 능선이나 **처마**를 뛰어넘을 수 있다. 세그먼트 길이(v=81m/s, Δ=1/120 → 0.68m)가 복셀(0.5m)보다 크다. → **세그먼트를 복셀 크기로 재분할**해서 검사한다(`ceil(len / voxel)` 등분).

### 5-6. 유도 미사일 예외 (§45)

유도탄만 닫힌 해가 아니다. **고정 스텝 적분**으로 결정론을 유지한다:

```
t < 0.6·T_예상  →  일반 탄도
t ≥ 0.6·T_예상  →  a += normalize(target − P(t)) · guideAccel   (guideAccel ≤ 8 m/s²)
```
턴제라 표적이 움직이지 않으므로 목표점은 발사 시점에 고정된다 → 재현 가능.
`ProjectileSimulator`는 `Mode { Analytic, Integrated }` 두 경로를 갖는다.

### 5-7. 조준 역산 (AI · 연습장 보조)

목표점까지 필요한 발사각을 구한다. **바람이 있어도 해석적으로 풀린다** — 이게 §5-3(가속도 상수)의 배당금이다.

> **핵심 트릭**: 가속도 `a`는 상수 벡터다. `a` 방향을 "아래"로 삼는 회전 좌표계에서는 바람이 사라지고 **중력 `G = |a|` 하나만 있는 표준 포물선**이 된다.

```
1) G = |a|,  down̂ = a/G
2) 목표 상대위치 d = target − P₀ 를 회전 좌표계로 변환
      y = −dot(d, down̂)                   (유효 "위" 방향 성분)
      x = |d − dot(d,down̂)·down̂|          (유효 수평 거리)
3) 표준 해:
      판별식 D = v⁴ − G·(G·x² + 2·y·v²)
      D < 0  →  해 없음 (사거리 부족 → 파워를 올려라)
      tanθ = (v² ± √D) / (G·x)
      → 저각 해(−)와 고각 해(+) 두 개
4) 두 해를 역회전해 월드 방향으로 되돌린다
5) 각 해로 ProjectileSimulator를 돌려 지형에 막히지 않는 쪽을 택한다
   (둘 다 막히면 고각 해 우선 — 산 넘기기)
```

**용도**: AI 조준(§10) · 연습장 "정답 보기" · 밸런스 검증 하네스.
**⚠️ PvP HUD에는 절대 노출 금지** (기획서 §58).

> ⚠️ **각도만 보정하고 야우를 목표 방향으로 두면 안 된다** (실측으로 잡은 버그).
> 옆바람이면 **바람 반대로 틀어 쏘는 성분**이 필요한데, 피치만 보정하면 그게 통째로 빠져 7~28m 빗나간다.
> 유효 좌표계에서 각을 푼 뒤 **발사 방향을 벡터로 역회전**해서 월드 야우·피치를 함께 뽑아야 한다.
>
> **실측 (`tools/BallisticsVerify.cs`, 오차 0으로 조준)**
>
> | | 목표와 거리 3m 이내 |
> |---|---|
> | 피치만 보정(버그) | 24개 중 **8개** |
> | 벡터 역회전(수정) | 24개 중 **24개** (전부 1.2~1.7m) |
>
> 평지·언덕 × 40/80/120/160m × 바람 없음/→6/↖6.4 조합. 네거티브 컨트롤로 ±5° 틀어 쏘면 20~24m 빗나간다.

**바람 편차 실측** — 이론치와 정확히 일치한다:

| 바람 | 실측 편차 | ½·a·t² 이론 |
|---|---|---|
| 1 | 1.9m | 1.9m |
| 5 | 9.6m | 9.6m |
| 10 | 19.1m | 19.2m |

**사거리 실측** (45°, 바람 0): 파워 25→73m · 50→122m · 75→172m. 제곱근 매핑(§5-2)대로 파워에 선형이다.

## 6. 피해 계산 (확정)

### 6-1. 감쇠 곡선

```csharp
// d: 폭발 중심 ~ 탱크 중심 거리,  R: weapon.ExplosionRadius
float inner = R * 0.21f;                       // 평탄 코어
float t = Mathf.Clamp01((d - inner) / (R - inner));
float falloff = Mathf.Pow(1f - t, 1.3f);
float dmg = weapon.BaseDamage * falloff;
```

**검증(계산, R=7m·Base=300)**

| 거리 | 이 공식 | 기획서 §39 표 | 오차 |
|---|---|---|---|
| 0m | 300 | 300 | 0 |
| 2m | 263 | 250 | +5% |
| 4m | 135 | 150 | −10% |
| 6m | 32 | 40 | −20% |
| 7m | 0 | 0 | 0 |

기획서 의도를 한 줄 공식으로 재현했다. 무기별로 `ExplosionRadius`·`BaseDamage`만 데이터로 두고 `0.21`·`1.3`은 전역 상수로 고정한다(무기마다 곡선 모양이 다르면 플레이어가 학습할 수 없다).

### 6-2. 직격 · 방향

```
최종 = (폭발피해 + 직격피해) × 방향계수 × (1 − 경감)
방향계수: 전면 1.00 / 측면 1.05 / 후면 1.15     ← 포탑 기준 아님, 차체 전방 기준
직격피해: 포탄이 탱크 캡슐에 직접 맞은 경우만 weapon.DirectDamage 가산
```

### 6-3. 낙하 피해

```
fallDamage = clamp((fallHeight − 3m) × 12, 0, 240)
```
3m까지 무피해, 최대 240(HP의 24~30%). 기획서 §27 "즉사 수준으로 만들지 않는다"를 상한으로 강제.

## 7. 지형 시스템 — SDF 볼륨 + Surface Nets

> **"코드로 그린다"**: 유니티 Terrain도, 미리 만든 지형 메시 에셋도 없다. SDF에서 메시를 매번 생성한다.
> 구현·검증 완료 — `projects/tank-artillery/Sim/`, 하네스 `tools/SdfVerify.cs`.

### 7-1. 자료 구조 — 하이브리드 희소

SDF 규약: **양수 = 공기 · 음수 = 땅 · 0 = 표면**.

| 항목 | 값 | 비고 |
|---|---|---|
| 맵 | 200 × 200m, 높이 −20~80m | |
| **복셀** | **0.5m** | 소형탄(Rc=3m)이 6복셀 반경 — 크레이터가 구형으로 읽히는 하한 |
| **청크** | **16³ 복셀 = 8m 큐브** | 폭발 dirty 범위와 메시 재생성 단위 |
| 저장 | `Dictionary<청크키, float[4096]>` | **파괴된 청크만 할당** |

⚠️ **전체 복셀화는 하지 않는다.** 200×100×200m를 0.5m로 깔면 32M 복셀 = 128MB다. 대신:

```
파괴 안 된 곳  →  기본 지형 함수 h(x,z)로 즉석 평가          → 메모리 0
파괴된 곳만    →  그 청크를 함수값으로 채워 할당(copy-on-write) 후 수정
```

**실측: 초기 지형 SDF 메모리 0 KB. 폭발 100회 후 10.4 MB(667청크).**

### 7-2. 메시 생성 — Surface Nets

마칭 큐브 대신 Surface Nets(듀얼 컨투어링 단순형)를 쓴다:
- 셀당 정점 1개 → 삼각형이 마칭 큐브의 약 절반
- 256케이스 테이블이 없다(구현·검증이 짧다)
- 쿼드 격자라 균일해서 변형 후에도 셰이딩이 튀지 않는다

청크를 **1셀 겹쳐** 생성하면 이음매가 없다(SDF 샘플이 전역이라 가능).

⚠️ **로컬 SDF 캐시가 필수다.** 청크 빌드에서 `SdfVolume.Sample`을 직접 부르면 같은 코너를 최대 8번 조회하고 매번 딕셔너리 탐색 + FloorDiv/Mod를 거친다. 18³ 배열에 한 번만 캐시하면:

| | 캐시 전 | 캐시 후 |
|---|---|---|
| 초기 지형 전체 | 1,137 ms | **411 ms** |
| 폭발 1회(일반탄) | 16.63 ms | **7.94 ms** |
| 폭발 1회(굴착탄) | 136.96 ms | **42.69 ms** |

### 7-3. 폭발 — 구 빼기(CSG subtract)

```
sdf' = max(sdf, R − |p − c|)
```
구 안쪽에서 `R − |p−c| > 0` → 공기가 된다. Heightfield의 "컬럼 누르기"와 달리 **진짜 구형**이라 위쪽 흙이 남는다.

건드린 격자 범위(`DirtyBounds`)를 반환하고, **그 범위와 겹치는 청크만** 메시를 다시 만든다.

### 7-5. ✅ 지형 콜라이더를 만들지 않는다 (SDF에서 더 강해진 판단)

Heightfield 때의 결론이 SDF에서 **오히려 더 유리**해졌다 — SDF는 거리를 직접 주므로 충돌 판정이 더 싸다.

| 용도 | 방법 |
|---|---|
| 포탄 vs 지형 | `SampleWorld()` 부호 변화 |
| 탱크 접지 | `SurfacesAlongColumn()` 의 최상단 표면 |
| 조준 거리계 / AI 시야 | SDF 레이마칭(스피어 트레이싱 — SDF의 본래 용도라 빠르다) |
| 프롭 충돌 | 프롭 자체 콜라이더 (지형과 무관) |

콜라이더가 없으니 메시 재생성이 GPU 버퍼 갱신으로만 끝난다. SIM 레이어가 유니티 물리에서 완전히 독립해 헤드리스 서버가 그대로 돈다.

### 7-6. ✅ SDF가 새로 만든 문제 3개 — **전부 해결·검증됨** (2026-09-15)

Heightfield에는 없던 문제였다. 구현 + 실측 완료 — 하네스 `tools/GameplayVerify.cs`.

#### (1) 부유 덩어리 — SDF에는 중력이 없다 ✅

천장을 옆으로 파면 지지 없는 흙덩이가 공중에 그대로 뜬다.

**해법: 얇은 흙 층은 무너진다** (`CeilingCollapse.cs`, 임계 **1.0m**). 연결성 플러드필보다 훨씬 싸고, **플레이어가 예측할 수 있다** — "한 발 더 때리면 천장이 뚫린다".

| 천장 두께 | 결과 | 기대 |
|---|---|---|
| 0.78m | 표면 교차 3→**1** (붕괴) | ✅ |
| 0.92m | 표면 교차 3→**1** (붕괴) | ✅ |
| 1.42m | 3→3 (유지) | ✅ |
| 2.40m / 4.44m | 3→3 (유지) | ✅ |

실전 시나리오(지하 터널 3발 → 천장 0.78m): 붕괴 패스 **0.42 ms**, dirty 범위를 25×2×9 복셀 넓힘.

> ⚠️ **두께를 복셀 개수로 재지 마라** (실측으로 잡은 버그). 0.78m 천장이 격자 경계에 걸치면 땅 복셀 2개를 차지해 "2칸 = 1.0m"로 잡히고, 임계 미만인데도 안 무너진다. **표면 위치를 선형보간**해서 재야 한다.
>
> ⚠️ 이 패스는 폭발 직후 **항상** 돌려야 한다. 빠뜨리면 공중에 흙이 뜬 채로 남는다. 반환된 dirty 범위를 폭발 범위와 `Union`해서 메시를 다시 만든다.

#### (2) 탱크 갇힘 ✅

구 빼기 크레이터 벽은 수직이거나 오버행이다(Heightfield는 72°라 안식각으로 눕힐 수 있었지만, SDF는 볼륨이라 같은 수법을 못 쓴다).

**해법: 지형이 아니라 이동 규칙으로 푼다** (`TankGroundProbe.cs`) — **턱 넘기 1.2m**(차체 높이 절반).

| Rc | 크레이터 깊이 | 밖까지 걸어나가기 |
|---|---|---|
| 2m | 1.60m | ✅ 탈출 |
| 3m | 2.57m | ✅ 탈출 |
| 5m | 4.53m | ✅ 탈출 |
| 7m (일반탄) | 6.48m | ✅ 탈출 |
| 10m (대형) | 9.44m | ✅ 탈출 |
| **14m (굴착탄급)** | 13.41m | ⚠️ **갇힘** |

일반 화력으로는 안 갇히고, **굴착탄급으로 정확히 노려야 가둘 수 있다**. 의도한 난이도다 — 갇힘을 버그가 아니라 **"적을 구덩이에 가두기"라는 새 전술**로 승격시킨다.

> ⚠️ **걸음 크기가 등반 가능 여부를 직접 바꾼다** (실측으로 잡은 함정). 구 크레이터 가장자리는 수직이라 가장자리 ε 구간의 상승량이 **√(2Rε)** 다. R=3m 기준 걸음 0.5m면 1.73m(턱 초과 → 막힘), 0.25m면 1.22m(경계), 0.1m면 0.77m(통과).
> → **`WalkStep = 0.25m`로 고정한다.** 이동을 이보다 큰 단위로 쪼개면 멀쩡한 크레이터에서 탱크가 갇힌다.
>
> ⚠️ **갇힘 판정을 "한 걸음 가능한가"로 하면 안 된다.** 크레이터 바닥에서 옆 바닥으로 가는 것도 한 걸음이라 Rc=14m조차 8/8 통과로 나온다. **밖까지 연쇄 이동**으로 판정해야 한다.
>
> ⚠️ **접지는 위가 아니라 발밑에서 아래로 찾는다**(`GroundBelow`). 위에서 찾으면 오버행 아래 탱크가 처마 위로 순간이동한다(실측 확인: 공동 안 18.8m 탱크 → 처마 26.5m로 튐).
>
> ⚠️ 자동 구제(텔레포트·무료 이동·지형 복구)를 **넣지 마라.** 포격으로 만든 지형이 무의미해진다. 갇힘은 숨기지 말고 HUD에 남은 탈출 방향 수를 표시한다.

#### (3) 굴착탄 프레임 스파이크 ✅

**42.69 ms → 8.82 ms (4.8배).** Job System 병렬화 없이 알고리즘만으로.

| | 개선 전 | 개선 후 |
|---|---|---|
| 초기 지형 전체 | 411 ms | **127 ms** |
| 일반탄 (SDF+메시) | 13.2 ms | **5.2 ms** |
| **굴착탄 (SDF+메시)** | 59.6 ms | **15.1 ms** (프레임 예산 안) |
| 폭발 100회 | 589 ms | **271 ms** |

두 가지가 전부였다:
1. **`h(x,z)`를 (i,k) 평면에 캐시** — y에 무관한데 y축으로 18번 중복 계산 중이었다(18³→18²). 프로파일 결과 청크 빌드의 46%.
2. **표면 없는 청크 조기 탈출** — `FillBlock`이 min/max를 함께 반환하고, 전부 땅이거나 전부 공기면 즉시 반환. 폭발의 dirty 범위는 육면체인데 깎이는 건 내접한 구라 **모서리 청크들이 전부 걸린다**(굴착탄에서 특히).

⚠️ 최적화 후에도 삼각형 수(451,270)와 §7-4의 오버행·동굴 검증 결과가 **완전히 동일**함을 확인했다 — 최적화가 결과를 바꾸지 않았다.

Job System 병렬화는 **더 이상 필요 없다**(청크 빌드가 서로 독립이라 언제든 붙일 수 있지만, 지금 수치로는 근거가 없다).

### 9-1. 구조

```
TankVisualData (SO)          →  TankMeshBuilder (S)  →  Mesh ×3
─────────────────────────       ──────────────────      ────────
bodyLength/Width/Height          박스·실린더 프리미티브   Body
trackWidth/Radius/Count          합성 + 정점 병합        Turret
turretRadius/Height                                     Barrel
barrelLength/Caliber
muzzleBrake (bool)
silhouetteTag (enum)
```

**분리 이유**: 포탑은 야우 회전, 포신은 피치 회전이 필요하므로 GameObject를 나눠야 한다.

```
Tank (root)
└── Body          [Mesh: 차체 + 궤도 + 보기륜]
    └── Turret    [Mesh: 포탑]  ← yaw 회전
        └── Barrel[Mesh: 포신]  ← pitch 회전
            └── FirePoint (empty)  ← 발사 원점 P₀
```

### 9-2. 프리미티브

`TankPartMeshes.cs`가 제공: `Box`, `Cylinder(축, 세그먼트)`, `Wedge`(차체 경사장갑), `TrackLoop`(캐터필러 단면 압출).

목표 정점 수 **500~1,500**. 세그먼트 수는 실린더 10~12면 충분(세미 스타일라이즈드, §71).

## 10. 네트워크 계약

### 10-1. 클라이언트가 보낼 수 있는 것 (전부)

```csharp
struct MoveCommand  { byte tankId; ushort turnSeq; Vector3Q[] waypoints; }
struct FireCommand  { byte tankId; ushort turnSeq; int yawQ; int pitchQ; ushort powerQ; byte weaponSlot; }
```

그 외 **아무것도 없다.** 특히 "맞았다", "피해량", "내 위치" 없음(기획서 §78).

### 10-2. 서버가 보내는 것

```csharp
struct TurnResult {
  ushort turnSeq;
  ImpactRecord[]  impacts;      // 다연장 대비 배열
  DamageEvent[]   damages;      // { tankId, amount, isDirect, faceSide }
  TerrainDelta[]  terrainDeltas;
  FallEvent[]     falls;        // { tankId, fromY, toY, damage }
  TankStateSync[] states;       // 턴 종료 시점 권위 상태 (드리프트 보정)
}
```

### 10-3. 결정론 방어

부동소수점 결정론은 플랫폼 간(x86/ARM) 보장되지 않는다. **결정론에 의존하지 않는 설계**를 쓴다:
- 클라는 궤적을 **예측 재생**할 수 있지만(같은 코드라 보통 일치), **권위는 항상 `TurnResult`**
- 지형은 **델타를 명시 전송**한다(재계산 의존 금지) — 한 번 어긋나면 이후 모든 궤적이 어긋나므로 지형만은 절대 재계산에 맡기지 않는다
- 불일치 감지 시 `TankStateSync`로 스냅

### 10-4. 로컬 모드도 같은 경로

`LocalTransport`가 `ServerAuthority`를 같은 프로세스에서 호출한다. **싱글플레이와 멀티플레이가 같은 코드 경로를 탄다** → 멀티를 나중에 붙일 때(§91) 재작성이 없다. 이게 §11 마일스톤에서 네트워크를 맨 뒤로 미룰 수 있는 근거다.

### 12-1. 🟡 `g = 30` 이 왜 아직 열려 있나 — **M1 네거티브 컨트롤이 실시되지 않았다**

§11 머리말은 이렇게 못 박았다: 「각 게이트는 "통과"가 아니라 **"빨간불을 먼저 봤는가"**로 판정한다.
**네거티브 컨트롤이 없는 통과는 통과가 아니다.**」
그리고 M1 게이트 본문이 그 대조군을 **명시**한다:
> `g` 를 30→15 로 바꿨을 때 체감이 명확히 달라지는가(안 달라지면 파워/각도가 결과를 지배하지 않는다는 뜻 → 상수 재설계)

🚨 **그 대조군을 안 한 채로 M1 을 통과 처리했다**(2026-09-19 오너 판정). 판정 자체는 유효하지만,
**«다른 값과 비교한 통과»는 아니다** — 이 프로젝트가 하루에 두 번 잡은 결함(**«한쪽만 보고 통과»**)이
**최대 관문의 판정**에 그대로 들어 있다.

- 이 줄이 남아 있는 한 §11 M1 의 ✅ 는 **「네거티브 컨트롤 미실시」 딱지를 달고 있는 통과**다.
- 닫는 방법은 하나뿐이다: **오너가 `g=15` 로 몇 발 쏴 보고 체감이 달라지는지 말해 주는 것.**
- ⚠️ **`Gravity` 기본값 30 은 한 글자도 안 바뀐다.** 필요한 것은 «대조군 스위치»이지 수치 변경이 아니다.
- 🛑 그 스위치로 **밸런스 표를 다시 뜨지 마라.** 재는 것은 **사람의 체감** 하나다.
