## 2. ⚠️ 최대 변수 — 시트 단위로 뽑을 수 있는가

애니메이션을 **프레임 1장씩** 뽑을지, **시트 1장에 여러 프레임**을 담아 `split_sheets.py`로 자를지가 비용을 25배 가른다.

| 방식 | 잡몹 1종(11프레임 × 3방향 = 33장) | 크레딧 |
|---|---|---|
| 프레임 단위 | 33회 호출 | **66** |
| 시트 단위 (방향당 1장) | 3회 호출 | **6** |

오너의 기존 시트가 정확히 후자다(1536×1024 한 장에 여러 상태·프레임). **가능성은 실재하지만 아직 검증되지 않았다** — AI는 격자 셀 간 캐릭터 동일성을 자주 놓친다.

추가 제약: `split_sheets.py`는 배경 `#0D0D0D`, 격자선 밝기 45~130, 셀 128px, 여백 6px 이상을 요구한다. AI가 이 규격을 그대로 맞추긴 어려울 수 있으므로, **맞으면 그대로 쓰고 안 맞으면 스플리터를 AI 산출물 쪽에 맞춰 고친다**(사람이 다시 그리는 것보다 스크립트를 고치는 쪽이 싸다).

## 4. 앵커 전략 — 카테고리마다 다른 앵커

**하나의 앵커로 전부 덮지 않는다.** 프랍 앵커로 몬스터를 뽑으면 몬스터가 프랍처럼 나온다.

| 카테고리 | 앵커 | 상태 |
|---|---|---|
| 프랍·타일 | `art/anchor_characters.png` (오너 캐릭터 5종 합성) | ✅ 검증 완료 |
| 잡몹·정예 | `blender/source_sheets/sheet5_monster.png` | 미검증 |
| 캐릭터·보스 | `sheet1_base_motion.png` + `sheet3_character_design.png` | 미검증 |
| UI 아이콘 | 시트③의 직업 아이콘 4종(방패·교차검·십자지팡이·사각별) | 미검증 |

### ⚠️ 앵커와 팔레트 스왑의 충돌 — P0에서 반드시 확인할 것

문서 §5는 잡몹 프롬프트에 `neutral gray-white base color for palette swapping`을 **가장 중요한 구절**로 지정했다. 계열 5색을 색조 셰이더로 입히려면 원본이 무채색이어야 하기 때문이다.

그런데 **우리 앵커는 채도가 높다**(탱=청/금, 딜=흑/자주). 앵커가 화풍과 함께 *색까지* 전이시키면 무채색 요구가 깨지고 **계열 구분 전체가 무너진다.**

→ P0에서 "앵커를 물린 채로 무채색이 나오는가"를 별도로 확인한다. 안 되면 **잡몹 전용 무채색 앵커**를 따로 만든다(기존 몹 스프라이트를 회색조 변환해 사용).

## 6. 🔴 게임 연결 검토 (2026-08-14) — **리소스를 만들기 전에 고쳐야 하는 것**

> 이 프로젝트는 이미 **"수치는 나왔는데 화면이 비어 있었다"**(§21-1b)와 **"적용했는데 화면엔 안 나오는"**(`SpriteBank.cs:168`) 사고를 겪었다. 그래서 만들기 전에 받을 자리를 먼저 봤다. 아래는 코드를 직접 읽고 실측한 결과다.

### 🔴 C1. 방향 지원이 코드에 아예 없다 — 계획대로 뽑으면 물량 2/3이 버려진다

`GAME_ART_RESOURCES.md` §0-B 규칙 1과 프롬프트 문서 §1-4는 **모든 물량을 "×3방향(S·E·N)"으로 곱해** 산정했다(잡몹 178장·보스 552장의 3분의 2가 방향 때문이다).

그런데 받는 쪽에 방향이라는 개념이 없다:

| 지점 | 실측 |
|---|---|
| `SpriteBank.Char(Job, Frame)` | 방향 인자 **없음** |
| `SpriteBank.MobAnim(kind, Motion, t)` | 방향 인자 **없음** |
| `flipX` | 프리팹 파일에 `m_FlipX: 0`으로 있을 뿐 **런타임에 아무도 안 건드린다** |
| 파일명 규칙 | `<유닛>_<상태>_<번호>.png` — **방향 자리가 없다** |

→ **판단이 필요하다.** 둘 중 하나다:
- **(A) 방향을 포기한다** — 1방향만 뽑고 이동 방향은 `flipX`로 좌우만. 물량이 **1/3**로 준다(잡몹 178→60, 보스 552→184). 뱀서라이크는 화면에 수백 체가 나와 개별 방향이 잘 안 보인다는 §0-A의 논리를 한 단계 더 밀면 여기까지 온다
- **(B) 방향을 지원한다** — 파일명에 방향 자리를 넣고(`<유닛>_<상태>_<방향>_<번호>`), `SpriteBank`에 방향 인자를 추가하고, 렌더러가 이동 벡터로 방향을 고르게 한다. **코드 작업이 선행**돼야 한다

⚠️ **어느 쪽이든 리소스를 뽑기 전에 정해야 한다.** 나중에 뒤집으면 3배를 버리거나 3배를 다시 뽑는다.

### 🔴 C2. 아틀라스가 이미 58% 찼다 — W4 물량이 그대로 들어가면 조용히 뭉개진다

`SpriteBank`는 전부를 **4096² 런타임 아틀라스 한 장**에 넣는다(배칭이 W1 성능의 전제). 코드 주석이 이미 경고한다: *"아틀라스가 넘치면 PackTextures가 **조용히 축소**해 스프라이트가 뭉개진다."*

실측(2026-08-14):

| 구간 | 장수 | 면적 |
|---|---|---|
| 직업 4종 (tank·dps·healer·buffer) | 52 | 6.45 Mpx |
| mob01 | 22 | 0.50 Mpx |
| 루트 플레이스홀더 | 8 | 2.23 Mpx |
| ranged (미사용) | 5 | 0.62 Mpx |
| **합계 / 4096²=16.78Mpx** | **87** | **9.77 Mpx (58%)** |

**캐릭터 평균 크기(124k px) 기준 약 56장밖에 안 남는다.** W4 계획은 잡몹 132장 + 보스 138장이다 — 그대로는 못 들어간다.

→ **해결: 아틀라스 입력을 128px로 정규화한다.** 문서 §2가 이미 "런타임 스프라이트 128px"로 정해둔 규격인데 **현재 오너 아트는 416×297 원본 그대로 들어가 있다**(3.2배 낭비). `SpriteBank`는 PPU를 내용 높이로 역산하므로 128px 입력이어도 화면 크기는 그대로다. 정규화하면 캐릭터 구간이 6.45→0.63Mpx로 줄어 **여유가 10배**가 된다.
- 화면상 캐릭터는 2유닛 ≈ 108px로 보인다 → 128px 원본이면 충분하고 416px는 낭비다
- 루트 플레이스홀더 8장(2.23Mpx)과 미사용 `ranged/` 5장(0.62Mpx)은 교체·정리하면 추가로 비워진다

### 🔴 C3. 스타일 앵커의 채도가 계열 색조를 죽인다

계열 5종 구분은 `ProjectSetup.cs:343`의 `sr.color = m.색조` **한 줄**에 달려 있다. 이것은 **곱셈 틴트**라 원본이 무채색일 때만 5색이 서로 구분된다 — 프롬프트 문서 §5가 `neutral gray-white base color for palette swapping`을 "이 4줄에서 가장 중요한 구절"이라고 못 박은 이유다.

그런데 **우리 앵커는 채도가 높다**(탱=청/금, 딜=흑/자주). 앵커가 화풍과 함께 색까지 전이시키면 계열 구분 전체가 무너진다.

→ **잡몹·보스 전용 무채색 앵커를 따로 만든다.** 기존 몹 아트를 회색조 변환해 앵커로 쓰고, P0에서 "앵커를 물린 채 무채색이 나오는가"를 반드시 확인한다.

### 🟠 C4. 프레임 규격이 문서와 코드에서 어긋나 있다

| | 코드 (`SpriteBank`) | 문서 (§1-2) |
|---|---|---|
| 직업 | `JOB_FRAMES` **13 고정** (idle1·walk2·attack2·special1·hurt1·death1·dash4·invuln1) | 상태당 3~4프레임 |
| 잡몹 | `MOB_FRAMES` **22 고정** (idle4·walk6·atk4·hurt4·death4) | idle2·walk2·attack2·hurt1·death3 = **11** |

문서대로 11프레임을 뽑으면 로더가 22칸을 기대해 **11장이 누락 경고 + 단색 대체**가 된다. 반대로 22장을 뽑으면 문서 예산이 2배가 된다.

→ **뽑기 전에 한쪽으로 통일해야 한다.** 잡몹은 화면에 500체가 나오므로 문서(11프레임)가 옳고, `MOB_FRAMES`·`MobFrame`·`MobAnim`을 11프레임으로 줄이는 쪽을 권한다.

### 🟠 C5. 몹의 추가 상태를 재생할 슬롯이 없다

프롬프트 문서 §1-3은 `telegraph`(0.80초)·`dash`·`stagger`·`aim`·`fire`·`revive`·`explode`를 정의하고 **"이 길이가 곧 회피 가능성"**이라고 밸런스 수치로 못 박았다. 그런데 `MobFrame` enum에 이 상태들이 **하나도 없고** `MobAnim`의 `switch`도 Walk·Attack·Hurt·Death뿐이다.

→ 돌진 예고 0.8초를 뽑아도 **재생할 방법이 없다.** `Motion` enum과 `MobAnim`을 먼저 확장해야 한다.

### 🟠 C6. 보스는 애니메이션 경로 자체가 없다

`boss_0` **단일 스프라이트**가 `MakeAt(5, U_PROJ)`로 투사체 자리에 들어가 있고(`b.Projectile`), 보스용 `MobAnim` 경로가 없다. 보스 실루엣 4종 × 46프레임 계획을 받을 구조가 존재하지 않는다.

### 🟡 C7. 자잘한 불일치

- `elite_healer_0`가 `b.Summon`으로 로드된다 — 이름과 용도가 어긋나 다음 사람이 오해한다
- `ranged/` 5장(dash 4 + invuln 1)은 `JOB_DIRS`에 없어 **로드되지 않는다**. 완성하든 지우든 정해야 한다

### 🟢 C8. 문서가 낡은 것 하나 — 이미 해결됨

`GAME_ART_RESOURCES.md` §0-A는 *"현재 규칙은 Bilinear라 도트가 뭉개진다 — 방향별 도착 전에 수정할 것"*이라고 경고하는데, `Editor/TextureImportRules.cs`는 이미 `isReadable=true` · `Uncompressed` · `FilterMode.Point`를 전부 적용하고 있다(지형만 의도적으로 Bilinear). **조치 불필요 — 문서 쪽을 갱신해야 한다.**
