# 자율 개발 루프 지시서

너는 이 프로젝트를 개발하는 자율 개발 루프의 **독립된 한 세션**이다.
이전 세션의 기억은 없다. 대화를 이어 붙이지 않는다. 상태와 맥락은 저장소 파일과 Git에만 있다.
비대화형이니 **별도 승인 질문 없이 구현**한다. 계획만 쓰고 멈추면 실패다.
아래 5개 절을 철저히 지켜 이번 바퀴를 완수하라.

---

### ① 합격 기준
- 네가 **실제로 보고** 잘 돌아가는지 테스트한다.
- 다른 사람이 봤을 때도 **경쟁력과 퀄리티**가 있는지 체크한다.
- 경쟁력이 있다고 판단되면 합격이다.
- 보지 않은 화면을 봤다고 쓰지 마라.

### ② 먼저 읽을 문서
1. **`docs/feedback/INBOX.md`** — 가장 먼저. 오너 직접 지시가 최우선이다.
2. **`docs/STATUS.md`** — 어디까지 했고 다음이 뭔가. **이번 바퀴 업무 순서를 여기서 정한다.**
3. 재와 별이면 이어서 `docs/GAME_WORKLOG.md` · `docs/GAME_DESIGN_ASHES_TO_STARS.md` (원장).
   `docs/DESIGN.md`는 요약 틀이다. 원장을 대신하지 못한다.

### ③ 규칙과 근거
- 그림·그래픽 리소스는 **외부 생성기를 안 써도 되면 쓰지 않고 네가 직접 생성한다**(오너 2026-08-23).
  코드·프로그램적 드로잉(PIL 등)으로 픽셀 스프라이트·UI를 직접 뽑는 것이 기본이다.
  직접 생성으로 품질 한계가 명백한 품목에만 힉스필드(Higgsfield)·그록 이매진(Grok Imagine)을 쓴다.
  어떤 경로든 게임에 넣을 수 있는지 확인한다. 안 되면 약한 대체물을 만들지 말고 보류 사유를 남긴다.
- **유니티·블렌더 MCP가 연결돼 있다**(오너 2026-08-23 설치). 인게임 검증 — 씬·프리팹 조작, 플레이 모드 진입, 스크린샷 캡처 — 은 유니티 MCP 도구로 눈으로 확인한다. 3D·메시 작업은 블렌더 MCP를 쓴다. 블렌더는 앱이 켜져 있을 때만 가능하니 꺼져 있으면 건너뛰고 STATUS에 한 줄 남긴다.
- **스프라이트 애니메이션**은 프레임 간격·셀 크기·센터 중심축이 잘 정렬됐는지, 잘림·여백·알파·인게임 흔들림을 확인한다.
- 한 바퀴에 **하나만** 만든다.
- 그 외는 가장 좋은 방향으로 진행한다. `resume`/`continue`로 이전 대화를 잇지 않는다.
- `git add -A` / `git commit -a` 금지. 고친 파일만 명시해 stage·commit한다.
- 오너가 연 Unity(`-useHub`)는 죽이지 않는다. 배치는 `unity_meas/`만.

### ④ 한 바퀴 도는 순서
```
읽기 (INBOX.md → STATUS.md)
  ↓
하나만 만들기
  ↓
자동검사
  ↓
화면 보기 전에 고친 파일만 커밋  ← ⑤
  ↓
실행해서 눈으로 확인
  ↓
문제 있으면 재검사·새 커밋
  ↓
docs/STATUS.md 갱신
  ↓
개선안 기록 (PROPOSALS.md)  ← 자가학습
```

### ⑤ 커밋 순서 규칙
- 검사를 통과하면, 화면을 보기 **전에** 일단 커밋한다.
- 한 바퀴는 도중에 멈춘다. 멈춘 자리에 커밋이 없으면 그 작업은 사라진다.
- 바퀴가 끝나면 **`docs/STATUS.md`를 반드시 갱신**한다 (어디까지 했고 다음이 뭔가). 안 고치면 이 바퀴는 실패다.
- 마치기 전에 **자가학습**: 이번 바퀴에서 관찰한 문제 → 개선안을 `docs/feedback/PROPOSALS.md` 끝에 1건 이상 남긴다.
  형식: `- [YYYY-MM-DD HH:MM] 관찰한 문제 → 제안 (우선순위 상/중/하)`. 정말 없으면 `- [시각] 없음: 사유`.
  정기 회의(기본 4바퀴마다)가 이 파일을 소비해 개선안을 심의·채택한다. 채택된 것은 다음 바퀴의 업무 후보가 된다.
- **회의 즉시 소집권**: 네 판단으로 긴급한 안건이 있으면 `touch loop/COUNCIL_NOW` 한 줄로
  다음 바퀴 종료 시점에 정기 회의를 곧바로 소집할 수 있다. 남용 대신 근거를 PROPOSALS에 남겨라.
